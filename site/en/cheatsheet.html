3. Tiled matmul: W×W, T×T, W % T = 0

__shared__ float Mds[T][T], Nds[T][T];
int row=blockIdx.y*T+ty, col=blockIdx.x*T+tx;
float sum=0;
for (int m=0; m<W/T; ++m) {
  Mds[ty][tx] = M[row*W + m*T + tx];
  Nds[ty][tx] = N[(m*T + ty)*W + col];
  __syncthreads();                // tile ready
  for (int k=0;k<T;++k) sum+=Mds[ty][k]*Nds[k][tx];
  __syncthreads();                // tile may be overwritten
}
P[row*W+col]=sum;

W=matrix width, T=tile side (=blockDim.x=blockDim.y in this example); tx=threadIdx.x, ty=threadIdx.y; m=phase; phase=tile number (starting at 0), k=inner tile multiplication index (0..T-1); Mds/Nds=shared tiles; sum=output accumulator. First sync waits for loads, second protects reuse.

5. __syncthreads() rules

// wrong: divergent barrier
if (tid<16) { s[tid]=v; __syncthreads(); }
// correct:
if (tid<16) s[tid]=v;
__syncthreads();
// load → sync → use → sync → next load

Block barrier; all participating threads must reach it. Synchronize shared write→other-thread read; divergent if/early return unsafe.

6. Shared memory and reverse

__shared__ float s[B]; // per-block, on-chip
int t=threadIdx.x, i=blockIdx.x*B+t;
s[t]=in[i]; __syncthreads();
out[i]=s[B-1-t]; // reverse within block
// reuse tile before loading next phase

Without the barrier, reading another thread's value may race. Blocks are independent.

8. Transpose: access direction

// A and B: N×N, row-major
naive: B[col*N+row] = A[row*N+col];
read: adjacent col → contiguous
write: adjacent col → stride N
shared (T=32, block=32×32):

GPU memory hierarchy: where is each memory located?

ThreadRegisters: private to one thread, located on its SM
SM (Streaming Multiprocessor)Shared memory: explicit per-block scratchpad. L1: hardware-managed cache local to the SM.
GPU chipL2: one shared cache serving all SMs.
GPU memory (VRAM)Global device DRAM. Private local/spill data may be stored here too.
CPU / host RAMSystem memory, conceptually distinct from VRAM. CPU L1/L2 caches are not GPU L1/L2 caches.
MemoryWho accesses it?Location / control
RegisterOne threadOn an SM, compiler allocated
LocalOne threadNormally backed by device DRAM, may be cached in L1/L2
Shared (__shared__)Threads in one blockOn-SM storage, loaded/updated by explicit CUDA code
L1 cacheAccesses by an SMEach SM has its own hardware cache; on some architectures shares a physical pool with shared memory
L2 cacheAll SMsLarger, chip-wide hardware-managed cache
Global memoryAll device threadsDevice DRAM/VRAM
ConstantAll device threads (read)Read-only in kernels, can benefit from the constant cache

Cache hit: requested data already resides in the cache. Cache miss: fetch from a lower level. The common hierarchy puts registers, shared memory and caches close to computation; VRAM is larger and often higher latency. Do not memorize fixed sizes: L1/L2 capacities, latency, L1/shared configuration and caching behavior are GPU-dependent. L1 cache is not the same programming abstraction as shared memory, even when some hardware partitions the same on-SM capacity between them.

Units: 1 B=8 bits; 1 KiB=1024 B; 1 MiB=1024 KiB; float=4 B; 32 floats=128 B; pitchBytes is actual row stride in bytes (possibly greater than W×4 B). A hypothetical 32 B access segment is not automatically equal to a GPU L1/L2 cache line.

Coalescing: count warp accesses and transpose stride

// Warp: 32 threads; lane = 0..31; float=4 B
// Assume base address aligned to 32 B.
A[lane]       : offsets 0,4,...,124 B -> 4 segments =128 B
A[lane+1]     : offsets 4,8,...,128 B -> 5 segments =160 B
A[2*lane]     : offsets 0,8,...,248 B -> 8 segments =256 B
A[8*lane]     : offsets 0,32,...,992 B -> 32 segments =1024 B
A[1024*lane]  : offsets 0,4096,... -> 32 segments =1024 B
// Actual cache hits and transaction counts depend on GPU.
// Row-major matrix: A[row*W+col] (W = column count)
// x-neighbor threads -> col+1 -> +4 B: contiguous.
// Naive transpose: B[col*H+row] (H = output width)
// x-neighbor threads -> col+1 -> +4*H B: strided.

32 threads × 4 B = 128 B useful data. Consecutive A[lane] touches four aligned 32 B segments (128 B). A[2*lane] touches eight (256 B). Far-apart A[1024*lane] touches 32 (1024 B). These are modeled access segments, not universal GPU cache-line sizes or guaranteed memory transaction counts.

Matrix offsets: A[row*W+col], W=number of input columns. Increasing col by one for adjacent x threads advances by 4 bytes. Transpose: H×W input becomes W×H output, with B[col*H+row]. Adjacent x threads advance output stores by 4×H bytes, which can be inefficient.

Different mechanisms: Coalescing concerns the warp's address pattern; L1/L2 cache hit/miss concerns which data is already cached. pitchBytes is a row stride in bytes, applied before converting to float indexing.

Quick check: transpose and memory

If H=3, W=4, row=1, col=2: input A[1*4+2]=A[6], output B[2*3+1]=B[7]. L1 cache is on each SM; L2 cache is shared among SMs.

What does a mutex prevent? Two threads updating a counter

#include <mutex>
std::mutex m; // shared lock
int counter=0; // shared data
void increment(){
  std::lock_guard<std::mutex> hold(m); // lock
  ++counter; // protected critical section
} // hold destroyed => unlock

Timeline: (1) counter=0. (2) T0 locks mutex m. (3) T1 must wait. (4) T0 increments to 1 and lock_guard unlocks at scope exit. (5) T1 locks and increments to 2. Final value: 2. Without protection both could read 0 and write 1; an actual C++ data race is undefined behaviour.

Variables: m=exclusive mutex, counter=shared integer, hold=RAII guard object; lock_guard unlocks automatically. Manual lock/unlock is possible, but RAII is safer.

Producer–consumer: mutex, condition_variable and semaphore

#include <mutex>
#include <condition_variable>
#include <queue>
std::mutex m;
std::condition_variable cv;
std::queue<int> q; bool finished=false;
void produce(int value) {
  { std::lock_guard<std::mutex> lock(m);
    q.push(value); }
  cv.notify_one();
}
int consume() {
  std::unique_lock<std::mutex> lock(m);
  cv.wait(lock, [] { return !q.empty() || finished; });
  if(q.empty()) return -1; // finished, no work
  int v=q.front(); q.pop(); return v;
}
// When ending, set finished=true WITH m locked,
// then cv.notify_all(). -1 is the end marker.

The producer adds value to queue q while mutex m protects the container. cv.notify_one() alerts one waiting consumer. The consumer calls cv.wait(lock,predicate): it releases the mutex while sleeping, reacquires it on waking and rechecks the condition.

Variables: q=FIFO queue, m=mutex, cv=condition variable, finished=producer has stopped, v=consumed item. A unique_lock is needed so wait can unlock/relock the mutex. std::counting_semaphore<3> permits(3) allows up to 3 concurrent jobs, but does not alone guard a shared counter or queue.

#include <semaphore>
#include <mutex>
std::counting_semaphore<3> permits(3); // 3 slots
std::mutex m; int counter=0;
void job(){
  permits.acquire(); // 3 jobs may enter
  { std::lock_guard<std::mutex> guard(m);
    ++counter; } // only 1 writes at a time
  doWorkNoThrow(); // illustrative: no exception
  permits.release(); // return slot
}

Deadlock, starvation, livelock and prevention

std::mutex m1, m2;
// Bad: T0 locks m1 -> waits m2
//      T1 locks m2 -> waits m1
void safe(){ std::scoped_lock both(m1,m2);
  // both locks acquired without circular wait
}
// std::unique_lock is movable and supports
// unlock()/lock(); used by condition_variable.

Deadlock: T0 holds m1 and waits for m2; T1 holds m2 and waits for m1. Neither progresses. std::scoped_lock both(m1,m2) acquires both locks using deadlock-avoidance logic. Or acquire locks in the same order everywhere.

Starvation: a participant repeatedly cannot obtain its turn. Livelock: participants keep taking actions but make no useful progress. unique_lock is movable and unlockable; it supports condition_variable::wait.

H=6; W=8;
blockIdx=(1,0); blockDim=(4,2); threadIdx=(2,1);
row=0*2+1=1; col=1*4+2=6;
for(dy=0;dy<3;dy++){

Why: Because blockIdx and threadIdx are fixed, col=6 never changes. Only loop variable dy moves r by two. Rows 1, 3 and 5 are inside H=6. Draw: column 6 at rows 1, 3 and 5 (zero-based).

3. Mutex, lock_guard and semaphore are not interchangeable

#include <mutex>
#include <semaphore>
std::mutex m;
std::counting_semaphore<3> slots(3);
int counter=0;
void job(){
  slots.acquire(); // at most 3 jobs enter
  { std::lock_guard<std::mutex> hold(m);
    ++counter; }  // only 1 thread modifies it
  doWork();
  slots.release();
}
// Without mutex, 3 concurrent increments may race.

Difference: A semaphore allows three concurrent jobs; it does not give mutual exclusion for counter++. A mutex allows one owner. A lock_guard releases its mutex at scope exit.

Explain: Threads acquiring m1→m2 and m2→m1 can deadlock. Starvation is when a thread keeps being denied progress. No particular output is guaranteed for a C++ data race.

4. Coalescing: addresses and 32 B segments

32 lanes, float=4 B, aligned base=0
lane i: A[i]        -> 0,4,8,...,124 B
  covered segment numbers: 0,1,2,3 (4×32B)
lane i: A[2*i]      -> 0,8,16,...,248 B
  segments: 0..7 (8×32B)
lane i: A[1024*i]   -> spacing=4096 B
  segments: 32 distinct (32×32B = 1024B)
A[row*W+col] -> if col changes +1, address +4B

Why: In row-major memory, adjacent x-lanes reading adjacent columns request 128 contiguous bytes, which occupy four aligned 32 B segments. Advancing the row instead changes the offset by W elements.

Important: This is an aligned 32 B segment teaching model; actual cache and transaction behavior depends on the GPU. Pitch is expressed in bytes: base + row*pitchBytes + col*4.

5. Tiled matmul: what one thread loads in one phase

N=32; T=8; blockIdx=(1,0);
threadIdx=(2,3); phase=1
row=0*8+3=3; col=1*8+2=10
Mds[3][2] <- M[3][1*8+2] = M[3][10] = M[106]
Nds[3][2] <- N[1*8+3][10] = N[11][10] = N[362]
__syncthreads(); // all shared tiles loaded
for(k=0;k<8;k++) sum+=Mds[3][k]*Nds[k][2];
__syncthreads(); // next phase must not overwrite
P[3*32+10] = P[106] <- accumulated 4 phases

One thread per phase loads two global values but performs eight multiply-accumulates; the other 63 threads load the rest of the tile for shared-memory reuse. There are four phases: 0,1,2,3.

Two barriers: The first prevents reading before the cooperative tile is filled (RAW). The second prevents the next phase overwriting values still in use. Avoid divergent barrier control flow.

6. Transpose: one value, two different linear offsets

A is 3×5 (H=3,W=5), B is 5×3
A[row=1][col=3] => A[1*5+3] = A[8]
B[col=3][row=1] => B[3*3+1] = B[10]
__global__ void trans(float*A,float*B,int H,int W){
  int row=blockIdx.y*blockDim.y+threadIdx.y;
  int col=blockIdx.x*blockDim.x+threadIdx.x;
  if(row<H && col<W) B[col*H+row]=A[row*W+col];
}

Why: A has width 5; B has width 3. The value's row and column swap. Adjacent x-lanes may read A contiguously but their output stores have an H-element stride.

Exam technique: Write the output shape first (W×H), then multiply the output row by the new width when forming its linear offset.

5. __syncthreads() rules

  • Barrier within a block only; none across blocks (split the kernel / cooperative groups, CUDA 9+).
  • All threads of the block must execute it. Inside an if or after an early return = undefined (unless the condition is the same for everyone).
  • Required before reading shared data written by another thread. It actually synchronises warps.
  • ✗ if (tid<16){ s[tid]=..; __syncthreads(); } → ✓ if (tid<16) s[tid]=..; __syncthreads();

Moore's law and the power wall

  • Moore's law (Gordon Moore, 1970s): the number of transistors in an integrated circuit doubles about every two years. Transistor count, not frequency.
  • Frequency alone is not a comparison criterion: operations take different numbers of cycles (on x86-64, 32-bit integer add 1 cycle, 32-bit FP multiply 4).
  • For a long time more transistors came with higher frequencies; but higher frequency = more heat. Voltages were lowered (~1.29 V) but not enough. Around 2004–2005 frequencies maxed out at 2–4 GHz (Gelsinger's power wall).
  • The route left: put more logic and more cores on a chip. The first dual-core single-die chip: IBM Power 4 (2001); a natural evolution of multi-socket platforms.
  • GPGPU: a single GPU core is weaker than a CPU core, but hundreds/thousands of cores + high-bandwidth memory → orders of magnitude faster. Also better GFLOP/Watt: in servers and the cloud the energy a CPU uses over its lifetime can exceed its price.
  • Not free: multi-core needs multi-threaded, parallel code; algorithms must be redesigned and new APIs (CUDA, OpenCL) learnt.

Flynn's taxonomy

Michael Flynn (1966): machines are classified by (1) how many data items they process concurrently and (2) how many different instructions they execute at the same time.

ClassDescription
SISDA simple sequential machine: one instruction, one data item at a time.
SIMDEach instruction is applied to a collection of items; vector processors were the first.
MISDNormally makes no sense; in fault-tolerant systems (military, aerospace) the same data is processed by several machines and a majority decision is taken.
MIMDThe most versatile class. Multi-core machines, including GPUs.

Shared and distributed memory MIMD

  • Shared-memory MIMD: a universally accessible shared memory space. Communication between CPUs is cheap but memory is a bottleneck limiting scalability. Fix: partition memory among CPUs; local memory is fast, remote memory slower, addressing still universal: NUMA (up to a few tens of CPUs). Subtypes: SMP (all CPUs equivalent) and master-worker (some processors run specialised software, like coprocessors: GPU systems resemble this, though most have separate CPU and GPU memory spaces).
  • Distributed-memory (shared-nothing) MIMD: each processor has private memory; they communicate by exchanging messages. Communication is expensive, but with no single contested medium they scale without practical limit (apart from space and energy).

Modern processors: CPU and GPU

CPU: (1) large, multilevel caches, (2) few complex (pipelined) ALUs, (3) complex instruction decoding and prediction hardware to avoid stalling while waiting for main memory. Latency-oriented.

GPU: (1) small caches, (2) many simple ALUs operating in parallel (little data reuse in graphics, simple programs), (3) very wide, fast memory buses to feed the cores. Throughput-oriented.

NVIDIA Blackwell

  • Successor of Hopper and Ada Lovelace; aimed at AI, HPC and accelerated computing. Cores are grouped into SMs; each SM has 128 CUDA cores (SIMT) and can run its own program (blocks are scheduled independently on different SMs).
  • Hierarchy: GPU → GPC → TPC (2 SMs each) → SM. Per SM: 128 CUDA cores, 1 RT core, 4 Tensor cores, 4 SFUs, 4 texture units, a 256 KB register file, 128 KB L1/shared, schedulers. 64-bit FP throughput is about half of 32-bit.
  • B200: dual die (10 TB/s NV-HBI), 208 billion transistors, 148 active SMs = 18,944 CUDA cores, 592 Tensor cores.

Other examples: AMD APU (CPU and GPU on the same die, unified memory space → no data transfers; HSA: latency-oriented LCUs and throughput-oriented TCUs), the Cell BE, multi-core CPUs (TILE-Gx8072, Intel Xeon Phi).

Performance metrics

speedup = t_seq / t_par efficiency = speedup / N = t_seq / (N · t_par) (N = number of cores) speedup = N → linear speedup, 100% efficiency
  • Times depend on the programmer's skill, the compiler and its switches, the OS, the filesystem, the time of day.
  • Golden rules: (1) test the sequential and parallel programs on identical hardware/software under similar conditions; (2) the sequential program should be the fastest known solution.
  • Speedup may vary with the input: report averages (or avg./max./min.) over many inputs of the same size.
  • Speedup answers "can it be accelerated?", efficiency "with a modest amount of resources?". Linear speedup is ideal; coordination (messages, shared resources) eats CPU time.

Amdahl's law

Assumptions: the sequential application takes T on one CPU; a part α (0 ≤ α ≤ 1) can be parallelised, (1 − α) must be sequential; no communication cost, the parallel part divides evenly.

speedup = T / ((1 − α)T + αT/N) = 1 / ((1 − α) + α/N) N → ∞: speedup → 1 / (1 − α) α = 0.9 → speedup < 10, however many processors
  • "An army of ants versus a herd of elephants": if CPU A is r = TB/TA times faster than B, the best speedup with NB cheap CPUs is 1 / ((1−α)r + αr/NB); NB → ∞: 1/((1−α)r). If r ≥ 1/(1−α) the speedup never exceeds 1 (α = 90%, r = 10: one expensive CPU is better).
  • But reality disagrees: every Top500 supercomputer is built from thousands to millions of off-the-shelf cores. Where is the flaw?

Gustafson-Barsis's law

A parallel platform does more than speed up a sequential program: it can solve bigger problems. The question: how long would a sequential machine take to solve the problem the parallel machine solves?

Assumptions: the parallel application runs in a fixed time T on N CPUs; during a fraction α of the time all machines work, (1 − α) is sequential. With T fixed, increasing N increases the work done.

t_seq = (1 − α)T + N·α·T speedup = t_seq / T = (1 − α) + N·α efficiency = speedup / N = (1 − α)/N + α

It has its flaw too: it assumes zero communication cost. Even for "embarrassingly parallel" problems communication becomes decisive as N grows. In practice efficiency above 90% is a worthwhile achievement.

α = 0.9, N = 10. Amdahl: 1 / (0.1 + 0.09) = 1/0.19 ≈ 5.26. Gustafson: 0.1 + 9 = 9.1. The difference is whether the problem is fixed (Amdahl, strong scaling) or grows with N (Gustafson, weak scaling).

Latency and throughput

A work request arrives at t = 0. A latency-optimised processor (CPU) produces the first result quickly (low latency). A throughput-optimised processor (GPU) produces the first result later (high latency) but much more output per unit time (high throughput).

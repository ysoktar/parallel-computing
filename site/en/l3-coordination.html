Deadlock, atomics, monitors

The tools of 3.1 prevent races; this page covers what happens when you combine them: in what order memory becomes visible, how locks deadlock, and how threads wait for each other.

  • Define deadlock, livelock and starvation, and give the practical way to prevent deadlock.
  • Solve producer-consumer with semaphores and a mutex in the right order.
  • Explain atomic operations, CAS and the use of monitors/condition variables.

Memory consistency models

  • Design concerns: cache coherence (the same address) and the memory consistency model (the order in which operations on different addresses become visible).
  • Sequential consistency: events on shared objects should appear to happen one at a time and take effect in program order for each thread. In other words the operations of different threads may interleave, but the overall order must be one that could also arise if the same operations ran one after another in a single thread.
  • In high-level languages compiler optimisations can make the generated code very different from a sequential translation (instruction reordering), but the result preserves sequential consistency (from a single thread's point of view).

What can go wrong: deadlock, livelock, starvation

SituationDefinitionCPU usage
DeadlockTwo or more threads wait forever for each other's resources while holding their own (P1 holds R2, P2 holds R1; each wants the other). Nobody progresses.Low (sleeping)
LivelockThreads are not blocked but too busy responding to each other; no progress (two people in a narrow corridor dodging the same way).High (spent on the lock mechanism)
StarvationA thread able to continue is postponed indefinitely; priorities or unfair scheduling (P1 and P3 alternate, P2 never gets in). No deadlock.Normal

How to prevent deadlock? extra Four conditions are needed together: mutual exclusion, hold and wait, no preemption, circular wait. The most practical fix breaks the cycle: everyone takes the locks in the same order (R1, then R2). C++17: std::scoped_lock lk(m1, m2); takes several mutexes without deadlock.

The producer-consumer problem

Producers put items into a shared buffer (e.g. BUFFSIZE = 100), consumers take them. Two semaphores and a mutex: slotsAvail counts the free slots (initially BUFFSIZE), resAvail counts the filled slots (initially 0), and the mutex (l) protects the buffer indices.

// producer                          // consumer
slotsAvail.acquire();                resAvail.acquire();
l.acquire();                         l.acquire();
buffer[in] = item;                   item = buffer[out];
in = (in + 1) % BUFFSIZE;            out = (out + 1) % BUFFSIZE;
l.release();                         l.release();
resAvail.release();                  slotsAvail.release();

Without synchronisation: writing into a full buffer (old data lost), reading from an empty one, two threads using the same in/out index (the next slot to write/read). Termination: with a shared data item (e.g. the total number to produce) or by sending consumers a special "done" message (poison pill).

Atomic operations

  • std::atomic<T>: operations are indivisible; it also tells the compiler that the variable is shared between threads and its accesses must not be reordered. An atomic read has acquire semantics, an atomic write release semantics (default seq_cst; the meanings are below, in "Memory ordering of atomics").
  • Hardware support: CAS (compare-and-swap/exchange): compares a memory location with a value, stores the new value if they match, returns the value read in any case (x86: CMPXCHG). LL/SC (load-link / store-conditional): LL reads the value; SC writes only if nobody wrote the location in between (ARM, PowerPC).
  • Atomic operations can build locks, replace them or complement them (lock-free data structures; is_lock_free() asks whether the hardware supports a type without locks). Example: atomic<bool> as a lock (spin lock). Floating-point atomics in C++20.
  • On GPUs atomic operations can be very slow (the histogram example: many writes to the same bin).
std::atomic locked{false};
void lock()   { bool exp = false; while (!locked.compare_exchange_weak(exp, true)) exp = false; }
void unlock() { locked.store(false); }

Memory ordering of atomics

  • memory_order_relaxed: changes are not forcibly propagated to other cores; threads may see different value sequences. Do not use unless you are very sure.
  • memory_order_acquire / release (+ acq_rel, consume): changes propagate between pairs of threads; the writer uses release, the reader acquire. It makes a difference on processors with weak memory ordering (ARM, PowerPC).
  • memory_order_seq_cst (default): all threads see a variable's values in the same order.

Monitors and condition variables

  • Semaphores are flexible but hard to use correctly (the logic is spread over threads); atomics are even riskier. Monitor: an object designed to be accessed safely by multiple threads: its methods run under mutual exclusion (one thread inside at a time).
  • Condition variable: for waiting on a condition inside a monitor: wait() releases the lock and sleeps, notify_one()/notify_all() wakes. If the signalling thread continues, the woken thread must recheck the condition (a while loop).
  • C++11: std::mutex + std::unique_lock + std::condition_variable.
class Monitor {
    std::mutex m; std::condition_variable cv; int count = 0;
public:
    void put()  { std::unique_lock l(m); count++; cv.notify_one(); }
    void take() { std::unique_lock l(m);
                  cv.wait(l, [&]{ return count > 0; });   // releases the lock while waiting
                  count--; }
};

Asynchronous threads and thread management

  • std::async + std::future: run a function asynchronously and get its result later with get(). std::packaged_task: wraps a callable whose result is reached through a future (for task queues/thread pools).
  • Dynamic (a new thread per task) vs static thread management (a thread pool). Pool pros: no per-task start-up cost; the thread count can match the workload (more for I/O-bound, one per core for CPU-bound); thousands of tasks for good load balancing; fewer system resources. Cons: complexity, deadlock risk with dependencies between tasks.
  • Fibers / user-level threads (boost::fibers): scheduled by a library rather than the OS; tiny creation/switch overhead ("lightweight/green threads"), thousands easily, custom schedulers, portable. Con: if one makes a blocking system call, all block; no direct multi-core benefit.

The CPU ↔ GPU bridge: std::thread + join ≈ kernel launch + cudaDeviceSynchronize(); a barrier ≈ __syncthreads() (but within a block only); std::atomic ≈ atomicAdd; the histogram exercise shows the same race problem in both worlds.

Coalescing, transpose, unrolling

The 32 threads of a warp go to global memory at the same time. If their addresses are next to each other, the hardware serves them all with one large read; if they are scattered, it reads again and again for the same data. This is the most important performance topic of midterm 2.

  • Compute how many 32/128-byte segments an access pattern touches, and its efficiency.
  • Tell whether code is coalesced by looking at where threadIdx.x sits in the address.
  • Explain, index by index, why the naive transpose is slow and how a shared memory tile fixes it.
  • Say what loop unrolling gains and what it costs.

Global memory transactions

Lecture 6, slides 43–48:

  • For maximum performance global memory accesses must be coalesced (combined).
  • Global memory is accessed via 32, 64 or 128-byte transactions. Every access is fitted into these chunks: there is no such thing as "reading 11 bytes", you read 32 bytes.
  • A region of memory is aligned to N bytes if its first address is a multiple of N. Only 32/64/128 B segments aligned to their own size can be read or written. Read 33 bytes and you end up with two 32 B accesses.
  • When a warp executes an instruction that accesses global memory, it combines the threads' accesses into one or more transactions. What decides how many: (1) the size of the word each thread accesses, (2) the distribution of the addresses across the threads.
  • The more transactions needed, the more words the threads did not ask for are moved too, and instruction throughput drops accordingly. General rule: the more scattered the addresses, the lower the throughput.

Slide 47: why "throughput / 8"?

  • 32 threads read 4 bytes each from random addresses → a separate 32 B transaction (the minimum chunk) per thread → 32 × 32 B = 1024 B read.
  • 32 threads read 4 bytes each from consecutive addresses and the start is 128 B aligned → 32 × 4 = 128 B = a single 128 B transaction.
  • 1024 / 128 = 8 times more data → effective bandwidth / 8.

Basic alignment requirement

  • Global memory instructions read or write words of 1, 2, 4, 8 or 16 bytes per thread.
  • An access to data in global memory compiles to a single instruction if and only if (1) the size of the type is 1, 2, 4, 8 or 16 bytes and (2) the data is naturally aligned (its address is a multiple of its size). Otherwise it is split into several instructions that cannot fully coalesce.
  • Built-in types such as char, short, int, long, long long, float, double, float2, float4 satisfy this automatically. For structs the compiler is told with __align__(8) or __align__(16):
struct __align__(8)  Vec2 { float x; float y; };            // 8 bytes, 8-aligned → one 8 B load
struct __align__(16) Vec3 { float x; float y; float z; };   // 12 bytes of data, rounded up to 16 → one 16 B load
  • Addresses returned by cudaMalloc and the other allocation functions are aligned to at least 256 bytes.
  • The multiple-array trap (slides 52–53): if you replace several cudaMalloc calls by one large block partitioned into arrays, each array starts at an offset from the block's start. A float2 array following a float array is 4 B aligned but not guaranteed to be 8 B aligned. Reading 8/16-byte words misaligned gives wrong results (off by a few words).

The quick way to see coalescing in code: check whether threadIdx.x (or the col/x derived from it) sits on the right, without a multiplier in the address expression. A[row*width + col] ✓; A[col*width + row] ✗ (consecutive threads are width elements apart); A[2*col] half efficiency.

2D arrays and pitch

  • Common pattern: thread (tx, ty) accesses BaseAddress + width·ty + tx. For full coalescing both the thread block's width and the array's width must be multiples of the warp size (32).
  • An array whose width is not a multiple of 32 is accessed much more efficiently if it is allocated with its width rounded up to the next multiple of 32 and its rows padded. The functions that do this hardware-independently: cudaMallocPitch() (2D), cudaMalloc3D() (3D). They compute and return the right stride (pitch); this pitch must be used to access elements.
  • Copying: memory from cudaMallocPitch is copied with cudaMemcpy2D, from cudaMalloc3D with cudaMemcpy3D.
// Host
int width = 64, height = 64;
float* devPtr; size_t pitch;
cudaMallocPitch(&devPtr, &pitch, width * sizeof(float), height);
MyKernel<<<100, 512>>>(devPtr, pitch, width, height);

// Device: pitch is in BYTES → cast to char* first to find the start of the row
__global__ void MyKernel(float* devPtr, size_t pitch, int width, int height) {
    for (int r = 0; r < height; ++r) {
        float* row = (float*)((char*)devPtr + r * pitch);
        for (int c = 0; c < width; ++c) { float element = row[c]; }
    }
}

// Copying
cudaMemcpy2D(devPtr, devPitch,            // destination and its pitch (GPU)
             hostPtr, hostPitch,          // source and its pitch (CPU), usually Ncols*sizeof(float)
             Ncols * sizeof(float), Nrows,// BYTES per row, number of rows
             cudaMemcpyHostToDevice);

Pitch examples (256 B alignment): width 5, 50, 250 B → pitch 256; 500 B → 512; 700 B → 768.

Matrix transpose class

The instructor's example in class; the kernel series of NVIDIA's "An Efficient Matrix Transpose in CUDA C/C++". A transpose does no arithmetic at all, it only moves data: its performance depends entirely on the memory access pattern. That makes it the best example for showing coalescing.

Set-up: 32×32 tile, 32×8 threads

  • TILE_DIM = 32, BLOCK_ROWS = 8. Each block processes one 32×32 tile of the matrix but has 32×8 = 256 threads.
  • So each thread processes 4 elements of the tile (32/8): rows y, y+8, y+16, y+24. The loop runs over the second index (row), so consecutive threads of a warp still go to consecutive addresses. Benefit: the cost of the index calculation is shared by 4 elements.
  • Grid for an N×N matrix: dim3(N/32, N/32), block: dim3(TILE_DIM, BLOCK_ROWS) = dim3(32, 8).

1) Reference: copy

const int TILE_DIM = 32;
const int BLOCK_ROWS = 8;

__global__ void copy(float* odata, const float* idata)
{
    int x = blockIdx.x * TILE_DIM + threadIdx.x;
    int y = blockIdx.y * TILE_DIM + threadIdx.y;   // with TILE_DIM, not blockDim.y!
    int width = gridDim.x * TILE_DIM;
    for (int j = 0; j < TILE_DIM; j += BLOCK_ROWS)
        odata[(y + j) * width + x] = idata[(y + j) * width + x];
}
// dim3 grid(N / TILE_DIM, N / TILE_DIM), block(TILE_DIM, BLOCK_ROWS);

Both read and write are coalesced: one warp = 32 consecutive floats of a row = 128 B. However fast a transpose is, it cannot beat this kernel; it is the "ceiling" for measurements.

The same idea as the instructor's advice: first write a copy kernel that does no computation, check that the output equals the input (and its speed); then add the real operation. For the shared-memory version, too, first write copySharedMem (global → shared → global, same place) and verify the indices.

2) Naive transpose

__global__ void transposeNaive(float* odata, const float* idata)
{
    int x = blockIdx.x * TILE_DIM + threadIdx.x;
    int y = blockIdx.y * TILE_DIM + threadIdx.y;
    int width = gridDim.x * TILE_DIM;
    for (int j = 0; j < TILE_DIM; j += BLOCK_ROWS)
        odata[x * width + (y + j)] = idata[(y + j) * width + x];
}
  • Read idata[(y+j)*width + x]: x on the right, no multiplier → the warp reads one 128 B line ✓.
  • Write odata[x*width + (y+j)]: x multiplied by width → consecutive threads are width elements apart. In a 1024×1024 matrix the stride is 1024 floats = 4096 B → the warp's 32 writes hit 32 separate segments. Not coalesced.
  • The a[i*1024] example in the lab is exactly this write.

3) Coalesced transpose with shared memory

Idea: read the tile from global memory row by row (coalesced) into shared memory; do the swapping inside shared memory (scattered access is cheap there); then write a column of the tile as a row of the output (coalesced). The block also has to write to the transposed place.

__global__ void transposeCoalesced(float* odata, const float* idata)
{
    __shared__ float tile[TILE_DIM][TILE_DIM];

    int x = blockIdx.x * TILE_DIM + threadIdx.x;
    int y = blockIdx.y * TILE_DIM + threadIdx.y;
    int width = gridDim.x * TILE_DIM;

    for (int j = 0; j < TILE_DIM; j += BLOCK_ROWS)
        tile[threadIdx.y + j][threadIdx.x] = idata[(y + j) * width + x];   // coalesced read

    __syncthreads();   // threads will write DIFFERENT elements than they read: the tile must be full

    x = blockIdx.y * TILE_DIM + threadIdx.x;   // transposed block position: bx ↔ by
    y = blockIdx.x * TILE_DIM + threadIdx.y;

    for (int j = 0; j < TILE_DIM; j += BLOCK_ROWS)
        odata[(y + j) * width + x] = tile[threadIdx.x][threadIdx.y + j];   // coalesced write
}

Index trace (N = 1024, grid 32×32, block 32×8): blockIdx = (1, 2), threadIdx = (5, 3).

  • Load: x = 1·32 + 5 = 37, y = 2·32 + 3 = 67. For j = 0, 8, 16, 24 it reads rows 67, 75, 83, 91 / column 37 of idata into tile[3][5], tile[11][5], tile[19][5], tile[27][5]. This block loads the input tile rows 64–95, columns 32–63.
  • Store: x = 2·32 + 5 = 69, y = 1·32 + 3 = 35. It writes tile[5][3], tile[5][11], tile[5][19], tile[5][27] into rows 35, 43, 51, 59 / column 69 of odata. Check: tile[5][3] = input (row 64+5, column 32+3) = idata[69][35] → odata[35][69] ✓.
  • Consecutive threads of a warp (threadIdx.x = 0..31) go to consecutive global addresses both when reading and when writing; the scattered part (tile[threadIdx.x][…], reading a column) is in shared memory.

The __syncthreads() here is mandatory: the tile[threadIdx.x][threadIdx.y+j] a thread writes out was loaded by another thread (even another warp). In copySharedMem, which only copies, each thread writes what it loaded itself, so the barrier is technically unnecessary (the article includes it only for comparison); the measurements show the barrier is not the bottleneck.

4) The version without bank conflicts final

In a 32×32 tile all elements of a column fall into the same shared memory bank; reading a column (tile[threadIdx.x][…]) is a 32-way bank conflict. The fix is one line: __shared__ float tile[TILE_DIM][TILE_DIM + 1]; (each row shifts by one bank). Bank optimisation is not on this exam; knowing why it exists is enough.

Effective bandwidth = 2 × matrix size (one read + one write) / time. Conclusion: coalescing global memory is the most critical factor; the cost of shared memory and synchronisation is much smaller.

Loop unrolling class

Copying the loop body several times to reduce the number of iterations. Every iteration runs, besides the "real work", counter-increment, compare and branch instructions; on a GPU these take instruction slots too. Unrolling reduces this overhead and, by putting independent instructions side by side, increases instruction-level parallelism (ILP).

float sum = 0;
for (int k = 0; k < 16; ++k)
    sum += Mds[ty][k] * Nds[k][tx];
// 16 iterations × (multiply-add + k++ + k<16 + branch)

float sum = 0;
for (int k = 0; k < 16; k += 4) {
    sum += Mds[ty][k]     * Nds[k][tx];
    sum += Mds[ty][k + 1] * Nds[k + 1][tx];
    sum += Mds[ty][k + 2] * Nds[k + 2][tx];
    sum += Mds[ty][k + 3] * Nds[k + 3][tx];
}
// 4 iterations: loop control cut 4 times

#pragma unroll                 // fully unrolls if the trip count is known at compile time
for (int k = 0; k < TILE_WIDTH; ++k)      // TILE_WIDTH is a #define / const → constant
    sum += Mds[ty][k] * Nds[k][tx];

#pragma unroll 4               // unroll 4 times
for (int i = 0; i < n; ++i) a[i] *= s;

#pragma unroll 1               // do not unroll
for (int i = 0; i < n; ++i) a[i] += 1;
  • Gain: fewer loop-control instructions; when fully unrolled the indices become constants (Mds[ty][3]) and address arithmetic is done at compile time; independent loads can be issued back to back, hiding latency.
  • Cost: the code grows; more variables are live at the same time → register usage increases → if the per-thread register limit is exceeded, register spill (local memory) or fewer threads per SM (lower occupancy).
  • If the trip count is constant (the transpose's j loop: TILE_DIM/BLOCK_ROWS = 4 iterations; tiled matmul's k loop: TILE_WIDTH iterations) the compiler usually unrolls it anyway. If the trip count is only known at run time (width/TILE_WIDTH) it cannot be fully unrolled.
  • Connection: the "local memory" slide in L6. Arrays indexed with non-constant indices are placed in local memory instead of registers; since unrolling makes the indices constant, it can allow keeping the array in registers.

Check yourself

A warp reads a[3*threadIdx.x] from a 128 B-aligned float array. How many 32 B segments are touched?

  1. 4
  2. 12
  3. 32
  4. 3
Moved 12·32 = 384 B, used 128 B → efficiency 1/3.

Why are the transpose kernels' blocks 32×8 threads rather than 32×32?

  1. A 32×32 block cannot be launched.
  2. To avoid bank conflicts.
  3. So that each thread processes 4 elements of the tile and the index calculation cost is shared.
  4. To save shared memory.

Why does transposeCoalesced use x = blockIdx.y*TILE_DIM + threadIdx.x in the store phase?

  1. Tile (bx, by) of the input must be written to the transposed position (by, bx) of the output.
  2. To reduce bank conflicts.
  3. To make the read coalesced.
  4. A typo; it should be blockIdx.x.

Which is true about #pragma unroll?

  1. It distributes the loop iterations over different threads.
  2. It reduces register usage.
  3. It may change the result, be careful.
  4. It can fully unroll a loop whose trip count is constant at compile time.

GPUs and CUDA

  • GPU: designed for visual tasks (2D/3D graphics, games, CAD, effects); pushed by the consumer market to very high FP throughput and memory bandwidth. Programmable since around 2001.
  • CUDA (Compute Unified Device Architecture): the hardware + software that make GPUs programmable; C, C++ and Fortran flavours. CUDA C/C++ extends C with a small group of keywords. GPGPU: general-purpose computing on GPUs (CUDA / OpenCL).
  • Before CUDA: data was wrapped into OpenGL structures to fake graphics operations, since most graphics operations are FP matrix/vector operations.
  • GPU cores are called Streaming Multiprocessors (SMs): a combination of scalar processors (SPs), local cache and special function units. An SM executes thread blocks, an SP one thread of a block.

The reason for the difference

CPU: very complicated control logic + large multilevel caches. Ideal for random-access, independent-task parallel execution; latency-oriented.

GPU: data-level parallelism. Simple control logic, small caches → more transistors for computation. Faster, more optimised memory types. Suited to SIMD/SIMT execution; throughput-oriented.

Architecture examples: discrete GPU (over PCIe), memory controller integrated in the CPU (AMD Athlon 64, Intel Nehalem), and CPU+GPU on one chip (AMD APU; with hUMA, a unified memory space and cache coherence).

SIMD and SIMT

  • SIMD (Single Instruction Multiple Data): the same instruction is applied to many data elements in parallel (vector processors).
  • SIMT (Single Instruction Multiple Thread): the same instruction is executed by many threads in parallel. A more flexible version of SIMD. CUDA is SIMT: you can give threads different tasks, but as thread divergence increases, performance drops.
  • Since the same instruction is applied to everyone, flow control stays simple. With high arithmetic intensity (instructions / memory access), memory latency is hidden with computation instead of big caches.
  • Data-parallel programming: data elements → parallel threads. 3D rendering, image/video processing, encoding, stereo vision, object recognition, physics simulation, finance, biology…

Why multi-core?

  • Moore's law: the number of transistors on an integrated circuit doubles every ~2 years (the rate is slowing).
  • Raising the frequency is no longer possible: power scales with the cube of frequency (P ∝ f³), high clocks are hard to generate and distribute; heat and waveform degradation.
  • Multi-core: more power-efficient at lower frequencies; performance by running several operations at once. The catch: performance needs parallelised software.
  • Some tasks are inherently serial; the CPU suits them better. No single processor is best for everything → heterogeneous multi-core platforms (where OpenCL comes in). Power limits in mobile/embedded systems also force multi-core.

The general CUDA approach

  1. Analyse the code, find the bottlenecks (profiling): parts that take most of the time and are compute-heavy and/or bandwidth-hungry (not disk, user input, network waits).
  2. Find the data-parallel parts (some algorithms are serial: Newton's method, most compression algorithms).
  3. Copy the required inputs from CPU memory to GPU memory (PCIe; exception: zero-copy, unified DRAM).
  4. Compute on the GPU: find a good thread → data mapping, write the kernels.
  5. Copy the results back to the CPU.
  6. Check that GPU results match CPU results (within tolerance). Careful: FP operations are commutative but not associative: (a + b) + c ≠ a + (b + c) is possible.
  7. Iterate: how close are we to the theoretical peak GFLOPS and GB/s? If not, optimise.

Where to expect good gains: code applying the same operation to all data points; mostly float code (double is supported but slow, especially on old architectures); code where the data to move is small compared to the computation per element.

Thread hierarchy

  • threadIdx is a 3-component vector (.x .y .z): the thread's coordinates in a 3D thread cube. Arranged as 1D (vector), 2D (matrix), 3D (volume). Rule of thumb: thread dimensionality → data dimensionality.
  • A fixed-size group of threads = a thread block; its dimensions are decided before launch and read in the kernel via blockDim. On current GPUs a block has at most 1024 threads.
  • Threads are created/executed in warps; thread → warp assignment is not arbitrary, the thread index decides it:
1D: index = threadIdx.x 2D: index = threadIdx.y * blockDim.x + threadIdx.x 3D: index = threadIdx.z * blockDim.x * blockDim.y + threadIdx.y * blockDim.x + threadIdx.x warp = index / 32

dim3 block(16, 8, 2): 256 threads, 8 warps. threadIdx = (5, 3, 1) → index = 1·16·8 + 3·16 + 5 = 128 + 48 + 5 = 181 → warp 181/32 = 5.

__global__ void VecAdd(float* A, float* B, float* C) {   // <<<1, N>>>: 1 block, N threads
    int i = threadIdx.x;
    C[i] = A[i] + B[i];
}
__global__ void MatAdd(float* A, float* B, float* C) {   // <<<1, dim3(N, N)>>>
    const int i = threadIdx.y * blockDim.x + threadIdx.x;
    C[i] = A[i] + B[i];
}

The slides' blockDimx.x is a typo for blockDim.x.

Blocks and scalability

  • Thread blocks must execute independently: it must be possible to run them in any order, in parallel or in series. You cannot control which block runs on which SM. This lets the program scale with the number of SMs.
  • The CUDA approach: first partition the problem into coarse sub-problems solved independently in blocks (no interaction between blocks); then partition each sub-problem into finer pieces solved cooperatively by the block's threads (local interactions within the block).
  • Threads in a block share data through shared memory and synchronise with __syncthreads() (a barrier: nobody proceeds until all arrive; lightweight).
  • Design: (1) design blocks so that all local interactions of the algorithm happen within a block, (2) design the thread mapping to process each data element within the block, (3) remember that blocks run independently on SMs in no deterministic order.

Thread block clusters (compute 9.0)

  • An optional new level: thread → block → cluster. Just as a block's threads are guaranteed to be co-scheduled on one SM, a cluster's blocks are co-scheduled on one GPC (GPU Processing Cluster). (Ampere: 2 SMs = 1 TPC, 8 TPCs = 1 GPC, 8 GPCs = the full GPU.)
  • Largest portable cluster: 8 blocks. At compile time with __cluster_dims__(X,Y,Z) or at run time with cudaLaunchKernelEx. The grid dimension must be a multiple of the cluster size.
  • Blocks in a cluster can synchronise in hardware with cluster.sync() and access distributed shared memory.

Memory hierarchy

  • Each thread has private local memory.
  • Each block has shared memory visible to all its threads, with the block's lifetime.
  • All threads access the same global memory.
  • Two additional read-only memories: constant and texture. Global, constant and texture persist across kernel launches.

Details: L5 memory types, L6.

Compute capability

Major.minor. The same major = the same core architecture (1 Tesla, 2 Fermi, 3 Kepler, 5 Maxwell, 6 Pascal, 7 Volta/Turing, 8 Ampere/Lovelace, 9 Hopper…); minor = incremental improvement, new features. Newer architecture, better CUDA capabilities.

What lets CUDA programs run unchanged on GPUs with different numbers of SMs?

  1. The warp size being 32 on every GPU.
  2. Thread blocks being independent and runnable in any order.
  3. __syncthreads() synchronising all blocks.
  4. The programmer assigning blocks to SMs by hand.

GPU results do not match CPU results bit for bit. The most likely reason?

  1. The GPU does not support floats.
  2. FP addition is not commutative.
  3. __syncthreads() is always missing.
  4. FP operations are not associative; parallel code performs operations in a different order.

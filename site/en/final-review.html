Lecture 1 · Introduction and performance

Source page: l1-review.html

Key ideas

  • Moore's law is about the number of transistors, not frequency. Frequency stopped at 2–4 GHz around 2005 because of power and heat (power ∝ f³); the extra transistors went into cores.
  • Getting performance from many cores needs parallel software; that is what this course is about.
  • Flynn: SISD, SIMD, MISD, MIMD. Multi-core CPUs and GPUs are MIMD; the GPU's programming model is SIMT.
  • Shared memory (common address space, easy, limited scale; NUMA) ↔ distributed memory (message passing, harder, scales far).
  • CPUs are designed for latency (big caches, complex control), GPUs for throughput (many simple ALUs, wide memory buses).
  • speedup = tseq/tpar, efficiency = speedup/N. Amdahl: 1/((1−α) + α/N), ceiling 1/(1−α). Gustafson: (1−α) + αN.

Common mistakes

  • Taking α to be the serial part. In this course α is the parallelisable part; the serial part is 1 − α.
  • Mixing up speedup and efficiency: a speedup of 8 on 16 cores is 50% efficiency; there is no such thing as "8 times efficiency".
  • Thinking NUMA is distributed memory: in NUMA addressing is shared, remote memory is just slower.
  • Comparing against a slow sequential version: the golden rule compares with the fastest known sequential solution.

Open-ended questions for the final

1. 95% of a program can be parallelised. What are the speedup and efficiency on 19 cores? What is the most you can get with infinitely many cores?

1/(0.05 + 0.95/19) = 1/(0.05 + 0.05) = 10; efficiency 10/19 ≈ 53%. Bound: 1/0.05 = 20.

2. For the same program, what are the speedup and efficiency on 19 cores according to Gustafson? Why is it different from Amdahl?

0.05 + 19·0.95 = 0.05 + 18.05 = 18.1; efficiency 0.05/19 + 0.95 ≈ 95.3%. Gustafson assumes the problem grows with the number of cores (fixed time); Amdahl keeps the problem fixed.

3. Why was it not possible to keep raising the clock frequency? Give two reasons.

(1) Power grows very fast with frequency (about f³): the heat cannot be removed. (2) A high-frequency clock signal is hard to generate and distribute across the chip (the waveform degrades). Lowering the voltage helped for a while but was not enough.

4. 10,000 nodes in a server farm will work together. Shared or distributed memory? Why?

Distributed memory: shared memory becomes a bottleneck in a single common medium (memory bus, cache coherence) and chokes at tens to hundreds of cores. In distributed memory each node has its own memory and communicates by messages; that is expensive, but with no shared bottleneck it scales very far.

Lecture 2 · Parallel program design

Source page: l2-review.html

Key ideas

  • PCAM: Partition (as many pieces as possible, 10–100 times the number of processors), Communication (dependency graph), Agglomeration (group to reduce communication, ~10 times), Mapping (load balance + communication; NP-complete in general).
  • Decomposition: functional (by steps), data (by data), data flow (pipeline, event).
  • The slowest stage sets a pipeline's speed; there is a benefit only if the stages run concurrently.
  • In divide-and-conquer, parallelism is read from the dependency graph, not the call graph.
  • GPLS (SPMD, MPMD, master-worker, map-reduce) ↔ GSLP (fork/join, loop parallelism). CUDA = SPMD.

Common mistakes

  • Thinking task parallelism scales: the number of tasks is fixed, so it cannot follow the number of cores.
  • Confusing a pipeline's total latency with its throughput: in a 2+5+3 ms pipeline one item takes 10 ms, but in steady state there is one output every 5 ms.
  • Forgetting agglomeration: N² tiny tasks are very parallel in theory, slow in practice because of communication and task management costs.

Open-ended questions for the final

1. Design a histogram computation (Exercise 1) with the PCAM steps. In which step does a race appear, and how do you solve it?

  • P: each pixel a task (data decomposition).
  • C: each task updates one of 256 bins; everyone writes to the same small array → heavy communication and a race.
  • A: group pixels into chunks per thread; each thread first keeps its own local histogram, summed at the end.
  • M: equal-size chunks.

If the shared histogram is written directly, an atomic or a mutex is needed (L3); on a GPU, a per-block shared-memory histogram + atomicAdd.

2. A 4-stage pipeline has stage times 4, 4, 8, 4 ms. How long do 100 items take? How do you remove the bottleneck?

The first output at 20 ms (fill), then one every 8 ms: about 20 + 99·8 = 812 ms. The bottleneck is the 8 ms stage: split it in two (4+4) or run two copies of that stage in parallel; then there is an output every 4 ms (≈ 20 + 99·4 = 416 ms).

3. Explain the difference between SPMD and master-worker with one example each.

SPMD: everyone runs the same program and processes different data according to their unique ID (a CUDA kernel, MPI). Master-worker: the roles differ: the master hands out work and collects results, the workers do the work; since idle workers get new work, load balancing happens by itself (e.g. distributing frames in a render farm).

Lecture 3 · Threads and synchronisation

Source page: l3-review.html

Key ideas

  • Threads share the process's address space: communication is cheap, but access to shared data must be synchronised.
  • Data race: concurrent access with at least one writer (undefined behaviour in C++). Race condition: a wrong result because of ordering.
  • Read-modify-write must be indivisible: a mutex or an atomic.
  • Mutex = one thread + ownership; semaphore = N threads, a counter; condition variable = wait for a condition while releasing the lock.
  • Deadlock (nobody progresses, CPU idle), livelock (nobody progresses, CPU busy), starvation (one thread never gets a turn).
  • Producer-consumer: slotsAvail (free slots) and resAvail (full slots) semaphores + a mutex protecting the indices.
  • CAS (x86 CMPXCHG) and LL/SC: the hardware basis of atomics and lock-free structures.

Common mistakes

  • Locking only the writer and not the reader: a read races with a write too.
  • Waiting on a condition variable with if: after waking, the condition must be checked again (while or wait(lock, predicate)).
  • Swapping the semaphore and mutex order in producer-consumer: taking the mutex first and then waiting on the semaphore for a full buffer deadlocks (the mutex holder sleeps, the consumer cannot get the mutex).
  • Writing lock-free code because "8 bytes are atomic on x86": compilers and types make relying on it wrong.

Open-ended questions for the final

1. 4 threads each do an unprotected counter++ 1000 times. What can the final value be at most? Why does it come out below 4000?

At most 4000 (if there is never an overlap). In practice less, because the read-add-write steps interleave and updates are lost (the step-by-step counter++ table in 3.1). The theoretical lower bound is very small (a bad interleaving can bring it down to 2); in the exam what matters is explaining why: updates are lost and the result is nondeterministic.

2. In producer-consumer the consumer is written in this order: l.acquire(); resAvail.acquire(); …. What happens?

With an empty buffer the consumer takes the mutex, then sleeps on resAvail while holding the mutex. The producer cannot take the mutex to add an item → nobody can progress: deadlock. The right order is semaphore first, then mutex.

3. A web server can open at most 8 database connections at once. Which synchronisation tool do you use? Write the skeleton of the code.

A counting semaphore with initial value 8: each request takes a connection with sem.acquire(); and calls sem.release(); when done. The 9th request waits until a connection is freed.

4. Compare deadlock and livelock in terms of CPU usage and give a real-life example of each.

Deadlock: threads sleep waiting for each other's resources, CPU usage is low (two cars facing each other on a narrow bridge, neither backs off). Livelock: threads are not blocked but busy responding to each other, CPU usage is high but there is no progress (two people in a corridor dodging the same way).

Check yourself

  2. No, there is no data race unless at least one thread writes.
  3. Only if the variable is misaligned.
  4. Only if it is not atomic.

  1. Deadlock
  2. Starvation
  3. Livelock
  4. Race condition

The key difference between a mutex and a semaphore?

  1. A semaphore can admit N threads at once; a mutex one.
  2. A semaphore works only within one process.
  3. A mutex needs no atomic operations.
  4. A mutex can be released by another thread.

Lecture 4 · GPUs and CUDA

Source page: l4-review.html

Key ideas

  • On a GPU the silicon goes to arithmetic units instead of control and caches; GPUs are throughput-oriented, CPUs latency-oriented.
  • CUDA = SIMT: same instruction, many threads. Divergence (different paths within a warp) slows down.
  • The host prepares the work (allocate, copy, launch), the device executes. Flow: profile → find the parallel part → copy → compute → copy back → verify (FP is not associative) → iterate.
  • Hierarchy: grid → block (≤ 1024 threads, on one SM) → warp (32 consecutive threads) → thread. Linear index: tz·bx·by + ty·bx + tx, warp = index/32.
  • Blocks are independent and unordered → scalability. Cooperation within a block: shared memory + __syncthreads().
  • Memory: local per thread, shared per block, global for everyone; read-only constant and texture.

Common mistakes

  • Mixing up blockDim (threads per block) and gridDim (blocks per grid).
  • Thinking a warp can span two blocks: warps are always inside one block; a 48-thread block = 2 warps (the second half full).
  • Assuming block 0 runs before block 1.
  • Expecting CPU and GPU results to match bit for bit (different summation order).

Open-ended questions for the final

1. A kernel uses 100-thread blocks. How many warps per block, and how many thread slots are wasted?

⌈100/32⌉ = 4 warps; 4·32 = 128 slots, 28 empty (only 4 threads active in the last warp). Choosing block sizes that are multiples of 32 avoids this waste.

2. if (threadIdx.x < 48) A(); else B(); in a 128-thread block: how many warps diverge?

Warp 0 (0–31): all A, no divergence. Warp 1 (32–63): 32–47 A, 48–63 B → diverges. Warps 2, 3: all B. So only 1 warp.

3. Why must blocks be independent? What would we lose if they were not?

So that the runtime can distribute blocks to any SM in any order. If blocks waited for each other (order assumptions, synchronisation across blocks), the same program might not run, or might deadlock, on GPUs with different numbers of SMs: scalability would be lost.

Check yourself

In a dim3 block(32, 4, 2) block, which warp is the thread with threadIdx = (0, 2, 1) in?

  1. 2
  2. 1
  3. 6
  4. 8

What lets CUDA programs run unchanged on GPUs with different numbers of SMs?

  1. The warp size being 32 on every GPU.
  2. Thread blocks being independent and runnable in any order.
  3. __syncthreads() synchronising all blocks.
  4. The programmer assigning blocks to SMs by hand.

GPU results do not match CPU results bit for bit. The most likely reason?

  1. The GPU does not support floats.
  2. FP addition is not commutative.
  3. __syncthreads() is always missing.
  4. FP operations are not associative; parallel code performs operations in a different order.

Lecture 5 · Kernels, indexing, tiling

Source page: l5-review.html

Key ideas

  • Kernel = the body of the loop; the outer loops become threads. Host: cudaMalloc → cudaMemcpy (H→D) → kernel<<<grid, block>>> → cudaMemcpy (D→H) → cudaFree.
  • Global index = blockIdx·blockDim + threadIdx (on each axis); row-major address row·width + col; round the grid up, check the bounds.
  • __syncthreads(): barrier within a block, everyone in the block must execute it.
  • Blocks are assigned to SMs block by block; warp = 32 threads, the scheduling unit; many warps = latency hiding.
  • Naive matmul has CGMA = 1 → bandwidth-bound (~6% efficiency). Tiling: load a tile into shared memory once, use it T times → T times less global traffic, CGMA = T.
  • Two barriers in the tiled kernel: after loading (tile filled) and after computing (not overwritten).

Common mistakes

  • Passing a number of elements to cudaMalloc/cudaMemcpy: sizes are always in bytes (n * sizeof(float)).
  • Using x for the row and y for the column: consecutive threads go to distant elements (coalescing breaks) and the matrix is computed transposed.
  • Forgetting the second __syncthreads() in the tiled kernel: a fast thread writes the next phase's tile while others are reading.
  • Timing right after the kernel: the launch is asynchronous, call cudaDeviceSynchronize() first.

Open-ended questions for the final

1. Write a kernel that multiplies an n-element array by s, and the host code that launches it (256 threads per block, n may not be a multiple of 256).

__global__ void scale(float* a, float s, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) a[i] *= s;              // the extra threads do nothing
}
// host:
float* d;
cudaMalloc((void**)&d, n * sizeof(float));
cudaMemcpy(d, h, n * sizeof(float), cudaMemcpyHostToDevice);
scale<<<(n + 255) / 256, 256>>>(d, 2.0f, n);
cudaMemcpy(h, d, n * sizeof(float), cudaMemcpyDeviceToHost);
cudaFree(d);

2. What is the CGMA ratio of tiled matmul with TILE_WIDTH = T? Show it.

In each phase a thread does 2 global reads (one element each into Mds and Nds) and, in the inner loop, T multiplications + T additions = 2T FP operations. CGMA = 2T / 2 = T. With T = 16, a 16 times improvement: on the G80 the 21.6 GFLOPS bound rises to ~345 GFLOPS (close to the 367 peak).

3. Compute the shared memory use of 16×16 tiled matmul and how many blocks fit on a G80 SM. What is the limit?

Mds + Nds = 2·16·16·4 B = 2 KB/block; 16 KB/SM → 8 blocks by shared memory. But with 256 threads/block, 768/256 = 3 blocks. The limit: threads per SM (not shared memory).

Lecture 6 · Compilation and memory types

Source page: l6-review.html

Key ideas

  • nvcc: .cu → PTX (virtual ISA) → ptxas → SASS (cubin). A cubin for X.y runs only on X.z (z ≥ y); future GPUs need PTX + JIT. -arch selects the PTX, -code the binary.
  • Kernel launches are asynchronous: call cudaDeviceSynchronize() when timing; the first call includes initialisation.
  • Register and shared memory limits decide the threads/blocks per SM; too many registers → spill → local memory (as slow as global).
  • Global: coalescing (aligned 32/64/128 B segments), pitch in 2D. Local: variable-indexed arrays and spills.
  • Shared: 32 banks, bank = word index % 32; different words in the same bank = conflict; for s[stride·threadIdx.x] the degree is gcd(stride, 32); [32][33] padding for column reads.
  • Constant: best when everyone reads the same address (broadcast). Texture: 2D locality, interpolation, boundary handling; read-only, needs a CUDA array.

Common mistakes

  • Mixing up coalescing and bank conflicts: coalescing is about consecutive addresses in global memory; bank conflicts are about different words falling into the same bank of shared memory. s[2*threadIdx.x] means half efficiency in global memory and a 2-way conflict in shared memory.
  • Taking the pitch for a number of elements: the pitch is in bytes, the row start is (char*)p + r*pitch.
  • Having consecutive threads read consecutive addresses of constant memory: that is the bad pattern for constant memory (32 separate requests).
  • Thinking a binary built with -code=sm_70 runs on an 8.x GPU (not across a major change, and with no PTX there is no JIT).

Open-ended questions for the final

1. 32 threads read s[8*threadIdx.x + 1] from __shared__ float s[1024]. How many ways is the bank conflict?

Bank = (8i + 1) % 32: 1, 9, 17, 25, 1, 9, … → only 4 banks are used, with 8 different words each → 8-way (gcd(8, 32) = 8; the offset does not change the degree).

2. Why is tile[32][33] used instead of __shared__ float tile[32][32] in the transpose? Show it with the bank calculation.

With width 32 the bank of tile[r][c] is (32r + c) % 32 = c: the 32 elements of a column are in the same bank, so a warp reading a column makes a 32-way conflict. With width 33 the bank is (33r + c) % 32 = (r + c) % 32: 32 different banks for r = 0..31 → no conflict. The cost is 32 floats.

3. A kernel uses 40 registers per thread and an SM has 65,536 registers. With 256 threads per block, how many blocks fit on an SM at most (by registers)?

256·40 = 10,240 registers per block; 65,536 / 10,240 = 6.4 → 6 blocks (1536 threads). Bringing it down to 32 registers allows 8 blocks (2048 threads): register usage directly decides occupancy.

4. When do you choose constant memory and when texture memory? One example each.

Constant: when all threads read the same small data at the same time, e.g. the coefficients of a convolution filter (every thread reads the same coefficient at the same moment → broadcast). Texture: reads that are local in 2D but irregular, and fractional coordinates, e.g. image rotation (texRotate.cu): neighbouring pixels come from the cache, bilinear interpolation and edge handling are done in hardware.

Lecture 6 · Coalescing, transpose, unrolling

Source page: coalescing-review.html

Key ideas

  • A warp's accesses are gathered into 32/64/128-byte segments aligned to their size; the fewer the segments, the better.
  • Check: is threadIdx.x without a multiplier and rightmost in the address? A[row*W + col] ✓, A[col*W + row] ✗.
  • For 2D arrays, cudaMallocPitch so that row starts are aligned; the pitch is in bytes.
  • Transpose: in the naive version the write is ✗; with a shared memory tile read and write are ✓; [32][33] padding removes bank conflicts.
  • Loop unrolling: reduces loop control, increases ILP; the price is registers.

Open-ended questions for the final

1. A warp reads a[threadIdx.x * 2 + 1] from a float array (128 B aligned). How many 32 B segments are moved, and what is the efficiency?

Addresses 4, 12, 20, …, 252 (bytes): all 8 segments of the range 0–255 are touched → 8 · 32 = 256 B moved, 128 B used: 50%.

2. In the shared-memory transpose, why are both the global read and the global write coalesced? Which access stays scattered, and why is that not a problem?

In both the read and the write, threadIdx.x is rightmost in the global address (consecutive along a row). The swapping is done inside shared memory: tile[threadIdx.x][…] reads a column, so the scattered access is in shared memory. Shared memory is on-chip and fast, so this is cheap; its only cost is bank conflicts, which [32][33] padding removes.

  1. It distributes the loop iterations over different threads.
  2. It reduces register usage.
  3. It may change the result, be careful.
  4. It can fully unroll a loop whose trip count is constant at compile time.

Lecture 7 · Error checking and control flow

Source page: l7-review.html

Key ideas

  • Runtime calls return cudaError_t; a kernel launch does not. Asynchronous errors appear at a later call (or at cudaDeviceSynchronize()).
  • cudaPeekAtLastError() reads, cudaGetLastError() reads and resets. Pattern: clear first, launch, cudaGetLastError(), cudaDeviceSynchronize().
  • Divergence: different paths within a warp run one after the other (one program counter). Aligning the condition with threadIdx / 32 avoids divergence.
  • Predication (GPU): instructions are not skipped, they are masked with a per-thread predicate. Prediction (CPU): guessing the branch + speculative execution.
  • #pragma unroll N unrolls N times (code is added for leftover iterations); 1 does not unroll; without a number: fully unrolls a constant trip count.
  • Make loop counters int: since signed overflow is undefined, the compiler optimises more.

Common mistakes

  • Thinking "the launch returned no error, so it ran": a launch never returns an error; execution errors come later.
  • Calling cudaGetLastError() twice and expecting the error the second time too: the first call resets it.
  • Mixing up predication and prediction, or counting different warps taking different branches as divergence.
  • Writing #pragma unroll a few lines before the loop: it must be immediately before it.

Open-ended questions for the final

1. Complete the unchecked call k<<<g, b>>>(…);. What is the difference between Peek and Get?

First clear/check earlier errors (cudaGetLastError()), launch, cudaError_t launch = cudaGetLastError(); (configuration/parameter errors), then cudaError_t run = cudaDeviceSynchronize(); (execution errors); if either is not cudaSuccess, report and stop. Get reads and resets, Peek does not reset.

2. In a 128-thread 1D block, how many warps diverge for if (threadIdx.x < 40) and for if (threadIdx.x % 4 == 0)?

< 40: warp 0 all true, warp 1 (32–63) mixed, warps 2–3 all false → 1. % 4 == 0: 8 true, 24 false in every warp → 4 (all).

3. How is predication different from prediction? Why is #pragma unroll 4 not always faster?

Prediction (CPU) guesses the branch and executes speculatively, rolling back if wrong. Predication (GPU) does not skip instructions; it masks them with a per-thread predicate, and false ones neither write results nor read operands. Unrolling reduces loop control but increases code size and register usage; register spills or lower occupancy can erase the gain.

4. A program reports "illegal memory access" at a cudaMemcpy call, but the cudaMemcpy parameters are correct. Why?

The error most likely happened in the previous kernel (asynchronously). A kernel launch returns no error; the error was reported at the next unrelated call, here the cudaMemcpy. Checking the return value of cudaDeviceSynchronize() right after the kernel shows the error in the right place.

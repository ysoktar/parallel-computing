Lecture 1 · Why parallel, how much faster

Moore's law, the power wall, multi-core

  • Moore's law: the number of transistors on a chip doubles every ~2 years. It is not about frequency; "Moore's law says the frequency doubles" is false in an exam.
  • Power wall: dynamic power ≈ C·V²·f, and a higher f needs a higher V ⇒ power ≈ f³. The voltage was lowered (down to ~1.29 V) but not enough; around 2004–2005 frequency stopped at 2–4 GHz. Distributing a high-frequency clock across the chip without distortion also got harder.
  • Result: the extra transistors went into more cores (the first dual-core single chip: IBM Power 4, 2001). Performance no longer comes for free: parallel software is required.
  • Frequency alone is not a metric: operations take different numbers of clock cycles (on x86-64, int add 1, FP multiply ~4 cycles).
  • GPGPU: one GPU core is weak, but thousands of cores + high bandwidth; more work per watt (in servers electricity can cost more than the processor).

Flynn's taxonomy and memory architectures

  • Shared-memory MIMD: one address space; communication through shared variables (cheap), limited scale (memory bus, cache coherence). NUMA: memory split among CPUs, local fast and remote slow, but addressing shared (still shared memory!). SMP: all CPUs equivalent.
  • Distributed memory (shared-nothing): every node has private memory; message passing (MPI); communication is expensive but there is no shared bottleneck ⇒ scales to thousands–millions of cores; harder to program (data distributed explicitly).
  • CPU ↔ GPU: a CPU has big caches + complex control (branch prediction, out-of-order execution) for latency; a GPU has small caches + many simple ALUs + a wide memory path for throughput.

Measurement: speedup, efficiency, golden rules

S = T_seq / T_par E = S / N linear speedup: S = N (E = 100%)
  • Golden rule 1: serial and parallel are measured on the same hardware, compiler, flags and conditions. Golden rule 2: Tseq is the fastest known serial solution (not the parallel code run with 1 thread).
  • Speedup depends on the input: report the average/min/max over many inputs.
  • On a GPU two speedups are reported separately: kernel-only (kernel time only) and end-to-end (H2D + kernel + D2H). Example: CPU 80 ms, H2D 6, kernel 4, D2H 10 ⇒ kernel-only 20×, end-to-end 80/20 = 4×.
  • Superlinear speedup (S > N) is possible: each core's data starts to fit in cache, or the serial side was badly chosen.

Amdahl, Gustafson, ants vs elephants

Amdahl (fixed problem): S(N) = 1 / ((1−α) + α/N) S(∞) = 1/(1−α) Gustafson (fixed time): S(N) = (1−α) + α·N Ants vs elephants: S = 1 / ((1−α)·r + α·r/N) (r = speed ratio of the expensive CPU)
  • α = the parallelisable fraction (serial part 1−α). The most common mistake is mixing them up.
  • Amdahl's intuition: more cores only shrink the parallel part; the serial part becomes a floor. α = 0.9: N = 10 ⇒ 5.26; N = 100 ⇒ 9.17; N = ∞ ⇒ 10. Efficiency drops fast.
  • Gustafson's intuition: in real life we grow the problem with the cores (finer grid); the parallel part grows with N, the serial part stays ⇒ S ≈ N. This explains why supercomputers are thousands of cheap cores.
  • Both share a flaw: communication cost is taken as zero. In practice efficiency above 90% is a good achievement.
  • Ants vs elephants: if r ≥ 1/(1−α), no number of cheap CPUs beats the single expensive one (for a fixed problem).
  • Latency ↔ throughput: for work arriving at t = 0, the CPU gives the first result early; the GPU later, but many more results per unit time.

Lecture 2 · Parallel program design

Ask first, then PCAM

  • Ask first: is parallelism really needed (is serial fast enough)? Does the algorithm allow it (some are inherently serial: Newton's method, most compression)? Is there time/engineering effort? On a GPU the algorithm is usually redesigned.
  • Goals: correctness (in a parallel program the order of statements can change from run to run) and performance.
StepWhat you doPractical rule
Partitioningsplit the work into tasks as small as possible: functional (by steps) or data (by data) decomposition10–100 times as many tasks as processors
Communicationidentify dependencies and data volume → dependency graph (node = task, edge = communication)ideally independent tasks
Agglomerationgroup tasks to cut communication (communication inside a group is free); sometimes recomputing is cheaper than sending~10 times as many groups as processors
Mappingassign groups to processors: load balance + heavily communicating groups on one nodeNP-complete in general → heuristics

Example, 2D convolution: P: a task per output pixel; C: the inputs of 8 neighbours; A: group pixels into tiles, only the edge rows (halo) come from outside; M: equal tiles. On a GPU tile = block and the halo is loaded into shared memory.

Program structure patterns

  • GPLS (globally parallel, locally sequential): many tasks at once, each serial inside. SPMD: everyone runs the same program on different data by ID (a CUDA kernel, MPI). MPMD: different programs (heterogeneous platforms). Master-worker: the master hands out and collects, workers work; implicit load balancing because idle workers get work; a single master can be a bottleneck. Map-reduce: map over independent data, reduce the partial results.
  • GSLP (globally sequential, locally parallel): the program is serial, chosen parts are parallel. Fork/join: tasks are created dynamically and finish before the parent continues. Loop parallelism: parallelise the time-consuming loops of existing code (OpenMP); little effort, usually little gain.
  • The platform imposes the pattern: MPI → SPMD/MPMD, OpenMP → loop parallelism, CUDA → SPMD.

Lecture 3 · Threads and synchronisation

Processes, threads, races

  • Process: its own address space, open files, PID (fork is expensive). Thread: a separate flow of execution inside a process; program counter, stack, registers are per thread; the address space (heap, globals) is shared. Cheap to create and switch.
  • Threads are for: performance, background work, asynchronous (non-blocking) processing, program structure. std::thread since C++11 (pThreads before).
  • Data race: concurrent access to one location, at least one write, no synchronisation ⇒ undefined behaviour in C/C++. Only reads are no problem.
  • Race condition: a wrong result because of the order of events. Not every data race causes a race condition (it can be right by luck); not every race condition comes from a data race (with atomics the order can still vary the result).
  • counter++ = load, add, store. Two threads read 5, both write 6 ⇒ one update is lost. 4 threads × 1000 unprotected ⇒ result ≤ 4000, usually less, the theoretical minimum very small (down to 2).
  • Aligned 8-byte loads/stores are atomic on x86, but do not rely on it: the compiler may reorder, types may grow.

Tools: mutex, semaphore, atomic, monitor

  • Strong semaphore: waiters in FIFO order; weak: not (starvation possible). Without hardware atomics true parallel programming is impossible: every lock is built on atomic instructions.
  • Spin lock: atomic<bool> + a CAS loop; good for short critical sections, burns CPU on long waits.
  • Monitor: an object whose methods run under mutual exclusion; the logic sits in one place, harder to get wrong than semaphores.
  • Memory ordering: seq_cst (default, everyone sees the same order) · acquire/release (the writer releases, the reader acquires; matters on weakly ordered CPUs such as ARM/PowerPC) · relaxed (no guarantee; avoid unless sure).

What goes wrong, and producer-consumer

  • Deadlock: mutual exclusion + hold and wait + no preemption + circular wait, all four together. Threads sleep, CPU idle. The most practical prevention: always take locks in the same order, or std::scoped_lock(m1, m2).
  • Livelock: threads are not blocked but busy reacting to each other (two people dodging the same way in a corridor); CPU high, no progress.
  • Starvation: a thread that could continue never gets a turn because of unfair scheduling/priorities; no deadlock.
  • Producer-consumer: buffer (BUFFSIZE), slotsAvail = BUFFSIZE (free slots), resAvail = 0 (filled slots), mutex l for the indices. Producer: slotsAvail.acquire → l → write, in++ → release l → resAvail.release. Consumer symmetric. Order: semaphore first, then mutex; the reverse (sleeping on a semaphore while holding the mutex) deadlocks.
  • Termination: a shared counter or a "poison pill" message. Bugs without synchronisation: writing into a full buffer, reading from an empty one, two threads using the same index.
  • Thread pool: no per-task creation cost, thread count suited to the work (many for I/O-bound, one per core for CPU-bound); deadlock risk with dependent tasks. Asynchronous results with std::async + future.

Lecture 4 · GPUs and CUDA

GPUs, CUDA, SIMT

  • GPUs were designed for graphics; thanks to the games market they give very high FP throughput + bandwidth cheaply. Before CUDA, general computing was done by wrapping data into OpenGL textures and disguising it as drawing.
  • CUDA: the hardware + software that make the GPU programmable; a small extension to C/C++. SM (Streaming Multiprocessor): the GPU's building block; SPs (CUDA cores), register file, shared memory, caches. A block runs on one SM.
  • SIMD ↔ SIMT: SIMD applies one instruction to vector elements; in SIMT every thread has its own registers and ID and can do different work, but a warp executes one instruction at a time, so different paths run one after the other (divergence).
  • With high arithmetic intensity (compute per memory access), memory latency is hidden by other warps' computation instead of big caches.

The general CUDA approach and terms

  1. Profile: find the time-consuming, compute/bandwidth-heavy parts (not disk or network waits).
  2. Choose the data-parallel parts.
  3. Copy the inputs from CPU to GPU (PCIe; exceptions: zero-copy, shared DRAM).
  4. Write the kernels: a good thread → data mapping.
  5. Copy the results back; compare with the CPU result within a tolerance (FP addition is not associative: (a+b)+c ≠ a+(b+c) can happen).
  6. How close are we to the theoretical peak GFLOPS and GB/s? Optimise, repeat.

Terms: host = CPU + its memory (prepares, launches); device = GPU + its memory (executes). Kernel = a __global__ function launched with <<<grid, block>>>. Block (CTA) = a group of threads on one SM sharing shared memory. Warp = 32 threads scheduled together.

Thread hierarchy, warps, divergence

linear id in the block = tx + ty·Bx + tz·Bx·By warp = id / 32 lane = id % 32 global x = bx·Bx + tx global y = by·By + ty (x column, y row; x varies fastest)
  • At most 1024 threads per block (old 1.x: 512). Grids and blocks can be 1D/2D/3D (dim3). Match the thread shape to the data shape.
  • Warps always lie inside one block; a 48-thread block = 2 warps (the second half full, but it takes a full warp slot). Choose block sizes that are multiples of 32.
  • Example: dim3 block(16, 8, 2), threadIdx = (5, 3, 1) ⇒ id = 5 + 3·16 + 1·128 = 181 ⇒ warp 5, lane 21.
  • Divergence: happens only inside a warp; the two paths run in turn, the time is the sum. It does not give wrong results, it slows down. Align conditions to id / 32. In a 2D block a warp covers 32/Bx rows: in a 16×16 block a warp = 2 rows.
  • Thread block clusters (compute 9.0): block → cluster; a cluster's blocks are co-scheduled on one GPC, with cluster.sync() and distributed shared memory.

Blocks, scalability, memory, compute capability

  • Blocks must run independently: in any order, in parallel or in series. You cannot control which block runs on which SM ⇒ the same program runs on 2 SMs and on 100 SMs. You cannot assume block 0 starts first.
  • Design: split the problem into coarse pieces solved independently by blocks, then into fine pieces solved cooperatively by a block's threads. Cooperation inside a block: shared memory + __syncthreads(); between blocks: the kernel boundary (or atomics).
  • Memory: registers/local per thread, shared per block (lives as long as the block), global for everyone; read-only constant and texture. Global, constant and texture persist across kernels.
  • Compute capability major.minor: same major = same architecture (1 Tesla, 2 Fermi, 3 Kepler, 5 Maxwell, 6 Pascal, 7 Volta/Turing, 8 Ampere/Ada, 9 Hopper); not the CUDA toolkit version.

Lecture 5 · Kernels, indexing, tiling

From loop to kernel, and the host's five steps

  • Nested loops with regular indexing ⇒ most likely parallelisable. Start from the output: one output element = one thread; the outer loops become threads, the dot-product loop (k) stays inside the thread.
  • Five steps: cudaMalloc((void**)&d, bytes) → cudaMemcpy(d, h, bytes, cudaMemcpyHostToDevice) → kernel<<<grid, block>>>(…) → cudaMemcpy(h, d, bytes, cudaMemcpyDeviceToHost) → cudaFree(d). Sizes are in bytes. cudaMemcpy is synchronous, a kernel launch asynchronous.
  • cudaMalloc takes &d because it writes the allocated address into the pointer variable.
  • Qualifiers: __global__ (called from the host, runs on the device, returns void), __device__ (called from the device), __host__ (default); __host__ __device__ both.
  • Trap: float* Md, Nd, Pd; makes only Md a pointer; correct is float *Md, *Nd, *Pd;.
  • The first single-block matmul: the matrix is at most 32×32 (1024 threads); without blockIdx different blocks compute the same element.

Indexing, bounds checks, the <<<(3,3),(8,32)>>> example

grid = ⌈N / B⌉ = (N + B − 1) / B if (i < N) … A[row][col] → A[row·W + col]
  • 1000 elements with blocks of 256 ⇒ 4 blocks = 1024 threads, the last 24 threads have no element ⇒ the if is required.
  • <<<dim3(3,3), dim3(8,32)>>>: a block = 256 threads = 8 warps, 9 blocks = 2304 threads, 72 warps. The covered area is 96 rows × 24 columns. blockIdx=(2,1), threadIdx=(5,10) ⇒ row = 1·32 + 10 = 42, col = 2·8 + 5 = 21, P[42·24 + 21] = P[1029]; linear id 10·8 + 5 = 85 ⇒ warp 2.
  • In this block a warp = 4 rows × 8 columns: the N[k·24 + col] read is the same 8 floats in 4 rows ⇒ 1 segment; the P write is 4 separate 32 B segments; M[row·K + k] 4 different addresses. That is why block widths that are multiples of 32 are recommended.
  • Input and output mappings can differ (transpose, preparing shared memory).

Synchronisation, block assignment, latency hiding

  • __syncthreads(): every thread of the block waits there until all arrive; everyone finishes the previous phase before the next. All threads must call it: undefined inside if/else (unless the condition is the same for the whole block), after an early return, in a loop whose trip count depends on the thread.
  • There is no synchronisation between blocks inside a kernel (CUDA 9 cooperative groups need a special launch); splitting the kernel is the simplest way.
  • Blocks are assigned to SMs block by block; there are limits on blocks and threads per SM (GT200: 8 blocks, 1024 threads per SM; 30 SMs ⇒ 240 blocks, 30,720 threads at once).
  • Latency hiding: a warp waiting on a long-latency operation is not selected, a ready warp runs; switching is free. "You do not need to know warps to write CUDA, you need them to write fast CUDA."
  • GT200 block choice: 8×8 ⇒ 8 blocks × 64 = 512 threads (half empty); 16×16 ⇒ 4 blocks = 1024 ✓; 32×32 = 1024 > 512 threads per block ✗.

CGMA, memory types, tiling

CGMA = FP operations / global memory accesses ceiling ≈ BW/4 · CGMA (float) naive matmul: 2 reads, 2 FLOPs ⇒ CGMA 1 G80: 86.4/4 = 21.6 GFLOPS (~6% of the 367 peak) T×T tiling: reads per thread 2·W/T ⇒ CGMA = T BX×BY block: reduction = 2·BX·BY/(BX + BY)
  • Memory types: automatic scalar → register; automatic array → local (in global memory, slow; may go to registers if indexed by constants); __shared__ → block; __device__/cudaMalloc → global; __constant__ (outside functions, ~64 KB, read-only).
  • The idea of tiling: threads of a block read the same row/column again and again (each element twice in the 2×2 example). Load the tile into shared memory once, use it T times.
  • Phase m: thread (tx, ty) loads M[Row][m·T + tx] and N[m·T + ty][Col] (both coalesced within a warp), barrier, T multiply-adds, barrier. W/T phases (⌈W/T⌉ with zeros outside if W is not a multiple of T).
  • Two barriers: (1) after loading (read-after-write: you will read what others loaded), (2) after computing (write-after-read: the next phase must not overwrite).
  • Resources (G80): 16×16 tiles ⇒ Mds + Nds = 2 KB per block ⇒ 8 blocks by shared memory; but 768/256 = 3 blocks (thread limit) ⇒ only 6 KB used.
  • Non-square block (8×32): Mds[32][8], Nds[8][8]; only ty < 8 loads Nds, the barriers stay outside the if.

Lecture 6 · Compilation, memory, coalescing

API, nvcc, compatibility, initialisation

  • Runtime API (cuda*): manages context and modules implicitly, short code. Driver API (cu*): explicit contexts (the device's analogue of a process) and modules (the analogue of a dynamic library); more control. Primary context: one per device per process; one plug-in's cudaDeviceReset() breaks it for everyone.
  • Compilation chain: .cu → nvcc front end → PTX (virtual ISA, text) → ptxas → SASS (machine code for a given sm_XY, inside the cubin). nvcc -keep/-ptx, cuobjdump -sass, --ptxas-options=-v (registers/lmem).
  • Binary compatibility: a cubin for X.y runs only on X.z (z ≥ y): forward within a major, not across majors. PTX compatibility: PTX for X compiles to any binary for X or higher (old PTX cannot use new features). For future GPUs PTX must be embedded ⇒ JIT (the result goes to the compute cache).
  • -gencode arch=compute_70,code=sm_70 is SASS only; code="compute_70,sm_70" embeds the PTX too. __CUDA_ARCH__ is defined only in device code (compute_80 ⇒ 800).
  • Initialisation: since CUDA 12, cudaInitDevice/cudaSetDevice; otherwise the first call is slow. Timing: the GPU must be warmed up, cudaDeviceSynchronize() (or events) after the kernel.

  • G80: 8192 registers and 768 threads per SM ⇒ ≈ 10 registers per thread. 16 KB shared, 8 blocks ⇒ ≤ 2 KB per block for 8 blocks.
  • Register spill: the excess goes to local memory (DRAM); the kernel runs but slows down. High occupancy is no guarantee of speed.
  • Order for placing data: one thread → register (local if big; shrink it); reuse within a block → shared; read-only and everyone the same value → constant; read-only, 2D-local, fractional coordinates → texture; everything else → global (coalesced, pitch).

Shared-memory banks

bank = (byte address / 4) % 32 for s[k·t] (t = threadIdx.x) the degree = gcd(k, 32) tile[32][32]: bank of tile[r][c] = c ⇒ reading a column is 32-way tile[32][33]: bank = (r + c) % 32
  • Different words in one bank ⇒ the request is serialised (n-way ⇒ throughput / n). The same word ⇒ broadcast, no conflict. Unlike global memory, the SM does not switch warps while waiting on shared memory: a conflict slows down directly.
  • Examples: k = 1, 3, 33 ⇒ none; k = 2 ⇒ 2-way; k = 4 ⇒ 4; k = 16 ⇒ 16; k = 32 ⇒ 32; s[t % 16] ⇒ none (pairs read the same word); tile[t][t] ⇒ none (the diagonal); tile[t/2][t%2] ⇒ 16-way.
  • The cost of padding: 32 floats (128 B). But padding can break another pattern: with [32][33] the diagonal becomes 2-way.

Local, constant, texture, L2

  • Local: arrays not provably indexed by constants, very large structs/arrays, spills. In PTX .local, ld.local. Organised so consecutive 32-bit words go to consecutive threads: fully coalesced if everyone accesses the same relative index. Cached in L2 from 5.x on.
  • Constant: __constant__ outside functions, written by the host with cudaMemcpyToSymbol. A warp request is split into as many parts as there are different addresses: everyone the same address ⇒ one request; consecutive addresses ⇒ 32 requests (the opposite of global!).
  • Texture: read-only (surfaces are writable); a cache for 2D spatial locality (a hit reduces DRAM traffic, not latency); free bilinear filtering, border modes (clamp by default, border, wrap, mirror; wrap/mirror only with normalised coordinates), normalised coordinates [0,1), 8/16-bit → [0,1]/[−1,1] float conversion. Cost: copying the data into a CUDA array. Host steps: allocate the CUDA array → copy → resDesc → texDesc → texture object.
  • L2 control (CC 8.0+): part of L2 can be set aside for repeatedly accessed (persisting) data.

Coalescing, alignment, pitch

efficiency = requested bytes / moved bytes stride k ⇒ ≈ 1/k a column (stride W) ⇒ 4/32 = 12.5% pitch: start of row r = (char*)p + r·pitch (pitch in BYTES; 256 B alignment: 5/50/250 → 256, 500 → 512, 700 → 768)
  • Global memory is read in 32/64/128 B transactions aligned to their size; you cannot read "11 bytes", you read 32. 32 random addresses ⇒ 32 × 32 B = 1024 B; consecutive and aligned ⇒ 128 B ⇒ an 8-times difference.
  • Single-instruction condition: a type of 1/2/4/8/16 B, naturally aligned. Structs need __align__(8/16); a 12-byte struct is split into three 4 B reads. cudaMalloc addresses are ≥ 256 B aligned; packing several arrays into one block can break alignment (a float2 after a float may not be 8 B aligned ⇒ wrong results).
  • Quick check: is threadIdx.x (or the col derived from it) unscaled and rightmost in the address? A[row·W + col] ✓, A[col·W + row] ✗, A[2·col] half efficiency, a[i + 1] one extra segment.
  • For full coalescing in 2D, both the block width and the array width should be multiples of 32 ⇒ cudaMallocPitch/cudaMalloc3D, copied with cudaMemcpy2D/3D. Taking the pitch for an element count is the classic mistake.

Transpose and loop unrolling

  • The transpose series: copy (the ceiling and the index test; "copy first, compute later") → naive (reads coalesced, writes stride W ⇒ 32 segments) → coalesced through a shared tile (read the tile row by row, barrier, write its column as a row; the block position swaps bx ↔ by too) → no bank conflicts with [32][33] padding.
  • Blocks of 32×8 = 256 threads, 32×32 tiles: every thread handles 4 elements (y, y+8, y+16, y+24) ⇒ the index cost is shared, the warp stays consecutive.
  • Index trace (N = 1024): blockIdx (1,2), threadIdx (5,3) ⇒ loading x = 37, y = 67 (rows 67, 75, 83, 91); writing x = 69, y = 35.
  • Measurements: global coalescing is the critical factor; barrier and shared costs are small; padding brings the coalesced transpose close to copy speed.
  • Loop unrolling: copy the body, cut the trip count ⇒ fewer counter/compare/branch instructions, constant indices, independent loads back to back (ILP). Cost: bigger code, more live variables and registers ⇒ spill / lower occupancy. The compiler already unrolls constant trip counts; run-time values such as width/T cannot be fully unrolled.

Lecture 7 · Error checking and control flow

Error checking

  • Every runtime function returns a cudaError_t; an asynchronous function returns before the device finishes, so it cannot report later errors. A kernel launch returns nothing.
  • An asynchronous error shows up in a later, unrelated call ("on the wrong line"). Execution errors are sticky: every later call fails.
  • One error variable per host thread: cudaPeekAtLastError() reads it, cudaGetLastError() reads it and resets it to cudaSuccess.
  • Recommended pattern: cudaGetLastError(); (clear) → k<<<…>>>(…); → launchErr = cudaGetLastError(); (configuration: 2048 threads per block, too much shared memory, bad arguments) → runErr = cudaDeviceSynchronize(); (execution: out of bounds, null pointers).

Branching, predication, loops

  • Every control-flow statement (if, switch, for, while, do) can make a warp diverge; the paths run serially, then converge. If the condition depends on the thread ID, align it to warp boundaries (warp layout is deterministic).
  • 128 threads (4 warps): t % 2 == 0 ⇒ 4; t < 64 ⇒ 0; t < 70 ⇒ 1 (warp 2); t / 32 == 1 ⇒ 0. In a 16×16 block threadIdx.y % 2 == 0 ⇒ 8 (all).
  • Prediction (CPU): guess the branch, execute speculatively, discard on a miss. Predication (GPU): instructions are not skipped, a predicate per thread; false ones write no result, compute no address, read no operand. No jump and no divergence for short branches.
  • Branch optimisation is needed because of pipelining: a branch stalls the pipeline until the next instruction is known.
  • #pragma unroll right before the loop, applying only to it: no number ⇒ fully unrolls a constant trip count (otherwise not at all); N ⇒ N times (code added for leftover iterations, correct for n < N too); 1 ⇒ no unrolling.
  • Signed counters: signed overflow is undefined ⇒ the compiler may assume "i never overflows" and turn offset + stride·i into a pointer increment. Unsigned overflow is defined (wraps at 232) ⇒ those transformations are not allowed; and for (unsigned i = n−1; i >= 0; i--) never ends.

Trick questions 1 · Calculations

All of them can be done without a calculator. Each question combines two topics; first write down which formulas you need.

H1 · Amdahl, backwards

95% of a program can be parallelised. (a) Speedup and efficiency on 16 cores? (b) At least how many cores give a speedup of 15? (c) Can a speedup of 20 be reached? (d) What does Gustafson give for the same program on 16 cores, and which law do you use when?

(a) 1/(0.05 + 0.95/16) = 1/(0.05 + 0.059375) = 1/0.109375 ≈ 9.14; efficiency 9.14/16 ≈ 57%. (b) 1/(0.05 + 0.95/N) ≥ 15 ⇒ 0.05 + 0.95/N ≤ 1/15 ≈ 0.0667 ⇒ 0.95/N ≤ 0.0167 ⇒ N ≥ 57. (c) No: the ceiling 1/0.05 = 20 is only approached as N → ∞, never reached. (d) 0.05 + 0.95·16 = 15.25. Fixed problem size (the same job faster): Amdahl; fixed time with the problem growing with N: Gustafson.

H2 · An army of ants or an elephant?

An expensive CPU is r = 4 times faster than a cheap one. α = 0.8 of the program is parallel. (a) How many cheap CPUs beat the single expensive one? (b) What if r = 5? (c) Why does this seem to contradict how Top500 machines are built?

Speedup relative to the expensive CPU: 1/((1−α)r + αr/N). (a) 0.2·4 + 3.2/N < 1 ⇒ 3.2/N < 0.2 ⇒ N > 16 ⇒ 17 cheap CPUs. (b) (1−α)r = 0.2·5 = 1: the denominator is always > 1, no N is enough (r ≥ 1/(1−α) = 5). (c) The calculation keeps the problem fixed (Amdahl). Supercomputers solve bigger problems: the parallel part grows with N (Gustafson), so many cheap cores win.

H3 · A pipeline and a replicated stage

A 4-stage pipeline: 3, 7, 2, 4 ms. (a) How long do 50 items take? (b) What if the 7 ms stage runs as two copies? (c) Why does it still not drop to 2 ms?

(a) The first item leaves at 3+7+2+4 = 16 ms, then one every 7 ms: 16 + 49·7 = 359 ms. (b) Two copies ⇒ that stage effectively delivers one item every 3.5 ms; the new bottleneck is the 4 ms stage: 16 + 49·4 = 212 ms. (c) The slowest stage sets the speed; the 4 ms stage (then the 3 ms one) is next. Removing one bottleneck reveals the next.

H4 · Occupancy: which limit wins?

SM: at most 2048 threads, 64 warps, 32 blocks, 65,536 registers, 64 KB shared. Kernel: 192-thread blocks, 40 registers per thread, 9 KB shared per block. (a) Blocks per SM, occupancy? (b) If shared drops to 8 KB? (c) If registers also drop to 32?

A block = 6 warps, 192·40 = 7680 registers. (a) Threads: ⌊2048/192⌋ = 10; warps: 64/6 = 10; registers: ⌊65536/7680⌋ = 8; shared: ⌊64/9⌋ = 7; blocks: 32 ⇒ 7 blocks = 42 warps / 64 = 65.6% (shared is the limit). (b) Shared 64/8 = 8, registers 8 ⇒ 8 blocks = 48 warps = 75% (registers and shared limit together). (c) 192·32 = 6144 ⇒ ⌊65536/6144⌋ = 10; shared 8; threads 10 ⇒ still 8: with one bottleneck gone, shared limits. Lesson: improving one limit is not enough; look at the smallest.

H5 · double with stride 3: how many segments?

A warp reads a[3*threadIdx.x] from a 128 B-aligned double array. How many 32 B segments are moved, and what is the efficiency? And for float?

double: lane i reads bytes 24i … 24i+7; the last lane 744–751. The gap between elements is 16 B < 32 B, so every 32 B segment from 0 to 767 is touched: 24 segments = 768 B moved, 32·8 = 256 B used ⇒ 33%. float: lane i bytes 12i…12i+3, the last 372–375 ⇒ 12 segments from 0 to 383 = 384 B, 128 B used ⇒ again 33%. With stride k the efficiency is ≈ 1/k (when an element is smaller than a segment).

H6 · 3D index, warp and lane

Grid (4,3,2), block (8,4,4); volume W = 32, H = 12, D = 8 (x fastest). For blockIdx = (3,2,1), threadIdx = (7,3,2): global (x, y, z), the linear index in the volume, the linear id in the block, warp and lane, the block's linear number?

x = 3·8 + 7 = 31, y = 2·4 + 3 = 11, z = 1·4 + 2 = 6. Linear = x + W·(y + H·z) = 31 + 32·(11 + 72) = 31 + 2656 = 2687. In the block: 7 + 8·(3 + 4·2) = 7 + 88 = 95 ⇒ warp 95/32 = 2, lane 95 % 32 = 31. Block number: 3 + 4·(2 + 3·1) = 23. Check: the grid covers 4·8 = 32 = W, 3·4 = 12 = H, 2·4 = 8 = D, so the volume is covered exactly.

H7 · Divergence in a 2D block

Block (16,16). How many warps diverge for each condition? (a) if (threadIdx.x < 8) (b) if (threadIdx.y < 8) (c) if ((threadIdx.y * 16 + threadIdx.x) % 64 < 32) (d) if (threadIdx.y % 2 == 0)

In a 16×16 block a warp = two rows (y = 2w and 2w+1), each row x = 0..15. (a) Half of every row is true ⇒ all 8 warps. (b) y < 8 ⇒ warps 0–3 all true, 4–7 all false ⇒ 0. (c) Linear id % 64 < 32 ⇒ even warps true, odd warps false; each warp is uniform ⇒ 0. (d) A warp holds one even and one odd row ⇒ 8. Trap: counting (b) as divergence because “half are false”.

H8 · Tile + halo traffic in a convolution

A 5×5 filter, a 16×16 output tile, one tile per block. (a) Global reads per output without shared memory? (b) If the tile with its halo is loaded into shared memory once, reads per block and per output? (c) How many times fewer? (d) How many bytes of shared memory? (e) Where should the filter live?

(a) 25. (b) The halo is 2 on each side ⇒ (16+4)² = 400 reads / 256 outputs ≈ 1.56. (c) 25/1.5625 = 16 times. (d) 400·4 = 1600 B. (e) __constant__: at the same loop step every thread of a warp reads the same coefficient ⇒ one request, broadcast. Bigger tiles shrink the halo/interior ratio (with 32×32: 36²/1024 ≈ 1.27 reads per output) but grow the shared and thread limits.

H9 · Pitch and wrong pointer arithmetic

Rows of 1000 floats, 256 B alignment. (a) Pitch? (b) Byte offset of row 3, column 999? (c) Where does someone who writes p[3*pitch + 999] for a float* p end up?

(a) 4000 B → the next multiple of 256, 4096 B. (b) 3·4096 + 999·4 = 12288 + 3996 = 16284 B. (c) float* arithmetic counts elements: 3·4096 + 999 = 13287 elements = 53148 B, the middle of row 12 (wrong, and out of bounds if the allocation is small). Correct: ((float*)((char*)p + 3*pitch))[999].

H10 · Compute or memory bound? Is tiling enough?

G80: 367 GFLOPS peak, 86.4 GB/s. (a) What CGMA makes matmul compute bound? (b) Is T = 16 tiling enough, and what is the ceiling? (c) Why is T = 32 not possible on the G80?

(a) 86.4/4 = 21.6 G floats/s ⇒ 21.6·CGMA ≥ 367 ⇒ CGMA ≥ 17. (b) T = 16 ⇒ CGMA 16 ⇒ 21.6·16 = 345.6 GFLOPS: still just memory bound but very close to the peak. (c) 32×32 = 1024 threads exceeds the G80's 512 threads per block (shared would fit: 2·32²·4 = 8 KB). Giving each thread several elements (e.g. 32×16 blocks) gets around it.

Trick questions 2 · Read the code, find the bug

All of these compile; some are still wrong. For each, first write what it does, then what is broken and the fix. They are all in one program: ▶ runs the fixed versions.

K1 · A barrier is missing

for (int m = 0; m < width / T; ++m) {
    Ms[ty][tx] = M[row * width + m * T + tx];
    Ns[ty][tx] = N[(m * T + ty) * width + col];
    __syncthreads();
    for (int k = 0; k < T; ++k)
        sum += Ms[ty][k] * Ns[k][tx];
}

What can go wrong? Why does it usually give the right result when you test it?

There is no barrier after the inner loop: a fast warp writes the next phase's Ms/Ns element while a slow warp is still reading the old phase's value (a write-after-read race) ⇒ the result is undefined. In small blocks the warps move almost together, so it usually works; "it ran" is no proof. Fix: a second __syncthreads() after the inner loop.

K2 · An early return

__global__ void earlyReturn(const float* in, float* out, int n) {
    __shared__ float s[256];
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;
    s[threadIdx.x] = in[i];
    __syncthreads();
    out[i] = s[255 - threadIdx.x];
}

In which block are there two separate bugs? Write the fixed code.

In the last block (block 3: i = 768…1023) 24 threads (i ≥ 1000) return: (1) not every thread reaches the barrier ⇒ undefined behaviour; (2) valid threads read s[255 − threadIdx.x] from slots those 24 threads never wrote ⇒ garbage. Fix: s[threadIdx.x] = (i < n) ? in[i] : 0;, everyone calls __syncthreads(), then if (i < n) out[i] = ….

K3 · Histogram: two barriers, still wrong

__shared__ unsigned int local[BINS];
if (threadIdx.x < BINS) local[threadIdx.x] = 0;
__syncthreads();
int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) local[data[i] % BINS]++;
__syncthreads();
if (threadIdx.x < BINS) hist[threadIdx.x] += local[threadIdx.x];

Find the two separate races. Why are the barriers not enough? What is the fix, and why count in shared memory first and add to global memory later?

(1) local[bin]++: many threads of a block read-add-write the same bin ⇒ lost updates. (2) hist[...] += ...: different blocks write the same global bin ⇒ lost again. A barrier only coordinates progress; it does not stop simultaneous writes. Fix: atomicAdd(&local[bin], 1u) and atomicAdd(&hist[b], local[b]) (histFixed in the program). Shared atomics are cheap, and global memory gets only one atomic per bin per block: 4096 blocks × 64 instead of 220.

K4 · Right result, terrible speed

int row = blockIdx.x * blockDim.x + threadIdx.x;
int col = blockIdx.y * blockDim.y + threadIdx.y;
if (row < H && col < W) A[row * W + col] *= 2;

With the right grid the result is correct. Describe one warp's access: how many segments, what efficiency? The fix?

In a warp threadIdx.x = 0..31 varies and threadIdx.y is fixed ⇒ row is consecutive, col fixed. The addresses are W = 4096 floats = 16 KB apart ⇒ every lane its own 32 B segment: 32 segments to read, 32 to write, each 32 B piece using 4 B ⇒ 12.5%. Fix: column from x, row from y: col = blockIdx.x*blockDim.x + threadIdx.x; row = blockIdx.y*blockDim.y + threadIdx.y; (and the grid to match).

K5 · A barrier inside a loop

for (int k = 0; k < threadIdx.x % 4; ++k) {
    __syncthreads();
    s[threadIdx.x] += s[(threadIdx.x + 1) % 128];
}

The barrier is not inside an if. Why is it still wrong? Is there a second race?

The trip count depends on the thread (0, 1, 2 or 3): threads with threadIdx.x % 4 == 0 never reach the barrier, the others reach it a different number of times ⇒ the barrier is not called the same number of times by every thread ⇒ undefined. Second race: thread t reads s[t+1] while thread t+1 may be updating it (the barrier is not between the read and the write). Fix: make the trip count the same for the whole block (e.g. 3 rounds, threads that need fewer do nothing), and put a barrier between reading and writing (read into a temporary, barrier, then write).

K6 · One tile, three reads

__shared__ float tile[32][32];
float a = tile[t][0];
float b = tile[t][t];
float c = tile[t / 2][t % 2];

How many ways does each of the three reads conflict? What if the tile were tile[32][33]?

The bank of tile[r][c] is (32r + c) % 32 = c. (a) c is always 0 ⇒ 32 different words in one bank ⇒ 32-way. (b) bank = t ⇒ all different ⇒ no conflict (the diagonal). (c) bank = t % 2 ⇒ only 2 banks with 16 different words each ⇒ 16-way. With [32][33] the bank is (33r + c) % 32 = (r + c) % 32: (a) r = t ⇒ all different, no conflict; (b) 2t % 32 ⇒ t and t+16 share a bank ⇒ 2-way (padding broke the diagonal!); (c) (t/2 + t%2) % 32 ⇒ values 0,1,1,2,2,3,… ⇒ banks such as 1, 2 each get two different words ⇒ 2-way.

K7 · An endless loop on the CPU side

void reverseCopy(const float* in, float* out, unsigned n) {
    for (unsigned i = n - 1; i >= 0; i--)
        out[n - 1 - i] = in[i];
}

What happens? And for n = 0? How does it connect to Lecture 7's advice on signed counters?

An unsigned is never < 0: i >= 0 is always true; after i = 0, i-- wraps to 232 − 1 ⇒ out-of-bounds writes, an endless loop / crash. With n = 0, i starts at 232 − 1. Fix: for (int i = (int)n - 1; i >= 0; i--). Connection: unsigned overflow is defined (it wraps); it causes this bug and also limits the compiler's optimisations. A signed counter is better on both counts.

Trick questions 3 · Design and "why"

T1 · Sum 10⁸ elements

Compute the sum of 10⁸ floats on the GPU. Why can you not combine all blocks' results with a barrier inside one kernel? Write the steps of your design and the synchronisation in each step.

__syncthreads() is per block, and blocks run in any order, maybe not at the same time: a "grid barrier" that assumes all of them are resident can hang (cooperative groups need a special launch). Design: (1) each block sums its part as a tree in shared memory (half the threads per step, __syncthreads() between steps; with the divisor aligned to threadIdx.x / 32 there is no divergence except in the last steps); (2) the block's result goes to partial[blockIdx.x]; (3) a second kernel (or the same kernel with one block) sums partial. The kernel boundary is the barrier between blocks. Alternative: one atomicAdd per block; short, but the float result may not repeat bit for bit because the order of additions changes.

T2 · The heat equation: cluster or GPU?

On a 2D grid every cell takes the average of its 4 neighbours each step (1000 steps). Design it with PCAM for a 100-node distributed-memory cluster and for a GPU. Where is the communication, and where do the two designs differ?

P: one task per cell (geometric/data decomposition). C: 4 neighbours each step; a dependency between steps (step t+1 waits for step t). A: on the cluster 100 pieces (10×10 tiles or strips; tiles shrink the halo/interior ratio), and at the end of each step only the edge rows/columns go to the neighbour as messages. M: equal pieces, neighbouring pieces on nearby nodes. GPU: tile = block, the halo is loaded into shared memory, a step = a kernel launch (the kernel boundary is the global barrier between steps), two buffers (old/new) alternate. Difference: on the cluster communication is expensive messages ⇒ big tiles; on the GPU it is global memory traffic ⇒ coalesced rows and reuse through shared memory.

T3 · Is more occupancy always faster?

A friend cut registers from 64 to 32 with -maxrregcount and raised occupancy from 50% to 100%, but the kernel got slower. Explain two possible reasons.

(1) Register spill: values that do not fit in 32 go to local memory (DRAM); every access costs hundreds of cycles and eats the latency hiding gained. (2) If the kernel is already bandwidth bound, or 50% already gives enough warps to hide latency, extra warps gain nothing; also each warp gets less cache. Occupancy is a tool, not the goal: measure (check spills with --ptxas-options=-v).

T4 · The error on the wrong line

A program does k1<<<…>>>(); k2<<<…>>>(); cudaMemcpy(…);. cudaMemcpy returns "illegal memory access". Which kernel may be guilty, how do you find out, and why does every later call fail too?

Either: launches are asynchronous, so the error is reported by the first synchronising call (here cudaMemcpy). To find it, check cudaGetLastError() (launch error) and cudaDeviceSynchronize() (execution error) after each kernel; the one after which the error appears is guilty. Execution errors are sticky: the context is broken and every later CUDA call in the process returns the same error; the program has to restart.

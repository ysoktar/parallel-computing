Detailed summary

Lecture 1: why parallel, how much faster

  • Power wall: power ≈ f³; around 2005 frequency stopped at 2–4 GHz. Moore's law is about transistor count, not frequency; the extra transistors went into cores.
  • Flynn: SISD, SIMD, MISD, MIMD. The GPU's programming model is SIMT (a warp = one instruction, 32 threads). Shared memory (one address space; on NUMA remote memory is slower but addressing is shared) ↔ distributed memory (message passing, scales very far).
  • Measurement rules: same hardware and conditions; the serial side must be the fastest known serial solution; report kernel-only and end-to-end (with copies) speedup separately.
  • Amdahl (fixed problem, strong scaling): S = 1/((1−α)+α/N) → 1/(1−α) as N → ∞. Gustafson (fixed time, weak scaling): S = (1−α)+αN.
  • Ants vs elephants: if the expensive CPU is r times faster, the speedup of N cheap CPUs relative to it is 1/((1−α)r + αr/N); if r ≥ 1/(1−α) it never exceeds 1.
  • Latency ↔ throughput: a CPU finishes one job fast, a GPU finishes many jobs per unit time.

Lecture 2: design

  • Ask first: is parallelism necessary, does the algorithm allow it?
  • PCAM: Partitioning (10–100 times as many pieces as processors), Communication (dependency graph), Agglomeration (group to cut communication, ~10 times), Mapping (load balance + heavily communicating groups on one node; NP-complete in general).
  • Decomposition patterns: task parallelism (does not scale), divide and conquer (parallelism read from the dependency graph), geometric (needs halos), recursive data (prefix sum), pipeline (throughput ≤ 1/longest stage), event-based.
  • Program structure: GPLS (SPMD, MPMD, master-worker, map-reduce) ↔ GSLP (fork/join, loop parallelism). A CUDA kernel = geometric decomposition + SPMD.
  • Pipeline time: first output = the sum of the stage times, then one output per "longest stage".

Lecture 3: threads and synchronisation

  • Threads share the address space (stack, registers, program counter are separate). Data race: concurrent access, at least one write, no synchronisation (undefined in C++). Race condition: a wrong result because of the ordering.
  • counter++ = read + add + write; if two threads read the same old value, one update is lost.
  • Mutex: one thread + ownership. Semaphore: N permits (counting); a binary semaphore signals an "event". Atomic: one indivisible operation (CAS, LL/SC). Monitor / condition variable: release the lock and wait for a condition; check the condition with while.
  • Deadlock (four conditions: mutual exclusion, hold and wait, no preemption, circular wait; CPU idle) ↔ livelock (CPU busy, no progress) ↔ starvation (one thread never gets a turn). Prevention: always take locks in the same order, std::scoped_lock.
  • Producer-consumer: slotsAvail (free slots) and resAvail (filled slots) semaphores + a mutex for the indices; semaphore first, then mutex.
  • Memory ordering: seq_cst (default, everyone sees the same order), acquire/release (between pairs), relaxed (no ordering guarantee).

Lectures 4–5: the CUDA model, kernels, tiling

  • The host prepares (cudaMalloc → cudaMemcpy H2D → kernel → cudaMemcpy D2H → cudaFree), the device executes. Kernel launches are asynchronous; cudaDeviceSynchronize() before taking the time.
  • Qualifiers: __global__ (called from the host, runs on the device, void), __device__, __host__.
  • Hierarchy: a block ≤ 1024 threads, on one SM; a warp = 32 consecutive linear ids; blocks are independent and unordered → scalability. A partial warp takes a full warp slot.
  • Divergence: only within a warp; the two paths run one after the other, the time is the sum. No divergence if the condition is aligned to threadIdx / 32.
  • Barrier: __syncthreads() is per block; every thread of the block must reach it (undefined inside an if, after an early return, in a loop whose trip count depends on the thread).
  • Latency hiding: a ready warp runs instead of a waiting one (zero-cost switch); this needs many warps.
  • CGMA: naive matmul 1 (2 reads, 2 FLOPs). G80: 86.4 GB/s ⇒ 21.6 GFLOPS ≈ 6% of the 367 peak. T×T tiling: CGMA = T; for a rectangular BX×BY block the reduction is 2·BX·BY/(BX+BY).
  • Tiled kernel: in each phase everyone loads one element of the M and N tiles; barrier (1) so the tile is full, barrier (2) so it is not overwritten; ⌈width/T⌉ phases, 0 loaded at the edges.

Lecture 6: compilation and memory

  • Compilation: .cu → PTX (virtual ISA) → ptxas → SASS (cubin). A cubin for X.y runs only on X.z (z ≥ y); for new GPUs PTX must be embedded (JIT). -arch chooses the PTX, -code the binary. Register count: --ptxas-options=-v.
  • Memory map: register (thread, ~1 cycle) · shared (block, a few cycles, banks) · local (per thread but in DRAM!) · global (grid + host, 400–600 cycles, coalescing) · constant (read-only, same address → broadcast) · texture (read-only, 2D locality, interpolation, border modes).
  • Occupancy: blocks per SM = min(thread limit/Bt, warp limit/Bw, registers/(Bt·reg), shared/Bshared, block limit). Register spill → local memory.
  • Banks: 32 banks, bank = word index % 32; different words in one bank = conflict, the same word = broadcast. For s[k·threadIdx.x] the degree is gcd(k, 32). Reading a column of a 32×32 tile is 32-way → [32][33].
  • Coalescing: a warp's addresses are gathered into 32/64/128 B aligned segments; efficiency = used/moved. The pitch is in bytes: row r = (char*)p + r·pitch. Alignment: type of 1/2/4/8/16 B and naturally aligned.
  • Transpose: naive writes are strided; with a shared tile both sides coalesce; 32×8 blocks + 4 elements per thread; the copy kernel is the ceiling and the index test.

Lecture 7: errors and control flow

  • Runtime calls return a cudaError_t; a kernel launch does not. Configuration error → cudaGetLastError() right after the launch; execution error → cudaDeviceSynchronize() or a later, unrelated call. Execution errors are sticky.
  • cudaPeekAtLastError() reads; cudaGetLastError() reads and resets.
  • Predication (GPU): instructions are not skipped, they have no effect in threads whose predicate is false; for short branches. Prediction (CPU): guess + speculative execution.
  • #pragma unroll N right before the loop; without a number: fully unrolls a constant trip count; 1: no unrolling. Cost: registers and code size → spill / occupancy.
  • Make the counter an int: signed overflow is undefined, so the compiler optimises more; a count-down loop i >= 0 with an unsigned counter never ends.

Hard calculation questions

All of them can be done without a calculator. Each question combines two topics; first write down which formulas you need.

H1 · Amdahl, backwards

95% of a program can be parallelised. (a) Speedup and efficiency on 16 cores? (b) At least how many cores give a speedup of 15? (c) Can a speedup of 20 be reached? (d) What does Gustafson give for the same program on 16 cores, and which law do you use when?

(a) 1/(0.05 + 0.95/16) = 1/(0.05 + 0.059375) = 1/0.109375 ≈ 9.14; efficiency 9.14/16 ≈ 57%. (b) 1/(0.05 + 0.95/N) ≥ 15 ⇒ 0.05 + 0.95/N ≤ 1/15 ≈ 0.0667 ⇒ 0.95/N ≤ 0.0167 ⇒ N ≥ 57. (c) No: the ceiling 1/0.05 = 20 is only approached as N → ∞, never reached. (d) 0.05 + 0.95·16 = 15.25. Fixed problem size (the same job faster): Amdahl; fixed time with the problem growing with N: Gustafson.

H2 · An army of ants or an elephant?

An expensive CPU is r = 4 times faster than a cheap one. α = 0.8 of the program is parallel. (a) How many cheap CPUs beat the single expensive one? (b) What if r = 5? (c) Why does this seem to contradict how Top500 machines are built?

Speedup relative to the expensive CPU: 1/((1−α)r + αr/N). (a) 0.2·4 + 3.2/N < 1 ⇒ 3.2/N < 0.2 ⇒ N > 16 ⇒ 17 cheap CPUs. (b) (1−α)r = 0.2·5 = 1: the denominator is always > 1, no N is enough (r ≥ 1/(1−α) = 5). (c) The calculation keeps the problem fixed (Amdahl). Supercomputers solve bigger problems: the parallel part grows with N (Gustafson), so many cheap cores win.

H3 · A pipeline and a replicated stage

A 4-stage pipeline: 3, 7, 2, 4 ms. (a) How long do 50 items take? (b) What if the 7 ms stage runs as two copies? (c) Why does it still not drop to 2 ms?

(a) The first item leaves at 3+7+2+4 = 16 ms, then one every 7 ms: 16 + 49·7 = 359 ms. (b) Two copies ⇒ that stage effectively delivers one item every 3.5 ms; the new bottleneck is the 4 ms stage: 16 + 49·4 = 212 ms. (c) The slowest stage sets the speed; the 4 ms stage (then the 3 ms one) is next. Removing one bottleneck reveals the next.

H4 · Occupancy: which limit wins?

SM: at most 2048 threads, 64 warps, 32 blocks, 65,536 registers, 64 KB shared. Kernel: 192-thread blocks, 40 registers per thread, 9 KB shared per block. (a) Blocks per SM, occupancy? (b) If shared drops to 8 KB? (c) If registers also drop to 32?

A block = 6 warps, 192·40 = 7680 registers. (a) Threads: ⌊2048/192⌋ = 10; warps: 64/6 = 10; registers: ⌊65536/7680⌋ = 8; shared: ⌊64/9⌋ = 7; blocks: 32 ⇒ 7 blocks = 42 warps / 64 = 65.6% (shared is the limit). (b) Shared 64/8 = 8, registers 8 ⇒ 8 blocks = 48 warps = 75% (registers and shared limit together). (c) 192·32 = 6144 ⇒ ⌊65536/6144⌋ = 10; shared 8; threads 10 ⇒ still 8: with one bottleneck gone, shared limits. Lesson: improving one limit is not enough; look at the smallest.

H5 · double with stride 3: how many segments?

A warp reads a[3*threadIdx.x] from a 128 B-aligned double array. How many 32 B segments are moved, and what is the efficiency? And for float?

double: lane i reads bytes 24i … 24i+7; the last lane 744–751. The gap between elements is 16 B < 32 B, so every 32 B segment from 0 to 767 is touched: 24 segments = 768 B moved, 32·8 = 256 B used ⇒ 33%. float: lane i bytes 12i…12i+3, the last 372–375 ⇒ 12 segments from 0 to 383 = 384 B, 128 B used ⇒ again 33%. With stride k the efficiency is ≈ 1/k (when an element is smaller than a segment).

H6 · 3D index, warp and lane

Grid (4,3,2), block (8,4,4); volume W = 32, H = 12, D = 8 (x fastest). For blockIdx = (3,2,1), threadIdx = (7,3,2): global (x, y, z), the linear index in the volume, the linear id in the block, warp and lane, the block's linear number?

x = 3·8 + 7 = 31, y = 2·4 + 3 = 11, z = 1·4 + 2 = 6. Linear = x + W·(y + H·z) = 31 + 32·(11 + 72) = 31 + 2656 = 2687. In the block: 7 + 8·(3 + 4·2) = 7 + 88 = 95 ⇒ warp 95/32 = 2, lane 95 % 32 = 31. Block number: 3 + 4·(2 + 3·1) = 23. Check: the grid covers 4·8 = 32 = W, 3·4 = 12 = H, 2·4 = 8 = D, so the volume is covered exactly.

H7 · Divergence in a 2D block

Block (16,16). How many warps diverge for each condition? (a) if (threadIdx.x < 8) (b) if (threadIdx.y < 8) (c) if ((threadIdx.y * 16 + threadIdx.x) % 64 < 32) (d) if (threadIdx.y % 2 == 0)

In a 16×16 block a warp = two rows (y = 2w and 2w+1), each row x = 0..15. (a) Half of every row is true ⇒ all 8 warps. (b) y < 8 ⇒ warps 0–3 all true, 4–7 all false ⇒ 0. (c) Linear id % 64 < 32 ⇒ even warps true, odd warps false; each warp is uniform ⇒ 0. (d) A warp holds one even and one odd row ⇒ 8. Trap: counting (b) as divergence because “half are false”.

H8 · Tile + halo traffic in a convolution

A 5×5 filter, a 16×16 output tile, one tile per block. (a) Global reads per output without shared memory? (b) If the tile with its halo is loaded into shared memory once, reads per block and per output? (c) How many times fewer? (d) How many bytes of shared memory? (e) Where should the filter live?

(a) 25. (b) The halo is 2 on each side ⇒ (16+4)² = 400 reads / 256 outputs ≈ 1.56. (c) 25/1.5625 = 16 times. (d) 400·4 = 1600 B. (e) __constant__: at the same loop step every thread of a warp reads the same coefficient ⇒ one request, broadcast. Bigger tiles shrink the halo/interior ratio (with 32×32: 36²/1024 ≈ 1.27 reads per output) but grow the shared and thread limits.

H9 · Pitch and wrong pointer arithmetic

Rows of 1000 floats, 256 B alignment. (a) Pitch? (b) Byte offset of row 3, column 999? (c) Where does someone who writes p[3*pitch + 999] for a float* p end up?

(a) 4000 B → the next multiple of 256, 4096 B. (b) 3·4096 + 999·4 = 12288 + 3996 = 16284 B. (c) float* arithmetic counts elements: 3·4096 + 999 = 13287 elements = 53148 B, the middle of row 12 (wrong, and out of bounds if the allocation is small). Correct: ((float*)((char*)p + 3*pitch))[999].

H10 · Compute or memory bound? Is tiling enough?

G80: 367 GFLOPS peak, 86.4 GB/s. (a) What CGMA makes matmul compute bound? (b) Is T = 16 tiling enough, and what is the ceiling? (c) Why is T = 32 not possible on the G80?

(a) 86.4/4 = 21.6 G floats/s ⇒ 21.6·CGMA ≥ 367 ⇒ CGMA ≥ 17. (b) T = 16 ⇒ CGMA 16 ⇒ 21.6·16 = 345.6 GFLOPS: still just memory bound but very close to the peak. (c) 32×32 = 1024 threads exceeds the G80's 512 threads per block (shared would fit: 2·32²·4 = 8 KB). Giving each thread several elements (e.g. 32×16 blocks) gets around it.

Read the code, find the bug

All of these compile; some are still wrong. For each, first write what it does, then what is broken and the fix. They are all in one program: ▶ runs the fixed versions.

K1 · A barrier is missing

for (int m = 0; m < width / T; ++m) {
    Ms[ty][tx] = M[row * width + m * T + tx];
    Ns[ty][tx] = N[(m * T + ty) * width + col];
    __syncthreads();
    for (int k = 0; k < T; ++k)
        sum += Ms[ty][k] * Ns[k][tx];
}

What can go wrong? Why does it usually give the right result when you test it?

There is no barrier after the inner loop: a fast warp writes the next phase's Ms/Ns element while a slow warp is still reading the old phase's value (a write-after-read race) ⇒ the result is undefined. In small blocks the warps move almost together, so it usually works; "it ran" is no proof. Fix: a second __syncthreads() after the inner loop.

K2 · An early return

__global__ void earlyReturn(const float* in, float* out, int n) {
    __shared__ float s[256];
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;
    s[threadIdx.x] = in[i];
    __syncthreads();
    out[i] = s[255 - threadIdx.x];
}

In which block are there two separate bugs? Write the fixed code.

In the last block (block 3: i = 768…1023) 24 threads (i ≥ 1000) return: (1) not every thread reaches the barrier ⇒ undefined behaviour; (2) valid threads read s[255 − threadIdx.x] from slots those 24 threads never wrote ⇒ garbage. Fix: s[threadIdx.x] = (i < n) ? in[i] : 0;, everyone calls __syncthreads(), then if (i < n) out[i] = ….

K3 · Histogram: two barriers, still wrong

__shared__ unsigned int local[BINS];
if (threadIdx.x < BINS) local[threadIdx.x] = 0;
__syncthreads();
int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) local[data[i] % BINS]++;
__syncthreads();
if (threadIdx.x < BINS) hist[threadIdx.x] += local[threadIdx.x];

Find the two separate races. Why are the barriers not enough? What is the fix, and why count in shared memory first and add to global memory later?

(1) local[bin]++: many threads of a block read-add-write the same bin ⇒ lost updates. (2) hist[...] += ...: different blocks write the same global bin ⇒ lost again. A barrier only coordinates progress; it does not stop simultaneous writes. Fix: atomicAdd(&local[bin], 1u) and atomicAdd(&hist[b], local[b]) (histFixed in the program). Shared atomics are cheap, and global memory gets only one atomic per bin per block: 4096 blocks × 64 instead of 220.

K4 · Right result, terrible speed

int row = blockIdx.x * blockDim.x + threadIdx.x;
int col = blockIdx.y * blockDim.y + threadIdx.y;
if (row < H && col < W) A[row * W + col] *= 2;

With the right grid the result is correct. Describe one warp's access: how many segments, what efficiency? The fix?

In a warp threadIdx.x = 0..31 varies and threadIdx.y is fixed ⇒ row is consecutive, col fixed. The addresses are W = 4096 floats = 16 KB apart ⇒ every lane its own 32 B segment: 32 segments to read, 32 to write, each 32 B piece using 4 B ⇒ 12.5%. Fix: column from x, row from y: col = blockIdx.x*blockDim.x + threadIdx.x; row = blockIdx.y*blockDim.y + threadIdx.y; (and the grid to match).

K5 · A barrier inside a loop

for (int k = 0; k < threadIdx.x % 4; ++k) {
    __syncthreads();
    s[threadIdx.x] += s[(threadIdx.x + 1) % 128];
}

The barrier is not inside an if. Why is it still wrong? Is there a second race?

The trip count depends on the thread (0, 1, 2 or 3): threads with threadIdx.x % 4 == 0 never reach the barrier, the others reach it a different number of times ⇒ the barrier is not called the same number of times by every thread ⇒ undefined. Second race: thread t reads s[t+1] while thread t+1 may be updating it (the barrier is not between the read and the write). Fix: make the trip count the same for the whole block (e.g. 3 rounds, threads that need fewer do nothing), and put a barrier between reading and writing (read into a temporary, barrier, then write).

K6 · One tile, three reads

__shared__ float tile[32][32];
float a = tile[t][0];
float b = tile[t][t];
float c = tile[t / 2][t % 2];

How many ways does each of the three reads conflict? What if the tile were tile[32][33]?

The bank of tile[r][c] is (32r + c) % 32 = c. (a) c is always 0 ⇒ 32 different words in one bank ⇒ 32-way. (b) bank = t ⇒ all different ⇒ no conflict (the diagonal). (c) bank = t % 2 ⇒ only 2 banks with 16 different words each ⇒ 16-way. With [32][33] the bank is (33r + c) % 32 = (r + c) % 32: (a) r = t ⇒ all different, no conflict; (b) 2t % 32 ⇒ t and t+16 share a bank ⇒ 2-way (padding broke the diagonal!); (c) (t/2 + t%2) % 32 ⇒ values 0,1,1,2,2,3,… ⇒ banks such as 1, 2 each get two different words ⇒ 2-way.

K7 · An endless loop on the CPU side

void reverseCopy(const float* in, float* out, unsigned n) {
    for (unsigned i = n - 1; i >= 0; i--)
        out[n - 1 - i] = in[i];
}

What happens? And for n = 0? How does it connect to Lecture 7's advice on signed counters?

An unsigned is never < 0: i >= 0 is always true; after i = 0, i-- wraps to 232 − 1 ⇒ out-of-bounds writes, an endless loop / crash. With n = 0, i starts at 232 − 1. Fix: for (int i = (int)n - 1; i >= 0; i--). Connection: unsigned overflow is defined (it wraps); it causes this bug and also limits the compiler's optimisations. A signed counter is better on both counts.

Design and "why" questions

T1 · Sum 10⁸ elements

Compute the sum of 10⁸ floats on the GPU. Why can you not combine all blocks' results with a barrier inside one kernel? Write the steps of your design and the synchronisation in each step.

__syncthreads() is per block, and blocks run in any order, maybe not at the same time: a "grid barrier" that assumes all of them are resident can hang (cooperative groups need a special launch). Design: (1) each block sums its part as a tree in shared memory (half the threads per step, __syncthreads() between steps; with the divisor aligned to threadIdx.x / 32 there is no divergence except in the last steps); (2) the block's result goes to partial[blockIdx.x]; (3) a second kernel (or the same kernel with one block) sums partial. The kernel boundary is the barrier between blocks. Alternative: one atomicAdd per block; short, but the float result may not repeat bit for bit because the order of additions changes.

T2 · The heat equation: cluster or GPU?

On a 2D grid every cell takes the average of its 4 neighbours each step (1000 steps). Design it with PCAM for a 100-node distributed-memory cluster and for a GPU. Where is the communication, and where do the two designs differ?

P: one task per cell (geometric/data decomposition). C: 4 neighbours each step; a dependency between steps (step t+1 waits for step t). A: on the cluster 100 pieces (10×10 tiles or strips; tiles shrink the halo/interior ratio), and at the end of each step only the edge rows/columns go to the neighbour as messages. M: equal pieces, neighbouring pieces on nearby nodes. GPU: tile = block, the halo is loaded into shared memory, a step = a kernel launch (the kernel boundary is the global barrier between steps), two buffers (old/new) alternate. Difference: on the cluster communication is expensive messages ⇒ big tiles; on the GPU it is global memory traffic ⇒ coalesced rows and reuse through shared memory.

T3 · Is more occupancy always faster?

A friend cut registers from 64 to 32 with -maxrregcount and raised occupancy from 50% to 100%, but the kernel got slower. Explain two possible reasons.

(1) Register spill: values that do not fit in 32 go to local memory (DRAM); every access costs hundreds of cycles and eats the latency hiding gained. (2) If the kernel is already bandwidth bound, or 50% already gives enough warps to hide latency, extra warps gain nothing; also each warp gets less cache. Occupancy is a tool, not the goal: measure (check spills with --ptxas-options=-v).

T4 · The error on the wrong line

A program does k1<<<…>>>(); k2<<<…>>>(); cudaMemcpy(…);. cudaMemcpy returns "illegal memory access". Which kernel may be guilty, how do you find out, and why does every later call fail too?

Either: launches are asynchronous, so the error is reported by the first synchronising call (here cudaMemcpy). To find it, check cudaGetLastError() (launch error) and cudaDeviceSynchronize() (execution error) after each kernel; the one after which the error appears is guilty. Execution errors are sticky: the context is broken and every later CUDA call in the process returns the same error; the program has to restart.

Trick questions

The 32 threads of a warp read c[threadIdx.x] from __constant__ float c[64]. What happens?

  1. One request, full efficiency: consecutive addresses.
  2. A 32-way bank conflict.
  3. The request is split into 32 separate requests.
  4. A compile error: constant memory cannot be indexed by thread.

s[threadIdx.x % 16] (float, 32 banks) is read. Conflict degree?

  1. 2-way: two threads in one bank.
  2. No conflict.
  3. 16-way.
  4. 32-way.

A block has 48 threads. The SM allows 64 warps, 2048 threads, 32 blocks. Warp occupancy and the active-thread ratio?

  1. 75% and 75%
  2. 100% and 100%
  3. 50% and 75%
  4. 100% warps, 75% active threads

Which is always false?

  1. Block 0 starts before block 1.
  2. All threads of a warp are in the same block.
  3. Threads of one block run on the same SM.
  4. A kernel launch returns to the host at once.

A counting semaphore initialised to 3 lets 3 threads do a shared counter++. The result?

  1. Correct: the semaphore provides mutual exclusion.
  2. A deadlock.
  3. Still a data race: 3 threads can read-add-write at once.
  4. Correct only on x86.

A program built with -gencode arch=compute_70,code=sm_70 on an 8.6 GPU:

  1. Runs; the driver JIT-translates the sm_70 binary.
  2. Fails with "no kernel image": binaries do not cross majors, no PTX embedded.
  3. Runs but does not use Tensor Cores.
  4. A compile error.

In tiled matmul, what does going from T = 16 to T = 32 certainly change?

  1. The kernel becomes 2 times faster.
  2. The number of phases stays the same.
  3. Shared memory per block stays the same.
  4. Global reads per thread halve and threads per block grow 4 times.

notify_one() is called when no thread is waiting on a condition variable. Then a thread enters wait() (without checking a condition). What happens?

  1. The signal is lost; the thread sleeps until the next notify.
  2. The thread wakes at once: the signal was stored.
  3. A guaranteed deadlock.
  4. Undefined behaviour.

Which is true about divergence?

  1. It can give wrong results.
  2. It happens when different blocks take different branches.
  3. For short branches the compiler can remove the branch entirely with predication.
  4. if (threadIdx.x < 32) makes both warps of a 64-thread block diverge.

A speedup of 18 was measured on 16 cores (superlinear). The most likely explanation?

  1. Amdahl's law is wrong.
  2. Each core's share of the data started to fit in cache (or the serial version is not the fastest).
  3. Gustafson's law.

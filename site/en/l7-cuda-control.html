Error checking and control flow

If your kernel silently did nothing, how do you catch the error? Why does an if slow a warp down, and why does a GPU "mask" (predication) instead of "guess" (prediction)? How do loops get faster?

  • State what the forms of #pragma unroll mean and why signed loop counters are recommended.

A GPU is like a kitchen that takes the order and says "OK" right away. When you launch a kernel the CPU does not wait (asynchronous); if something goes wrong while the kernel runs, you only find out later, when you ask the kitchen "is it done?" (cudaDeviceSynchronize()). The first half of this lecture is catching errors in the right place. The second half is performance: the 32 threads of a warp share one program counter, so branches (if, for, while) must be written with care; and loops get faster with unrolling and the right counter type.

Error checking

  • All runtime functions return an error code (cudaError_t).
  • But an asynchronous function returns before the device has finished, so its error code cannot report errors that happen on the device later. It only reports errors on the host before the task starts (typically parameter validation).
  • If an asynchronous error occurs, it is reported by some subsequent, unrelated runtime call. (The error shows up "on the wrong line"!)
  • The only way to check for asynchronous errors right after an asynchronous call is to call cudaDeviceSynchronize() right after it and check its return value.

The error variable: Peek and Get

  • The runtime keeps an error variable per host thread: initially cudaSuccess, overwritten every time an error occurs (a parameter error or an asynchronous error).
  • cudaPeekAtLastError(): returns this variable (does not reset it).
  • cudaGetLastError(): returns the variable and resets it to cudaSuccess.
  • Kernel launches do not return an error code. To get pre-launch errors (such as an invalid configuration), call Peek/Get right after the launch.
  • To make sure the returned error does not come from calls before the launch, the variable must be cudaSuccess right before the launch: e.g. a cudaGetLastError() just before the launch.
  • Since launches are asynchronous, an application that wants to see asynchronous errors must synchronise between the launch and Peek/Get.
cudaGetLastError();                        // make sure the error variable is cudaSuccess before the launch
k<<<(n + 255) / 256, 256>>>(d, n);
cudaError_t l2 = cudaGetLastError();       // launch / configuration errors
cudaError_t r2 = cudaDeviceSynchronize();  // errors during execution

In a program without error checks, even a crashed kernel looks "successful" and the results are garbage; the error is only reported at the next cudaMemcpy, on an unrelated line. What the exam wants: cudaGetLastError() after the launch, then cudaDeviceSynchronize(), checking the return value of both.

Branching and divergence

  • Any flow control instruction (if, switch, do, for, while) can significantly reduce instruction throughput by making threads of the same warp diverge (follow different paths).
  • If this happens, the different paths must be serialised, because all threads of a warp share one program counter. The total number of instructions executed by the warp increases. When the paths complete, the threads converge back to the same path.
  • When control flow depends on the thread ID, the condition should be written to minimise the number of divergent warps. This is possible because the distribution of warps over the block is deterministic.
  • A trivial example: if the condition depends only on threadIdx / WSIZE (WSIZE = warp size), it is perfectly aligned with the warps and no warp diverges.

Branch predication and branch prediction

Similar names, different things: predication ≠ prediction.

CPU: branch prediction

  • Guess whether a conditional branch will be taken.
  • Start speculative execution based on the guess (instructions that may or may not be needed).
  • When the condition is evaluated, see the real result: if the guess was right, keep going; if wrong, discard the speculative work and restart with the right branch.

GPU: branch predication

  • None of the instructions that depend on the condition is skipped.
  • Each is associated with a per-thread predicate (condition code) set to true or false by the condition.
  • All are scheduled, but only those with a true predicate actually execute.
  • Instructions with a false predicate do not write results, do not evaluate addresses and do not read operands.

Predication is ideal for short branches: instead of jumping over a few-instruction branch like if (x < 0) x = -x; (a jump + draining the pipeline), the instruction is issued to everyone with a predicate and takes effect only in the threads where the condition holds. No divergence, no jump.

Branch optimisation and pipelining

  • Branch optimisations are needed because of instruction pipelining.
  • A pipeline (fetch → decode → execute → write back) raises throughput by processing several instructions in different stages at the same time.
  • A branch makes the pipeline wait until the next instruction is known, or fill it with the wrong instructions; it cuts down the gain of pipelining. CPUs soften this with prediction, GPUs with predication and by switching warps.

Loop unrolling

  • The compiler may unroll small loops with a known trip count by itself.
  • The programmer controls it with #pragma unroll. It must be placed immediately before the loop and applies only to that loop.
  • It optionally takes a number: #pragma unroll 5 unrolls the loop 5 times. The compiler adds code for correctness (e.g. so that there are only n iterations when n < 5).
  • #pragma unroll 1: the compiler never unrolls the loop.
  • Without a number: the loop is completely unrolled if its trip count is constant, otherwise not at all.
  • Choosing the best unroll number is up to the programmer. The smaller the loop body, the bigger the gain.
float s = 0;
#pragma unroll 5
for (int i = 0; i < n; ++i)
    s += in[i];

A detailed example and the costs (register pressure): Coalescing page, loop unrolling.

Loop counters: signed vs unsigned

  • Since counters are always positive, declaring them unsigned is tempting. But for slightly better performance they should be signed (int).
  • Why? Compilers can optimise signed arithmetic more aggressively. Signed overflow is undefined in C/C++, so the compiler may assume "i never overflows": instead of recomputing offset + stride*i every iteration it can advance a pointer by stride, and safely switch to 64-bit address arithmetic.
  • With unsigned, overflow is defined (it wraps around at 232); the compiler has to preserve that wrap-around possibility and cannot do some transformations.
for (int i = 0; i < n; i++) {
    out[i] = in[offset + stride*i];
}

Summary

  • Runtime calls return cudaError_t; a kernel launch does not. Asynchronous errors appear at a later call (or at cudaDeviceSynchronize()).
  • cudaPeekAtLastError() reads, cudaGetLastError() reads and resets. Pattern: clear first, launch, cudaGetLastError(), cudaDeviceSynchronize().
  • Divergence: different paths within a warp run one after the other (one program counter). Aligning the condition with threadIdx / 32 avoids divergence.
  • Predication (GPU): instructions are not skipped, they are masked with a per-thread predicate. Prediction (CPU): guessing the branch + speculative execution.
  • #pragma unroll N unrolls N times (code is added for leftover iterations); 1 does not unroll; without a number: fully unrolls a constant trip count.
  • Make loop counters int: since signed overflow is undefined, the compiler optimises more.

Common mistakes

  • Thinking "the launch returned no error, so it ran": a launch never returns an error; execution errors come later.
  • Calling cudaGetLastError() twice and expecting the error the second time too: the first call resets it.
  • Mixing up predication and prediction, or counting different warps taking different branches as divergence.
  • Writing #pragma unroll a few lines before the loop: it must be immediately before it.

Open-ended questions for the quiz

1. Complete the unchecked call k<<<g, b>>>(…);. What is the difference between Peek and Get?

First clear/check earlier errors (cudaGetLastError()), launch, cudaError_t launch = cudaGetLastError(); (configuration/parameter errors), then cudaError_t run = cudaDeviceSynchronize(); (execution errors); if either is not cudaSuccess, report and stop. Get reads and resets, Peek does not reset.

2. In a 128-thread 1D block, how many warps diverge for if (threadIdx.x < 40) and for if (threadIdx.x % 4 == 0)?

< 40: warp 0 all true, warp 1 (32–63) mixed, warps 2–3 all false → 1. % 4 == 0: 8 true, 24 false in every warp → 4 (all).

3. How is predication different from prediction? Why is #pragma unroll 4 not always faster?

Prediction (CPU) guesses the branch and executes speculatively, rolling back if wrong. Predication (GPU) does not skip instructions; it masks them with a per-thread predicate, and false ones neither write results nor read operands. Unrolling reduces loop control but increases code size and register usage; register spills or lower occupancy can erase the gain.

4. A program reports "illegal memory access" at a cudaMemcpy call, but the cudaMemcpy parameters are correct. Why?

The error most likely happened in the previous kernel (asynchronously). A kernel launch returns no error; the error was reported at the next unrelated call, here the cudaMemcpy. Checking the return value of cudaDeviceSynchronize() right after the kernel shows the error in the right place.

Check yourself

Which error does cudaGetLastError() catch right after a kernel launch?

  1. An out-of-bounds access inside the kernel.
  2. None; a kernel launch produces no errors.
  3. Pre-launch errors such as an invalid configuration.
  4. The errors of the next cudaMemcpy.

The difference between cudaPeekAtLastError() and cudaGetLastError()?

  1. Peek reads the device's error, Get the host's.
  2. Peek does not reset the variable, Get does.
  3. Peek synchronises, Get does not.
  4. There is no difference.

Which is true of the GPU's branch predication?

  1. It guesses the branch outcome and executes speculatively.
  2. The instructions of threads whose condition is false are skipped.
  3. Instructions with a false predicate read operands but do not write results.
  4. Each instruction is associated with a per-thread predicate; only true ones execute.

What does #pragma unroll without a number do?

  1. Fully unrolls the loop if its trip count is constant, otherwise not at all.
  2. Unrolls the loop 4 times.
  3. Prevents the loop from being unrolled.
  4. Unrolls every loop in the file.

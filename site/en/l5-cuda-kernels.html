Data parallelism: from loop to kernel

Data parallelism: the same operation performed on independent data elements simultaneously (vector addition, convolution, matrix-vector and matrix-matrix multiplication). Rule of thumb: when you see nested for loops with regular indexing, there is a good chance of parallelisation.

for (int i = 0; i < N; i++)
    C[i] = A[i] + B[i];

__global__ void VecAdd(float* A, float* B, float* C) {
    int i = threadIdx.x;
    C[i] = A[i] + B[i];
}
// VecAdd<<<1, N>>>(A, B, C);   // 1 block, N threads

for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        C[i*N + j] = A[i*N + j] + B[i*N + j];

__global__ void MatAdd(float* A, float* B, float* C) {
    const int i = threadIdx.y * blockDim.x + threadIdx.x;
    C[i] = A[i] + B[i];
}
// dim3 threadsPerBlock(N, N);
// MatAdd<<<1, threadsPerBlock>>>(A, B, C);

Matrix multiplication: the CPU version

void MatrixMultiplication(float* M, float* N, float* P, int width) {
    for (int i = 0; i < width; ++i)
        for (int j = 0; j < width; ++j) {
            float sum = 0;
            for (int k = 0; k < width; ++k)
                sum += M[i*width + k] * N[k*width + j];
            P[i*width + j] = sum;
        }
}

Start from the output: one output element = one dot product = one for loop, and neighbouring output elements are independent. So each thread can compute one P[i][j]; the two outer loops become threads, the inner k loop stays inside the thread.

The host side: allocate, copy, launch

The GPU is a coprocessor: we offload parallel work to it, copy the result back and continue. The kernel is the actual GPU code; the rest is set-up, executed by the host (CPU).

void cuMatrixMultiplication(float* M, float* N, float* P, int width)
{
    int size = width * width * sizeof(float);
    float *Md, *Nd, *Pd;
    // 1. allocate device memory
    cudaMalloc((void**)&Md, size);
    cudaMalloc((void**)&Nd, size);
    cudaMalloc((void**)&Pd, size);
    // 2. copy the inputs to the device
    cudaMemcpy(Md, M, size, cudaMemcpyHostToDevice);
    cudaMemcpy(Nd, N, size, cudaMemcpyHostToDevice);
    // 3. launch the kernel
    dim3 dimBlock(TILE_WIDTH, TILE_WIDTH);
    dim3 dimGrid(width / TILE_WIDTH, width / TILE_WIDTH);
    MatMulKernel<<>>(Md, Nd, Pd, width);
    // 4. copy the result back to the host
    cudaMemcpy(P, Pd, size, cudaMemcpyDeviceToHost);
    // 5. free device memory
    cudaFree(Md); cudaFree(Nd); cudaFree(Pd);
}
  • cudaMalloc(void** devPtr, size_t size): the first parameter is the address of the pointer variable (the function writes the allocated address there), cast to (void**) because the function is type-agnostic. The second parameter is the size in bytes (like C's malloc).
  • cudaFree(void* devPtr): frees what cudaMalloc allocated.
  • cudaMemcpy(dst, src, bytes, kind): kind is cudaMemcpyHostToHost / HostToDevice / DeviceToDevice / DeviceToHost. It is synchronous (blocking, does not return until done); asynchronous versions exist.
  • A kernel launch, in contrast, is asynchronous: when timing, wait for it with cudaDeviceSynchronize() (L6).

The slide's float* Md, Nd, Pd; line makes only Md a pointer in C (Nd, Pd become plain floats). The correct form is float *Md, *Nd, *Pd;. Watch out when writing code in the exam.

Kernels and function qualifiers

A kernel specifies the code executed by all threads. SIMT (Single Instruction Multiple Threads): threads see the same instruction, but its parameters come from each thread's own registers, so different threads can do different work. threadIdx lets a thread distinguish itself and direct itself to its part of the data (predefined variables read from hardware registers).

QualifierExecuted onCallable from

Without a qualifier the function defaults to __host__. __global__ means a kernel, returning void.

__global__ void MatMulKernel(float* Md, float* Nd, float* Pd, int width)
{
    int tx = threadIdx.x;
    int ty = threadIdx.y;
    float sum = 0;
    for (int i = 0; i < width; i++)
        sum += Md[ty * width + i] * Nd[i * width + tx];
    Pd[ty * width + tx] = sum;
}
// dim3 blockDim(width, width); dim3 gridDim(1, 1);

Where are the loops? The outer i and j loops are gone: ty (row) and tx (column) replaced them. The dot-product loop remains.

Its problem: it uses only one block, so the matrix can have at most as many elements as the threads-per-block limit (512 on old GPUs → 16×16; 1024 on newer ones → 32×32). Even with more blocks, threads in different blocks with the same threadIdx would compute the same Pd element, because blockIdx is not used.

Thread blocks and indexing

  • When a kernel is launched it executes as a grid of parallel threads (thousands to millions of lightweight threads).
  • Two-level hierarchy: grid → one or more thread blocks; all blocks of a grid have the same number of threads. Each block has a blockIdx coordinate (2D on compute 1.x, 3D on 2.0+).
  • Each block is a 3D array of up to 512 (compute 1.x) / 1024 (2.0+) threads; a thread's coordinate within the block is threadIdx.
  • 1D example (slides 31–33): N blocks of M threads → N·M threads. Thread 3 of block 0: 0·M + 3; thread 3 of block 5: 5·M + 3. In general: blockIdx.x * blockDim.x + threadIdx.x.
  • Input and output mappings can differ: read data with one mapping, process with another, write with a third (different input/output data rates, shared memory preparation, boundary conditions).
__global__ void MatMulKernel(float* Md, float* Nd, float* Pd, int width)
{
    int row = blockIdx.y * TILE_WIDTH + threadIdx.y;
    int col = blockIdx.x * TILE_WIDTH + threadIdx.x;
    float sum = 0;
    for (int i = 0; i < width; i++)
        sum += Md[row * width + i] * Nd[i * width + col];
    Pd[row * width + col] = sum;
}

Here TILE_WIDTH = blockDim.x = blockDim.y. Try your own configuration: lab.

The questions of slide 40. (1) Can we enforce an execution order on blocks? No. (2) Can we assume a block with a smaller ID starts before one with a larger ID? No. (3) How does this relate to scalability? Because blocks are independent, the runtime can distribute them to any SM in any order (round-robin); the same program runs on a 2-SM GPU and on an 80-SM GPU.

Limits to take into account: maximum threads per block, maximum blocks per SM, maximum threads per SM. Generally aim for as many resident threads on the SMs as possible (occupancy).

Synchronisation: __syncthreads()

  • Threads in the same block coordinate their activities with barrier synchronisation. Every calling thread is held at that point until all threads of the block reach it. This ensures everyone has finished one phase before anyone moves on. Typical example: filling shared memory.
  • Real life: four people carpooling to work. They work in parallel at their desks; when leaving, everybody waits until all four are back at the car (barrier).
  • It must be executed by all threads of the block. Using it in if/else is undefined behaviour; the only exception is when the condition evaluates the same for all threads of the block.
  • It actually synchronises warps, not threads.
  • To keep waiting times short, the runtime assigns all threads of a block to the same SM together.
  • Synchronising across blocks was almost impossible before CUDA 9 (hacks with __threadfence(), which halts a thread until its previous shared/global writes are visible to others). With CUDA 9 (Pascal): cooperative groups.

Block assignment, warps, latency hiding

  • When a kernel starts, the runtime creates the grid; threads are assigned to SMs block by block. GT200: 30 SMs, at most 8 blocks per SM → 240 blocks at once; a finished block is replaced by a new one from the list.
  • The number of threads an SM can track is limited too: 1024 per SM on the GT200 (e.g. 4 × 256 or 8 × 128) → 30 · 1024 = 30,720 resident threads.
  • Warp: 32 threads with consecutive threadIdx; the unit of scheduling on an SM. Threads 0–31 are the first warp, 32–63 the second… The mapping is deterministic. A 256-thread block = 8 warps; 3 blocks on an SM = 24 warps.
  • "You don't need to know about warps to write CUDA code; you DO need to know about them to write high-performance CUDA code."
  • Latency hiding: a warp waiting for the result of a long-latency operation (global memory access, pipelined FP arithmetic, branches) is not selected; another ready warp runs instead. The selection adds no idle time: zero-overhead thread scheduling. With enough warps the hardware always finds one to run.
  • That is why GPUs do not devote as much area to large caches and branch prediction as CPUs; they give that area to FP units.

Matmul block size for the GT200 (1024 threads/SM, 8 blocks/SM, 512 threads/block):

  • 8×8 = 64 threads → filling the SM would need 16 blocks but the limit is 8 → 8·64 = 512 threads: resources half idle, few warps to hide latency.
  • 16×16 = 256 threads → 1024/256 = 4 blocks (under the limit of 8) → full capacity ✓.
  • 32×32 = 1024 threads → exceeds the limit of 512 per block ✗.

Result: 16×16. (No shared memory yet; with it the calculation gets more complicated.)

Memory access efficiency: CGMA

  • The simple kernel reaches only a small fraction of the hardware's potential: threads repeatedly load overlapping input data from global memory.
  • Global memory = DRAM: hundreds of clock cycles of latency, limited bandwidth. Latency hiding helps, but not if everyone accesses global memory all the time.
  • CGMA (compute to global memory access): the number of FP operations per global memory access in a region. The matmul inner loop does 2 global reads and 1 multiply + 1 add per iteration → CGMA = 1.
G80: 86.4 GB/s global bandwidth 86.4 / 4 B = 21.6 billion floats/s can be loaded CGMA = 1 → at most 21.6 GFLOPS Peak 367 GFLOPS → 21.6 / 367 ≈ 6% CGMA must be raised for higher performance.

  • A __constant__ declaration must be outside any function body; its scope is all grids, its lifetime the whole application. Often used for input values to kernels.

Tiling with shared memory

The basic trade-off: global memory is large but slow, shared memory small but fast. Strategy: partition the data into tiles that each fit in shared memory; the computations on tiles must be doable independently. (Not every data structure can be tiled for every kernel.)

Overlapping accesses

The small example in the slides: P computed by four 2×2 blocks. The four threads of block (0,0) compute Pd0,0, Pd1,0, Pd0,1, Pd1,1. Each thread reads 4 elements of Md and 4 of Nd, and thread(0,0) and thread(1,0) both read all of row 0 of Md. During block (0,0) every Md and Nd element is read exactly twice: if the threads cooperate to load each element once, global traffic halves.

In general: with N×N blocks the possible reduction is N times. 16×16 → global traffic 1/16.

16×16 block, NO shared memory: 16·16 threads × (width + width) reads = 16·16·2·width 16×16 block, WITH shared memory: each element read once = 16·width·2 Ratio: (16·16·2·width) / (16·width·2) = 16

Slides 86 and 88: "What about 16×8?", "1024×1024 matrices, 32×8 blocks?" A BX×BY block computes a BY-row × BX-column tile of P. Without shared memory the block does BX·BY·2·width reads; with tiles it reads BY·width from M and BX·width from N. Reduction = 2·BX·BY / (BX + BY). 16×8: 256/24 ≈ 10.7×. 32×8: 512/40 = 12.8× (independent of the matrix size). For a square T×T it equals T.

The tiled kernel

Threads cooperatively load Md and Nd elements into shared memory, then use them in their dot products. Since shared memory is small, Md and Nd are divided into tiles that fit, and the dot product is split into phases: in phase m each thread loads one element from the M tile and one from the N tile.

__global__ void MatrixMulKernel(float* Md, float* Nd, float* Pd, int width)
{
    __shared__ float Mds[TILE_WIDTH][TILE_WIDTH];
    __shared__ float Nds[TILE_WIDTH][TILE_WIDTH];
    int bx = blockIdx.x, by = blockIdx.y;
    int tx = threadIdx.x, ty = threadIdx.y;
    int Row = by * TILE_WIDTH + ty;     // this thread's row of P
    int Col = bx * TILE_WIDTH + tx;     // this thread's column of P
    float Pvalue = 0;
    for (int m = 0; m < width / TILE_WIDTH; ++m) {           // phase loop
        Mds[ty][tx] = Md[Row * width + (m * TILE_WIDTH + tx)];   // M[Row][m*T + tx]
        Nds[ty][tx] = Nd[(m * TILE_WIDTH + ty) * width + Col];   // N[m*T + ty][Col]
        __syncthreads();                                      // (1) tiles filled
        for (int k = 0; k < TILE_WIDTH; ++k)
            Pvalue += Mds[ty][k] * Nds[k][tx];
        __syncthreads();                                      // (2) everyone done using them
    }
    Pd[Row * width + Col] = Pvalue;
}
  • Loading M: row Row fixed (the thread's row), column m*T + tx: column tx of the tile in phase m. tx is consecutive within a warp → coalesced.
  • Loading N: row m*T + ty, column Col: row ty of the tile in phase m. Again tx (inside Col) is on the right → coalesced.
  • Computing: Mds[ty][k] = element k of the P row, Nds[k][tx] = element k of the P column. In total width/T phases × T terms = width terms, as in the CPU version.
  • Why two barriers? (1) After the writes: Mds[ty][k], Nds[k][tx] loaded by other threads will be read; not before the tile is full. (2) After the computation: the next phase overwrites Mds/Nds; a fast thread must not write while others are still reading.
  • Global reads per thread: naive 2·width, tiled 2·width/T → T times fewer. This code assumes width is a multiple of TILE_WIDTH.

Check yourself

Why is &Md passed in cudaMalloc((void**)&Md, size)?

  1. Because Md will be allocated in host memory.
  2. To give the size in bytes.
  3. So that the function can write the allocated address into the variable Md.
  4. To copy data into Md.

With 256-thread blocks and 3 blocks on an SM, how many warps are on the SM?

  1. 8
  2. 24
  3. 768
  4. 32

Why is the CGMA ratio of naive matmul 1?

  1. There is one FP operation per shared memory access.
  2. Each thread reads one element.
  3. Each thread uses one register.
  4. Each iteration does 2 global reads and 2 FP operations (multiply, add).

What can happen if the second __syncthreads() in the tiled kernel is removed?

  1. A thread may load the next phase's tile while another thread is still reading the previous phase's values.
  2. A compile error.
  3. The write to Pd is no longer coalesced.
  4. Nothing; the second barrier is unnecessary.

Which is true for __constant__ variables?

  1. They live in a separate on-chip memory, no cache needed.
  2. They are declared inside the kernel.
  3. All grids see the same version; stored in global memory but cached.
  4. Kernels can write to them.

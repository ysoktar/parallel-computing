GPU memory: one picture and its limits

Instead of memorising the memory types one by one, we place them on a single map; then we look at how their limited size decides how many threads can run on an SM at once.

  • Place each memory with three questions (where is it, who sees it, how should it be accessed).
  • Say which memory each variable of a kernel lives in.
  • Compute blocks and threads per SM from the register and shared-memory limits.

Three questions, one memory map

Instead of memorising the memory types one by one, let us place them in a structure using three questions. Every memory type is a combination of answers to these three questions:

  1. Where is it physically? On the chip (on-chip: registers, shared memory, caches) or off the chip in DRAM (global, local, and the data of constant and texture memory)? On-chip is fast and small, DRAM is large and slow (hundreds of cycles).
  2. Who sees it, and how long does it live? One thread (register, local), one block (shared), or the whole grid and the host (global, constant, texture).
  3. For speed, how should the warp's 32 threads access it? Each memory has its own "rule"; speed depends on following it.

The same s[2*tid] pattern means "50% efficiency" (twice the segments) in global memory, a "2-way bank conflict" in shared memory and "32 separate requests" in constant memory. Coalescing, bank conflicts and broadcast are not separate topics; they are the answers, in different memories, to the same question: how do a warp's 32 addresses fall on this memory?

One kernel, every memory

In the kernel below the comments say which memory each variable lives in. While reading, ask on every line "where is this data, who sees it?".

__constant__ float coef[4];                     // CONSTANT: the whole grid sees it, only the host writes
__device__ float total;                         // GLOBAL: the whole grid + the host

__global__ void tour(const float* in, float* out, int n, int k)
{
    __shared__ float tile[256];                 // SHARED: the block's 256 threads see the same array
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // REGISTER: every thread has its own i
    float acc = 0.0f;                           // REGISTER
    float hist[64];                             // may be LOCAL: large, indexed at run time
    for (int j = 0; j < 64; j++) hist[j] = j;

    tile[threadIdx.x] = (i < n) ? in[i] : 0.0f; // GLOBAL read (consecutive i → coalesced) → SHARED write
    __syncthreads();                            // everyone must have written before shared memory is used
    float left = tile[(threadIdx.x + 255) % 256];    // SHARED read: a value another thread wrote
    acc = coef[0] * tile[threadIdx.x] + coef[1] * left + hist[k & 63];   // CONSTANT: same address for all → broadcast
    if (i < n) out[i] = acc;                    // GLOBAL write (coalesced)
    if (i == 0) total = acc;                    // GLOBAL
}

Which memory for which data?

When placing data, ask the questions in this order:

  1. Is it used by one thread only? If it is a small scalar → register (automatic). If it is a large or variable-indexed array, the compiler puts it in local memory (slow): try to shrink it or index it with constants (unrolling).
  2. Do the block's threads reuse the same data again and again? → load it into shared memory once, __syncthreads(), then everyone reads from there (tiling). Spread the accesses over different banks.
  3. Is it read-only, with everyone in the warp reading the same value at the same time? (filter coefficients, constant parameters) → constant.
  4. Is it read-only, local in 2D, with fractional coordinates or edge handling needed? (rotating, scaling an image) → texture.
  5. None of these (large input/output arrays) → global; make the accesses coalesced, use a pitch in 2D.

Read tiled matmul through this lens: M, N, P are in global memory (large, everyone sees them; the loads are coalesced). The tiles Mds, Nds are in shared memory (16 threads of the block use the same element). Row, Col, Pvalue are in registers (private to the thread). The barrier is the price of sharing shared memory. The pieces of this picture are detailed on 6.3 (global, local, shared, constant) and 6.4 (texture).

Memory limits and their effects

  • The register limit directly affects the number of threads that can run at high performance (without spills).
  • The shared memory limit directly affects the number of blocks that can reside on an SM (and indirectly the number of threads).
  • Bottom line: the more memory each thread needs, the fewer threads fit on an SM (and on the whole processor).

G80: 16 SMs, 8K = 8192 registers per SM → 128K = 131,072 in total. Sounds like a lot, but to fill 768 threads per SM each thread can use only 8192/768 ≈ 10 registers.

Register spill: if the compiled code uses more than (max registers / number of threads), the kernel still runs but the excess goes to local memory (= global memory, private per thread) → performance hit. To see the register count: --ptxas-options=-v.

Shared: 16 KB per SM on the G80, at most 8 blocks → ≤ 2 KB per block to reach the maximum. Using more than 2 KB, the number of blocks on an SM is such that the total does not exceed 16 KB.

Matmul: 16×16 tiles → Mds 16·16·4 = 1 KB + Nds 1 KB = 2 KB/block → 8 blocks fit (the G80 limit anyway). But the real limit is 768 threads per SM: 768 / 256 = 3 blocks → only 3·2 = 6 KB of shared memory used. All these limits are device-dependent.

Architecture list (~20 types as of 2023): Tesla (1.0, 1.1), Fermi (2.0, 3.0), Kepler (3.0, 3.5, 3.7), Maxwell (5.0, 5.2, 5.3), Pascal (6.0, 6.1, 6.2), Volta (7.0, 7.2), Turing (7.5), Ampere (8.0, 8.6, 8.7), Lovelace (8.9). Memory behaviour is device-dependent: always know the characteristics of the device you are using.

Parallel program design

In a parallel program the order of statements is not unique; without careful design, erroneous updates and blocked communications creep in. The goals: correctness and performance.

  • State the four PCAM steps and each step's rule of thumb.
  • Choose a suitable decomposition pattern for a problem.
  • Tell GPLS and GSLP program structure patterns apart.

Ask first: is parallel necessary and achievable?

  • The algorithm may not allow a parallel implementation; time/engineering resources may be missing.
  • Parallel execution may need a completely new algorithm. GPUs impose so many restrictions on program structure that a complete redesign is typical.

PCAM

Partitioning, Communication, Agglomeration, Mapping: Ian Foster's (1995) four-step design method. Roughly: find pieces of work that can run concurrently, assign them to processors with their communication needs in mind.

StepWhat happensRule of thumb
PartitioningBreak the computation into as many pieces as possible; bring out the parallelism. Functional decomposition (by steps) or domain/data decomposition (by data).Number of pieces 10–100 times the number of nodes.
CommunicationDependencies between tasks and the volume of data to pass are determined → the task dependency graph (node = task, edge = communication volume).Ideal: totally independent tasks.
AgglomerationGroup tasks to reduce communication; communication within a group disappears.Number of groups ~10 times the number of nodes.
MappingAssign the groups to nodes: load balance + reduce communication by putting heavily communicating groups on the same node (communication over shared memory is virtually free).NP-complete in general → heuristics.

Duplicating computations can improve performance by removing the need to communicate their results. Examples: matrix addition (fully independent), 2D convolution (needs neighbour data).

Decomposition patterns

The six patterns of Mattson et al.; functional and data decomposition are joined by data flow decomposition. There is no strict separation; a problem can be decomposed in several ways.

Task parallelism

Modules on different nodes: e.g. a game loop's readUserInput, drawScreen, playSounds, strategize as separate tasks, with a barrier() at the end of each iteration. Works without complex dependencies but does not scale: the number of nodes cannot exceed the number of tasks.

Divide-and-conquer

DnC(A) {
    if (A is a base case) return solution(A);
    split A into N subproblems B[N];
    for (int i = 0; i < N; i++) sol[i] = DnC(B[i]);
    return mergeSolution(sol);
}
  • Example: merge sort. The dependency graph is not the call graph. For an 8-element merge sort the maximum concurrency is 4 tasks (size-1 calls do no work).
  • Tasks are generated dynamically at run time (long impossible on GPUs). Generation stops at a given size or at the number of processors; the parent can solve one subproblem itself instead of idling (N − 1 new tasks).

Geometric decomposition

Arrays/matrices are split along one or more dimensions and assigned to tasks. With no dependencies between data: embarrassingly parallel. Example: the 5-point Laplace filter [0 1 0; 1 −4 1; 0 1 0]: each output needs 5 values → neighbour (halo) rows are needed at region borders. This is the block/tile approach on GPUs.

Recursive data decomposition

Trees, lists, graphs are decomposed into elements assigned to nodes; the algorithm may be modified (similar to dynamic programming). Example: partial sums (prefix sum) S[i] = S[i−1] + A[i]: sums of groups of 2, then 4, then 8.

Pipeline

  • An assembly line: each stage applies an operation to an item. CPU instruction pipelines, signal processing (FFT → coefficient manipulation → inverse FFT), graphics pipelines, Unix shell pipes.
  • A benefit only if the stages run concurrently on different items. Stage durations should be close: the slowest stage dictates the pipeline's speed (throughput ≤ 1 / longest stage duration).

Event-based coordination

The communication flow is not fixed; tasks interact dynamically at run time; the execution profile cannot be known in advance. Example: discrete-event simulation (event = time-stamped message).

Program structure patterns

GPLS (Globally Parallel, Locally Sequential): many tasks concurrently, each sequential.

  • SPMD
  • MPMD
  • Master-worker
  • Map-reduce

GSLP (Globally Sequential, Locally Parallel): the program runs sequentially, requested parts in parallel.

  • Fork/join
  • Loop parallelism
PatternEssence
SPMDAll nodes run the same program; different data and/or different paths. Steps: initialisation → obtain a unique ID (a vector in CUDA: blockIdx/threadIdx) → run according to the ID → shut down and combine results. CUDA and MPI follow this pattern.
MPMDWith a heterogeneous platform or tight memory, different programs are assembled into one application.
Master-workerThe master hands out work, collects results, does I/O and user interaction. A single master can be a bottleneck → hierarchical masters. Feeding idle workers gives implicit load balancing.
Map-reduceA master-worker derivative (Google). Apply a function to independent data (map), combine partial results with a second function (reduce). Automated tools handle deployment and load balancing.
Fork/joinTasks are created dynamically at run time (fork) and finish before the parent resumes (join). New threads or a thread pool (reduces creation overhead).
Loop parallelismParallelise the loops that dominate an existing sequential code (OpenMP directives). Little effort, usually small gains.

Platforms impose patterns: MPI → SPMD/MPMD, OpenMP → loop parallelism, CUDA → SPMD (every thread the same kernel, different IDs).

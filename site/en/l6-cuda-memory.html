Compilation and memory types

How does a .cu file become code that runs on the GPU, and on which GPUs does it run? And when and how is each memory type (register, local, shared, global, constant, texture) used? The coalescing part of Lecture 6 is on its own page.

  • Say which code is loaded on which GPU from a -gencode line.

Programming interface: runtime and driver API

  • CUDA C++ = a minimal set of extensions to C++ + a runtime library. Any source file containing these extensions must be compiled with nvcc (NVIDIA CUDA Compiler).
  • Runtime API (starts with cuda, e.g. cudaMalloc()): host functions to allocate/free device memory, copy between host and device, manage multiple devices. Built on top of the lower-level driver API (starts with cu, e.g. cuMemAlloc()).
  • The driver API gives extra control: CUDA contexts (the analogue of host processes for the device) and CUDA modules (the analogue of dynamically loaded libraries). Kernel launches are more laborious (configuration and parameters via explicit calls), but modules can be loaded and unloaded as needed; it is language-independent (deals only with cubin objects).
  • The runtime API does initialisation, context and module management implicitly → shorter code, less control. Most applications use the runtime API; the two can be mixed when needed.
  • Primary context: the runtime creates one per device per process (reference-counted), shared by all runtime users in the process. Synchronised with cudaDeviceSynchronize(), destroyed with cudaDeviceReset(). Trap: if one plug-in in a process calls cudaDeviceReset(), the others' context is destroyed without their knowledge.
  • A context has its own address space: the same pointer value in different contexts refers to different memory locations.

Compiling with nvcc

  • Kernels can also be written in the CUDA instruction set architecture PTX (Parallel Thread Execution), analogous to assembly; C++ is usually more effective. Either way kernels must be compiled to binary code by nvcc.
  • Offline compilation: nvcc separates host and device code; compiles device code to PTX and/or binary cubin; replaces the <<<…>>> syntax in host code with runtime calls that load and launch the kernel. The modified host code is output as C++ or, by invoking the host compiler, as object code.
  • JIT (just-in-time) compilation: PTX loaded by an application at run time is compiled to binary by the driver. It increases load time but benefits from compiler improvements in new drivers, and is the only way to run on devices that did not exist when the application was compiled. The result is kept in the compute cache, invalidated when the driver is upgraded. Alternative: NVRTC (C++ → PTX at run time).

The compilation chain (on the board): .cu (C/C++) → nvcc front end → PTX (virtual ISA, text) → ptxas → SASS (real machine code for a specific sm_XY; inside the cubin). PTX is the portable intermediate language, SASS is architecture-specific. To see the intermediate files: nvcc -keep or -ptx; to see SASS: cuobjdump -sass; register count: --ptxas-options=-v.

Compatibility

  • Binary (cubin) compatibility: a cubin is architecture-specific; -code=sm_80 produces code for compute capability 8.0. A cubin for X.y runs only on X.z devices with z ≥ y: forward within the same major; not backward or across majors. (Desktop only; not on Tegra.)
  • PTX compatibility: some PTX instructions exist only on higher compute capabilities (e.g. warp shuffle 5.0+). -arch sets the compute capability assumed when compiling C++ → PTX (always give it for maximum performance). PTX for a given compute capability can always be compiled to binary of equal or greater capability. But a binary compiled from older PTX cannot use newer hardware features (e.g. a Volta 7.0 binary from Pascal 6.0 PTX does not use Tensor Cores).
  • Application compatibility: to run on future architectures (for which no binary can be generated yet), an application must contain PTX to be JIT-compiled.
nvcc x.cu -gencode arch=compute_50,code=sm_50
          -gencode arch=compute_60,code=sm_60
          -gencode arch=compute_70,code=\"compute_70,sm_70\"

For architecture-specific code paths, the __CUDA_ARCH__ macro: defined only in device code; equal to 800 with -arch=compute_80.

Initialisation and timing

  • Since CUDA 12.0, cudaInitDevice() and cudaSetDevice() initialise the runtime and the device's primary context. Without them the runtime uses device 0 and initialises itself on the first API call (that call is slow, and its error code comes from there). Before 12.0: cudaFree(0) to isolate initialisation.
  • When the context is created, device code is JIT-compiled if necessary and loaded into device memory.
  • The GPU is a coprocessor; the CPU boots the OS, "the CPU runs the show".
  • When timing: (1) the GPU must already be initialised (no cold runs), (2) the code must have finished. Kernel launches are asynchronous: call cudaDeviceSynchronize() after the kernel and before taking the time. (Otherwise you measure "miraculously short" times.) Example: texRotate.cu times kernel + cudaDeviceSynchronize() in each of 100 repetitions and averages.

Memory limits and their effects

  • The register limit directly affects the number of threads that can run at high performance (without spills).
  • The shared memory limit directly affects the number of blocks that can reside on an SM (and indirectly the number of threads).
  • Bottom line: the more memory each thread needs, the fewer threads fit on an SM (and on the whole processor).

G80: 16 SMs, 8K = 8192 registers per SM → 128K = 131,072 in total. Sounds like a lot, but to fill 768 threads per SM each thread can use only 8192/768 ≈ 10 registers.

Register spill: if the compiled code uses more than (max registers / number of threads), the kernel still runs but the excess goes to local memory (= global memory, private per thread) → performance hit. To see the register count: --ptxas-options=-v.

Shared: 16 KB per SM on the G80, at most 8 blocks → ≤ 2 KB per block to reach the maximum. Using more than 2 KB, the number of blocks on an SM is such that the total does not exceed 16 KB.

Matmul: 16×16 tiles → Mds 16·16·4 = 1 KB + Nds 1 KB = 2 KB/block → 8 blocks fit (the G80 limit anyway). But the real limit is 768 threads per SM: 768 / 256 = 3 blocks → only 3·2 = 6 KB of shared memory used. All these limits are device-dependent.

Architecture list (~20 types as of 2023): Tesla (1.0, 1.1), Fermi (2.0, 3.0), Kepler (3.0, 3.5, 3.7), Maxwell (5.0, 5.2, 5.3), Pascal (6.0, 6.1, 6.2), Volta (7.0, 7.2), Turing (7.5), Ampere (8.0, 8.6, 8.7), Lovelace (8.9). Memory behaviour is device-dependent: always know the characteristics of the device you are using.

Global memory

Four key points for efficient access (slide 35):

  1. Coalesce your accesses.
  2. Watch for byte alignment (pitched accesses).
  3. Read/write in large batches.
  4. Use shared memory.

Details, segment calculations, pitch and the transpose: Coalescing page. In short: cudaMalloc addresses are aligned to at least 256 bytes; but in a 2D array the start of the next row depends on the width, so cudaMallocPitch/cudaMalloc3D pad the rows and return a pitch. An instruction accessing addressable memory (global, local, shared, constant, texture) may have to be re-issued several times depending on the distribution of addresses across the warp.

cudaExtent extent = make_cudaExtent(width * sizeof(float), height, depth);
cudaPitchedPtr devPitchedPtr;
cudaMalloc3D(&devPitchedPtr, extent);

__global__ void MyKernel(cudaPitchedPtr devPitchedPtr, int width, int height, int depth) {
    char* devPtr = (char*)devPitchedPtr.ptr;
    size_t pitch = devPitchedPtr.pitch;
    size_t slicePitch = pitch * height;
    for (int z = 0; z < depth; ++z) {
        char* slice = devPtr + z * slicePitch;
        for (int y = 0; y < height; ++y) {
            float* row = (float*)(slice + y * pitch);
            for (int x = 0; x < width; ++x) { float element = row[x]; }
        }
    }
}

Local memory

  • Only some automatic variables go to local memory: (1) arrays the compiler cannot determine are indexed with constants, (2) large structs/arrays that would consume too many registers, (3) any variable if the kernel uses more registers than available (register spilling).
  • In PTX (-ptx or -keep) it is declared with .local and accessed with ld.local/st.local. Later compilation phases may still decide otherwise: inspect the cubin with cuobjdump; --ptxas-options=-v reports total local usage (lmem). Some math functions may use local memory too.
  • It resides in device memory: as high latency and low bandwidth as global, same coalescing rules. But it is organised so consecutive 32-bit words go to consecutive thread IDs: fully coalesced if all threads of a warp access the same relative address (same array index, same struct member). 5.x onwards: cached in L2.

Shared memory

  • On-chip; much higher bandwidth and much lower latency than local/global.
  • Its use comes with synchronisation (__syncthreads()). The amount used directly affects the number of blocks per SM.
  • Unlike global memory access, a shared memory access does not cause another ready warp to run to hide the delay.
  • Usage and tiled matmul: L5.

Banks and bank conflicts final

Announcement: "Shared memory bank optimization is not included in this exam." A short summary for reference:

  • For high bandwidth, shared memory is divided into 32 banks of equal size that can be accessed simultaneously; consecutive 4-byte (8-byte on newer architectures) chunks are assigned to consecutive banks.
  • n addresses falling in n distinct banks are served simultaneously. If two addresses fall in the same bank: a bank conflict, the request is split into conflict-free parts and serialised (n-way conflict → throughput / n).
  • Stride 1 and stride 3 (odd) are conflict-free; stride 2 is a two-way conflict. Threads reading the same word do not conflict (broadcast).
  • Fix: padding (e.g. tile[32][33]).

L2 cache control

If a kernel accesses a global memory region repeatedly those accesses are persisting; if only once, streaming. With CUDA 11.0 and compute capability 8.0+, a portion of L2 can be set aside for persisting accesses; normal/streaming accesses use that portion only when it is unused.

Constant memory

  • Resides in device memory (global), cached in the read-only constant cache.
  • A request is split into as many separate requests as there are different addresses in it (throughput drops accordingly); served at constant-cache speed on a hit, at device-memory speed otherwise.
  • Best scenario: all threads read the same address (the opposite of global memory, where consecutive addresses are good).
__constant__ float constData[256];          // outside any function
float data[256];                             // host-side buffer
cudaMemcpyToSymbol(constData, data, sizeof(data));   // copy before the kernel launch

Texture memory not on midterm 2

Texture memory is not in the scope of midterm 2. This section is for reference and later.

  • A subset of the texturing hardware the GPU uses for graphics. Textures are read-only; a surface is like a texture that can be written.
  • Resides in device memory, cached in the texture cache: a fetch costs a device memory read only on a cache miss. The cache is optimised for 2D spatial locality: a warp reading addresses close together in 2D gets the best performance. Designed for streaming with constant latency: a hit reduces DRAM traffic, not latency.
  • Benefits: higher bandwidth for reads that do not follow global/constant access patterns but have locality; addressing done outside the kernel by dedicated units (fewer registers); packed data broadcast to separate variables in one operation; optional conversion of 8/16-bit integers to floats in [0, 1] / [-1, 1]; free linear filtering and out-of-bounds handling.
  • Drawbacks: cannot be written; linear memory must be copied to a CUDA array for texturing, which takes time: the following computation should be worth it.

Texture object

Reading a texture is called a texture fetch; each fetch takes a texture object, which specifies:

CUDA arrays: opaque (no direct access to values) 1D/2D/3D memory layouts optimised for texture fetching; elements with 1, 2 or 4 components (8/16/32-bit integers, 16/32-bit floats). Kernels access them only through texture fetches (read) or surface reads/writes.

// Host: 1) allocate CUDA array  2) copy data  3) resDesc  4) texDesc  5) create texture object
cudaChannelFormatDesc ch = cudaCreateChannelDesc(32, 0, 0, 0, cudaChannelFormatKindFloat);
cudaArray_t cuArray;
cudaMallocArray(&cuArray, &ch, width, height);
cudaMemcpy2DToArray(cuArray, 0, 0, img, width * sizeof(float), width * sizeof(float), height,
                    cudaMemcpyHostToDevice);

cudaResourceDesc resDesc = {};  resDesc.resType = cudaResourceTypeArray;  resDesc.res.array.array = cuArray;
cudaTextureDesc texDesc = {};
texDesc.addressMode[0] = cudaAddressModeWrap;   texDesc.addressMode[1] = cudaAddressModeWrap;
texDesc.filterMode = cudaFilterModeLinear;      // bilinear interpolation for free
texDesc.readMode = cudaReadModeElementType;
texDesc.normalizedCoords = 1;                   // coordinates in [0, 1)
cudaTextureObject_t texObj = 0;
cudaCreateTextureObject(&texObj, &resDesc, &texDesc, NULL);

// Device: rotate the normalised coordinate by θ about the centre, read from the texture
__global__ void transformKernel(float* output, cudaTextureObject_t texObj, int width, int height, float theta) {
    unsigned int x = blockIdx.x * blockDim.x + threadIdx.x;
    unsigned int y = blockIdx.y * blockDim.y + threadIdx.y;
    if (x < width && y < height) {
        float u = x / (float)width - 0.5f, v = y / (float)height - 0.5f;
        float tu = u * cosf(theta) - v * sinf(theta) + 0.5f;
        float tv = v * cosf(theta) + u * sinf(theta) + 0.5f;
        output[y * width + x] = tex2D(texObj, tu, tv);
    }
}
// dim3 block(16, 16); dim3 grid((width + 15) / 16, (height + 15) / 16);

Reading on the device: linear-memory textures tex1Dfetch(), array textures tex1D(), tex2D(), tex3D(). Management functions: cudaMallocArray, cudaFreeArray, cudaMemcpyToArray, cudaMemcpyFromArray. In the older texture reference API, type, dimensionality and read mode are fixed at compile time; normalisation, filter and address mode can change at run time (CUDA array textures only).

Check yourself

Can a compute capability 8.6 GPU run an application compiled only with -gencode arch=compute_70,code=sm_70?

  1. Yes, the sm_70 binary runs on 8.6.
  2. No: binaries are not compatible across major versions and no PTX is embedded.
  3. Yes, the driver JIT-recompiles the sm_70 binary.
  4. Only if compiled with the same driver version.

Why is cudaDeviceSynchronize() needed when timing a kernel?

  1. To complete memory allocation.
  2. Because cudaMemcpy is asynchronous.
  3. To synchronise the blocks with each other.
  4. Kernel launches are asynchronous; timing without waiting for completion gives a far too short (wrong) time.

Which variable is most likely to be placed in local memory?

  1. An automatic array accessed with an index computed at run time.
  2. An int loop counter.
  3. A __shared__ array.
  4. A __constant__ array.

Rows of 700 bytes were allocated with cudaMallocPitch (256 B alignment). How do you reach the start of row r?

  3. (float*)((char*)p + r * pitch), pitch = 768

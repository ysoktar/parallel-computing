Threads and synchronization

Shared-memory parallel programming on the CPU: C++11 threads, data races and the tools that prevent them. The CPU counterparts of __syncthreads() and atomic operations on the GPU.

  • Tell a data race from a race condition.
  • Say when to use a lock, mutex, semaphore, atomic or monitor.
  • Define and illustrate deadlock, livelock and starvation.

What is a thread?

  • Process: a running program with its own address space, open files and PID (fork() copies a process: expensive). Thread: a separate flow of execution inside a process; it has its own program counter, stack, registers and state, but shares the address space with the other threads of the process. A "lightweight process": cheaper to create and switch.
  • What they are good for: (1) performance (multi-core), (2) background tasks, (3) asynchronous processing (non-blocking calls: e.g. cudaMemcpyAsync returns immediately), (4) improving program structure.
  • Before C++11, pThreads (POSIX); since C++11, the standard std::thread.

Sharing data and races

  • Reads only: no problem. If at least one writes: problems.
  • Data race: multiple threads access the same variable concurrently and at least one writes. Undefined behaviour in C/C++; the compiler may assume it does not happen.
  • Race condition: an error where the ordering of events compromises correctness. Not every data race causes a race condition (you may get the right output by luck); not every race condition comes from a data race (remove the data race with atomics and the order of operations can still give varying output).
  • Aligned 8-byte loads/stores are atomic on x86, but never code relying on it: larger types exist, compilers and hardware can reorder memory operations or split one read/write in two. And never assume 8-byte alignment.
  • GPU note: many threads writing the same variable concurrently is (much) slower on a GPU than on a CPU and a serious bottleneck; it depends on where the variable is stored (GPUs have many memory types).

Locks, mutexes, semaphores

ToolProperty
LockOne thread at a time in the protected code section (critical section). Not shared between processes; the acquiring thread must release it. Some can be acquired repeatedly by the same thread (recursive), released the same number of times.
MutexLike a lock but can be system-wide (across processes). "Lock" usually means mutex. Mutual exclusion; like a binary semaphore that admits one thread at a time + ownership.
SemaphoreLike a mutex but admits N threads: limits the number of threads using critical resources (CPU, I/O, RAM). Binary (0/1) or counting. Usable as a resource counter, a lock, a signalling mechanism.

  • Without atomic support in hardware, true parallel programming is impossible.
  • If waiters are kept in a FIFO queue the semaphore is strong, otherwise weak (starvation possible).
  • A binary semaphore can be used for the "wait on an event" case (one thread releases, another acquires).
  • C++: std::mutex, std::timed_mutex, std::recursive_mutex; RAII wrappers std::lock_guard (releases at end of scope) and std::unique_lock (deferred locking, used with condition variables). Class examples: semaphore_single_sync.cpp, semaphore_double_sync.cpp.
  • Lazy init / call once: initialise a resource exactly once on first use (std::call_once); e.g. a video decoder.
  • Recursive locks: a normal mutex acquired twice by the same thread deadlocks; a recursive mutex allows it.

Consistency models

  • Design concerns: cache coherence (the same address) and the memory consistency model (the order in which operations on different addresses become visible).
  • Sequential consistency: events on shared objects should appear to happen one at a time and take effect in program order for each thread. Events of different threads may be shifted so that the overall history satisfies the object's sequential specification.
  • In high-level languages compiler optimisations can make the generated code very different from a sequential translation (instruction reordering), but the result preserves sequential consistency (from a single thread's point of view).

Producer-consumer

Producers put items into a shared buffer (e.g. BUFFSIZE = 100), consumers take them. Three semaphores: slotsAvail (initially BUFFSIZE), resAvail (initially 0), and a mutex (l) protecting the buffer indices.

// producer                          // consumer
slotsAvail.acquire();                resAvail.acquire();
l.acquire();                         l.acquire();
buffer[in] = item;                   item = buffer[out];
in = (in + 1) % BUFFSIZE;            out = (out + 1) % BUFFSIZE;
l.release();                         l.release();
resAvail.release();                  slotsAvail.release();

Without synchronisation: writing into a full buffer (old data lost), reading from an empty one, two threads using the same in/out index. Termination: with a shared data item (e.g. the total number to produce) or by sending consumers a special "done" message (poison pill).

Atomics

  • std::atomic<T>: operations are indivisible; a notification to the compiler. An atomic read has acquire semantics, an atomic write release semantics (default seq_cst).
  • Hardware support: CAS (compare-and-swap/exchange): compares a memory location with a value, stores the new value if they match, returns the value read in any case (x86: CMPXCHG). LL/SC (load-link / store-conditional): LL reads the value; SC writes only if nobody wrote the location in between (ARM, PowerPC).
  • Atomic operations can build locks, replace them or complement them (lock-free data structures: is_lock_free(), does the hardware support it?). Example: atomic<bool> as a lock (spin lock). Floating-point atomics in C++20.
  • On GPUs atomic operations can be very slow (the histogram example: many writes to the same bin).
std::atomic locked{false};
void lock()   { bool exp = false; while (!locked.compare_exchange_weak(exp, true)) exp = false; }
void unlock() { locked.store(false); }

Memory ordering

  • memory_order_relaxed: changes are not forcibly propagated to other cores; threads may see different value sequences. Do not use unless you are very sure.
  • memory_order_acquire / release (+ acq_rel, consume): changes propagate between pairs of threads; the writer uses release, the reader acquire. For older ARM/PowerPC.
  • memory_order_seq_cst (default): all threads see a variable's values in the same order.

Monitors and condition variables

  • Semaphores are flexible but hard to use correctly (the logic is spread over threads); atomics are even riskier. Monitor: an object designed to be accessed safely by multiple threads: its methods run under mutual exclusion (one thread inside at a time).
  • Condition variable: for waiting on a condition inside a monitor: wait() releases the lock and sleeps, notify_one()/notify_all() wakes. If the signalling thread continues, the woken thread must recheck the condition (a while loop).
  • C++11: std::mutex + std::unique_lock + std::condition_variable.
class Monitor {
    std::mutex m; std::condition_variable cv; int count = 0;
public:
    void put()  { std::unique_lock l(m); count++; cv.notify_one(); }
    void take() { std::unique_lock l(m);
                  cv.wait(l, [&]{ return count > 0; });   // releases the lock while waiting
                  count--; }
};

Asynchronous threads and thread management

  • std::async + std::future: run a function asynchronously and get its result later with get(). std::packaged_task: wraps a callable whose result is reached through a future (for task queues/thread pools).
  • Dynamic (a new thread per task) vs static thread management (a thread pool). Pool pros: no per-task start-up cost; the thread count can match the workload (more for I/O-bound, one per core for CPU-bound); thousands of tasks for good load balancing; fewer system resources. Cons: complexity, deadlock risk with dependencies between tasks.
  • Fibers / user-level threads (boost::fibers): scheduled by a library rather than the OS; tiny creation/switch overhead ("lightweight/green threads"), thousands easily, custom schedulers, portable. Con: if one makes a blocking system call, all block; no direct multi-core benefit.

The CPU ↔ GPU bridge: std::thread + join ≈ kernel launch + cudaDeviceSynchronize(); a barrier ≈ __syncthreads() (but within a block only); std::atomic ≈ atomicAdd; the histogram exercise shows the same race problem in both worlds.

Check yourself

Two threads only read the same int. Is this a data race?

  1. Yes, concurrent access is always a data race.
  2. No, there is no data race unless at least one thread writes.
  3. Only if the variable is misaligned.
  4. Only if it is not atomic.

Threads cannot make progress but CPU usage is high. Which is it?

  1. Deadlock
  2. Starvation
  3. Livelock
  4. Race condition

The key difference between a mutex and a semaphore?

  1. A semaphore can admit N threads at once; a mutex one.
  2. A semaphore works only within one process.
  3. A mutex needs no atomic operations.
  4. A mutex can be released by another thread.

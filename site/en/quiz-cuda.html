CUDA quiz: solved questions

31 questions prepared for the written CUDA quiz of 24 November; also a good CUDA revision for the final. The order starts with the latest topics (L7 → L6 → synchronisation → tiling → CGMA → occupancy → writing kernels → indexing). Solve each one yourself first, then Show the solution.

Think of four chains together: thread mapping → warp addresses → coalescing / divergence · tile size → shared/register use → occupancy → latency hiding · data reuse → CGMA → arithmetic intensity → bandwidth ceiling · data dependency → barrier / atomic / separate kernel stage.

1. Error checking, divergence, predication (L7)

Question 28 · Launch and asynchronous errors

Complete the unchecked call k<<<g,b>>>(...);. What is the difference between Peek and Get?

// first check all earlier API errors (clear with cudaGetLastError)
k<<<g,b>>>(...);
cudaError_t launch = cudaGetLastError();     // != cudaSuccess: report and stop
cudaError_t run = cudaDeviceSynchronize();   // != cudaSuccess: report and stop

A launch returns no error code. Get takes the last error and resets it to cudaSuccess; Peek does not reset. The launch check finds configuration/parameter errors, the sync check finds asynchronous errors during execution. The return values of all runtime calls should be checked too. Runnable example: 7.1.

Question 29 · Predication, unrolling, block order

How is predication different from prediction? Why is #pragma unroll 4 not always faster? Why is the execution order of normal (non-cluster) blocks not guaranteed?

Prediction (CPU): guess the branch, execute speculatively, roll back if wrong. Predication (GPU): conditional instructions are not skipped but masked with a per-thread predicate; false ones neither write results nor read operands. Unrolling reduces loop control but increases register pressure and code size (spills, lower occupancy). Block independence lets the hardware distribute blocks freely over any number of SMs; an order guarantee would break that flexibility (scalability). CC 9.0 clusters are a special exception.

Question 24 · Counting divergence

A 128-thread block, t = threadIdx.x: how many warps diverge for if (t < 70) and if (t % 2 == 0)? And if (threadIdx.y % 2 == 0) in a 16×16 2D block?

t < 70: warps 0, 1 all true; warp 2 (64–95) mixed; warp 3 false → 1. t % 2: all 4 warps mixed → 4. In a 16×16 block x varies fastest, each warp is two rows (one even, one odd) → all 8 warps. Different warps taking different branches does not count as divergence.

2. Global and shared memory access (L6)

Question 19 · Global memory transactions

Each of 32 lanes reads a 4 B float: (a) 32 consecutive floats, 128 B aligned; (b) 32 consecutive floats shifted 4 B from the base; (c) each lane in a separate 32 B segment. Data moved and efficiency? (32 B segment model)

Useful data is 128 B in every case. (a) 4 segments = 128 B, 100%. (b) bytes 4–131: 5 segments = 160 B, 80%. (c) 32 segments = 1024 B, 12.5% (1/8 of a). Real behaviour depends on the architecture.

Question 20 · Which matmul access is coalesced?

Row-major A, B; block (32,8), one warp maps to one output row. Compare the accesses A[r*K+k] and B[k*N+c] (k is a fixed instruction step).

Within a warp r and k are the same: one address of A is read by all lanes (a reuse opportunity). In B, c is consecutive: 32 consecutive floats, coalesced with suitable alignment. One thread walking down a column of B over time does not break coalescing within the warp: coalescing looks at the addresses across threads of the same instruction. Shared tiling reduces repeated global access in both.

Question 21 · Pitch

W = 100, H = 50 floats; the API returned pitch = 512 B. Byte offset of row 7, column 9 from the base? Allocated area and padding?

Offset = 7·512 + 9·4 = 3620 B. Real data per row 400 B, padding 112 B. Total 50·512 = 25600 B, logical data 20000 B, padding 5600 B. Access: ((float*)((char*)p + 7*pitch))[9]. The pitch is in bytes, the column offset in elements.

Question 22 · Shared banks

A warp reads s[lane*k] (lane = threadIdx.x % 32, float s[], 32 banks). Conflict degree for k = 1, 2, 3, 4, 16, 32, 33? And if everyone reads s[0]?

gcd(k, 32) = 1, 2, 1, 4, 16, 32, 1. k = 32: every lane a different address but the same bank → 32-way. k = 33 (padding): the banks spread. s[0]: the same address → broadcast, no conflict. A global segment and a shared bank are different concepts. Visualisation: 6.3, banks.

Question 26 · Choosing the memory

(a) A thread's accumulator, (b) a tile shared by the block, (c) a filter where the whole warp reads the same coefficient, (d) 2D locality and bilinear interpolation, (e) a large thread-private array: which memory?

(a) register; (b) shared; (c) constant (broadcast); (d) texture; (e) the compiler may place it in local memory (physically device DRAM, not fast). A surface is writable; a texture is read-only from a kernel.

Question 27 · Compilation and API

Runtime vs Driver API? How do an sm_70 binary and compute_70 PTX behave on 7.5 and 8.6 GPUs?

Runtime (cuda*): implicit context/module management; Driver (cu*): explicit, detailed control. An sm_70 binary runs on 7.5 (same major), not on 8.6 (different major). compute_70 PTX can be JIT-compiled by the driver on both GPUs, but using new architecture features is not guaranteed. nvcc separates host and device code.

3. Synchronisation and races

Question 23 · A broken shared memory kernel

What is wrong with the code below? Fix it so that out-of-range tile elements are 0.

if(i<N) {
    tile[threadIdx.x]=A[i];
    __syncthreads();
    B[i]=tile[(threadIdx.x+1)%blockDim.x];
}

In the last block some threads never reach the barrier (undefined behaviour), and the tile element to be read may not have been loaded. Every thread must fill the tile and reach the barrier:

tile[threadIdx.x]=(i

If the same tile is reloaded, a second barrier is needed after the reads.

Question 25 · Barrier or atomic?

Is the sum within a block correct with sum += A[i]; __syncthreads();? And if blocks also write to the same sum?

No. += is read-modify-write; a barrier only coordinates progress, it does not prevent lost updates. atomicAdd(&sum, A[i]) makes the update atomic. Alternative: a reduction within the block, a separate output per block, and a second kernel to sum them. __syncthreads() does not work across blocks; __threadfence() is not a grid barrier.

4. Tiling and reuse (L5)

Question 30 · Complete and analyse the tiled kernel

Grid = (7,7), block = (16,16), phases = ⌈100/16⌉ = 7; 12544 threads, 10000 valid. The first barrier guarantees the loads, the second the end of the reads. Shared 2·16²·4 = 2048 B/block. Limits: threads 2048/256 = 8, warps 64/8 = 8, registers 65536/(256·32) = 8, shared 24, blocks 16 → 8 blocks, 100% theoretical occupancy. Out-of-range lanes take part in the barriers too.

Question 31 · Optimising the transpose

In a matrix transpose the global reads are consecutive, the writes have stride W. What can be done with shared memory?

Read the tile coalesced, barrier, write coalesced with transposed indices. In a 32×32 tile the shared column access has stride 32 → a 32-way bank conflict; [32][33] padding removes it (32·1·4 = 128 B extra shared memory). Judge the global coalescing gain and the shared bank conflict separately; design the bounds checks outside the barrier. See transpose.

Question 17 · Tile size and phases

A = 64×96, B = 96×128; square T = 16. How many phases and blocks, shared bytes and input reads per block? And with T = 32?

T16: phases = 96/16 = 6, grid = (8,4) = 32 blocks, shared 2·16²·4 = 2048 B, reads/block = 6·2·256 = 3072, total 98304. T32: 3 phases, grid (4,2) = 8 blocks, shared 8192 B, reads/block 6144, total 49152: the traffic halves, but with 1024 threads/block and 8 KiB shared the resource limits must be checked.

Question 18 · Rectangular tile

Output H = 8, W = 32, phase depth D = 16. How many floats of shared memory? How do you spread the loads over 256 threads?

A tile 8·16 = 128, B tile 16·32 = 512; total 640 floats = 2560 B. The 256 threads, with linear id t, fill the A and B tiles with separate for (i = t; i < count; i += 256) loops; barrier; each thread does D = 16 multiply-adds; barrier again. Plugging the rectangular block's sizes straight into square-tile code is wrong.

5. CGMA and bandwidth

Question 13 · The G80 example

Peak 367 GFLOP/s, BW 86.4 GB/s, float 4 B. Ideal ceiling for CGMA = 1, 8, 16, 32?

86.4/4 = 21.6 G floats/s; P = min(367, 21.6·CGMA): 21.6 · 172.8 · 345.6 · 367 (at 32 the memory ceiling is 691.2 but the compute peak is 367). Compute-bound from CGMA ≥ 367/21.6 ≈ 17.

Question 14 · Matmul: FLOPs and traffic

N = 256, T = 16. Global reads, output writes, FLOPs and CGMA for naive and tiled?

FLOPs = 2N³ = 33,554,432. Naive reads = 2N³ = 33,554,432; tiled = 2N³/T = 2,097,152. Writes N² = 65,536. Reads only: CGMA 1 and 16. Including writes: ≈ 0.998 and ≈ 15.52.

Question 15 · Compute-bound or memory-bound?

BW = 320 GB/s, peak 8 TFLOP/s. The kernel does 40 FLOPs, 10 float reads and 1 float write per output. Ceiling?

CGMA = 40/11 ≈ 3.64; FLOP/byte = 40/44 ≈ 0.909. Pmem = 320 · 0.909 ≈ 290.9 GFLOP/s ≪ 8000 → memory-bound.

6. Occupancy and SM resources

Question 9 · Block choice on the GT200

1024 threads and 8 blocks per SM; 512 threads per block. 8×8, 16×16, 32×32?

8×8: 8 blocks × 64 = 512 threads, 50%. 16×16: 4 blocks = 1024, 100%. 32×32 = 1024 > 512: invalid. 16×16 is the best candidate for this device (not a performance guarantee).

Question 10 · Limits together

SM: 2048 threads, 64 warps, 16 blocks, 65536 registers, 48 KiB shared. Block: 256 threads, 48 registers/thread, 12 KiB shared. How many blocks, occupancy? And if shared drops to 8 KiB?

Block = 8 warps, 12288 registers. Threads 8, warps 8, blocks 16, registers ⌊65536/12288⌋ = 5, shared 48/12 = 4 → 4 blocks, 32 warps, 50%. Shared 8 KiB: shared allows 6 but registers limit to 5 → 5 blocks, 40 warps, 62.5%. Remove one bottleneck and another one limits.

Question 11 · The partial-warp trap

SM: 64 warps, 2048 threads, 32 blocks. Block of 48 threads. Occupancy?

⌈48/32⌉ = 2 warps per block. Threads ⌊2048/48⌋ = 42, warps 64/2 = 32, blocks 32 → 32 blocks × 2 = 64 warps → 100% warp occupancy, but 1536/2048 = 75% active threads. A partial warp takes a whole warp slot.

Question 12 · Spill or occupancy?

A kernel uses 64 registers per thread. What can happen as register pressure grows?

(1) The register capacity allows fewer blocks (lower occupancy). (2) The compiler spills values it cannot fit into local memory (DRAM traffic). These are different events; forcing fewer registers to raise occupancy can be slower because of spills.

Question 8 · Kernel and end-to-end speedup

CPU 80 ms, H2D 6 ms, kernel 4 ms, D2H 10 ms. The two speedups? Amdahl's bound for 95% parallel code?

Kernel only: 80/4 = 20×. End to end: 80/(6+4+10) = 4×. Amdahl: 1/0.05 = 20× (a separate ideal model). When timing with a host clock, wait for the kernel to finish.

8. Threads, blocks and indexing

Question 1 · 1D launch and extra threads

N = 1000, 128 threads per block. Grid, total threads, invalid threads, number of warps, index of thread 37 of block 5?

Grid ⌈1000/128⌉ = 8; 1024 threads, 24 out of range. 4 warps per block, 32 in total. Index 5·128 + 37 = 677; local warp 1, lane 5. 104 valid threads in the last block. if (i < 1000) is required.

Question 2 · 2D mapping

130 columns × 75 rows, block (16,8). Grid, total threads; (x,y), row-major index, warp and lane for blockIdx=(3,4), threadIdx=(7,5)?

Grid (9,10), 90 blocks × 128 = 11520 threads, 9750 valid. x = 55, y = 37, index 37·130 + 55 = 4865. Local 5·16 + 7 = 87 → warp 2, lane 23. Each warp spans two rows of 16.

Question 3 · 3D mapping

Volume W = 40, H = 30, D = 20; block (8,4,2). Global and local linear index for blockIdx=(2,3,4), threadIdx=(5,2,1)?

x = 21, y = 14, z = 9. Global = 21 + 40·(14 + 30·9) = 11381. Local = 5 + 8·(2 + 4·1) = 53 → warp 1, lane 21. Grid (5,8,10) = 400 blocks, 25600 threads, 24000 valid.

Question 4 · Why is blockIdx needed?

Why is an 8-block vector addition using int i = threadIdx.x; wrong?

All blocks have the same threadIdx range: they all process the first 128 elements again and the rest are never written; there are also concurrent writes to the same place. The fix is i = blockIdx.x*blockDim.x + threadIdx.x; and a bounds check.

Final check

Do not mix up: access within a warp ↔ one thread's successive time steps; local ↔ shared; CGMA ↔ transactions; occupancy ↔ speedup; barrier ↔ atomic; coalescing (global) ↔ bank conflicts (shared); predication ↔ prediction. If a question gives an old architecture, use its numerical limits.

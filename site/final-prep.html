Ayrıntılı özet

Lecture 1: neden paralel, ne kadar hızlanır

  • Güç duvarı: güç ≈ f³; ~2005'te frekans 2–4 GHz'de durdu. Moore yasası transistör sayısı içindir, frekans için değil; fazla transistörler çekirdeğe gitti.
  • Flynn: SISD, SIMD, MISD, MIMD. GPU'nun programlama modeli SIMT (bir warp = tek komut, 32 thread). Paylaşımlı bellek (ortak adres uzayı; NUMA'da uzak bellek yavaş ama adres ortak) ↔ dağıtık bellek (mesajlaşma, çok ölçeklenir).
  • Ölçüm kuralları: aynı donanım ve koşullar; seri taraf bilinen en hızlı seri çözüm olmalı; kernel-only ve uçtan uca (kopyalar dahil) hızlanma ayrı.
  • Amdahl (sabit problem, strong scaling): S = 1/((1−α)+α/N) → N → ∞ iken 1/(1−α). Gustafson (sabit süre, weak scaling): S = (1−α)+αN.
  • Karınca–fil: pahalı CPU r kat hızlıysa N ucuz CPU'nun ona göre hızlanması 1/((1−α)r + αr/N); r ≥ 1/(1−α) ise asla 1'i geçmez.
  • Gecikme ↔ throughput: CPU tek işi hızlı bitirir, GPU birim zamanda çok iş bitirir.

Lecture 2: tasarım

  • Önce sor: paralel gerekli mi, algoritma izin veriyor mu?
  • PCAM: Partitioning (işlemci sayısının 10–100 katı parça), Communication (bağımlılık grafı), Agglomeration (iletişimi azaltmak için grupla, ~10 katı), Mapping (yük dengesi + yoğun iletişimlileri aynı düğüme; genel hâli NP-complete).
  • Ayrıştırma desenleri: task parallelism (ölçeklenmez), böl ve yönet (paralellik bağımlılık grafından okunur), geometrik (halo gerekir), özyinelemeli veri (prefix sum), pipeline (throughput ≤ 1/en uzun aşama), olay tabanlı.
  • Program yapısı: GPLS (SPMD, MPMD, master-worker, map-reduce) ↔ GSLP (fork/join, loop parallelism). CUDA kernel'i = geometrik ayrıştırma + SPMD.
  • Pipeline zamanı: ilk çıktı = aşama sürelerinin toplamı, sonra her "en uzun aşama"da bir çıktı.

Lecture 3: thread'ler ve senkronizasyon

  • Thread'ler adres uzayını paylaşır (stack, register, program sayacı ayrı). Data race: eş zamanlı erişim, en az biri yazma, senkronizasyon yok (C++'ta tanımsız). Race condition: sıralama yüzünden yanlış sonuç.
  • counter++ = oku + ekle + yaz; iki thread aynı eski değeri okursa bir güncelleme kaybolur.
  • Mutex: tek thread + sahiplik. Semafor: N izin (counting), binary semafor "olay" sinyali. Atomik: tek bölünmez işlem (CAS, LL/SC). Monitör / condition variable: kilidi bırakıp koşulu bekle; koşul while ile.
  • Deadlock (dört koşul: karşılıklı dışlama, tut ve bekle, elden alınamama, döngüsel bekleme; CPU boşta) ↔ livelock (CPU meşgul, ilerleme yok) ↔ starvation (biri hiç sıra alamaz). Önlem: kilitleri hep aynı sırada al, std::scoped_lock.
  • Producer-consumer: slotsAvail (boş yer), resAvail (dolu yer) semaforları + indeks mutex'i; önce semafor, sonra mutex.
  • Bellek sıralaması: seq_cst (varsayılan, herkes aynı sırayı görür), acquire/release (çiftler arası), relaxed (sıra garantisi yok).

Lecture 4–5: CUDA modeli, kernel, tiling

  • Host hazırlar (cudaMalloc → cudaMemcpy H2D → kernel → cudaMemcpy D2H → cudaFree), device yürütür. Kernel başlatma asenkron; süre ölçmeden önce cudaDeviceSynchronize().
  • Niteleyiciler: __global__ (host'tan çağrılır, device'ta çalışır, void), __device__, __host__.
  • Hiyerarşi: blok ≤ 1024 thread, aynı SM'de; warp = ardışık 32 lineer id; bloklar bağımsız ve sırasız → ölçeklenebilirlik. Kısmi warp tam warp slotu kaplar.
  • Divergence: sadece warp içinde; iki yol sırayla çalışır, süre toplamı. Koşul threadIdx / 32'ye hizalıysa divergence yok.
  • Bariyer: __syncthreads() blok içi; bloğun bütün thread'leri ulaşmalı (if içinde, erken return'den sonra, thread'e bağlı tur sayılı döngüde tanımsız).
  • Latency hiding: bekleyen warp yerine hazır warp çalışır (sıfır maliyetli geçiş); bunun için çok warp gerekir.
  • CGMA: naive matmul 1 (2 okuma, 2 FLOP). G80: 86,4 GB/s ⇒ 21,6 GFLOPS ≈ tepe 367'nin %6'sı. T×T tiling: CGMA = T; dikdörtgen BX×BY blokta azalma 2·BX·BY/(BX+BY).
  • Tiled kernel: faz başına herkes M ve N karosundan birer eleman yükler; bariyer (1) karo dolsun, bariyer (2) üzerine yazılmasın; faz sayısı ⌈width/T⌉, kenarda 0 yüklenir.

Lecture 6: derleme ve bellek

  • Derleme: .cu → PTX (sanal ISA) → ptxas → SASS (cubin). cubin X.y sadece X.z (z ≥ y) üzerinde çalışır; yeni GPU için PTX gömülmeli (JIT). -arch PTX'i, -code ikiliyi seçer. Register sayısı: --ptxas-options=-v.
  • Bellek haritası: register (thread, ~1 çevrim) · shared (blok, birkaç çevrim, bank'lar) · local (thread ama DRAM'de!) · global (grid + host, 400–600 çevrim, coalescing) · constant (salt okunur, aynı adres → yayın) · texture (salt okunur, 2D yerellik, interpolasyon, sınır modları).
  • Occupancy: SM başına blok = min(thread sınırı/Bt, warp sınırı/Bw, register/(Bt·reg), shared/Bshared, blok sınırı). Register spill → local memory.
  • Bank'lar: 32 bank, bank = kelime indeksi % 32; aynı bank'ta farklı kelime = conflict, aynı kelime = yayın. s[k·threadIdx.x] için derece EBOB(k, 32). 32×32 karoda sütun okuma 32-yollu → [32][33].
  • Coalescing: warp'ın adresleri 32/64/128 B hizalı segmentlere toplanır; verim = kullanılan/taşınan. Pitch bayt cinsindendir: satır r = (char*)p + r·pitch. Hizalama: tip 1/2/4/8/16 B ve doğal hizalı.
  • Transpose: naive'de yazma stride'lı; shared karo ile ikisi de coalesced; 32×8 blok + 4 eleman/thread; copy kernel'i tavan ve indeks testi.

Lecture 7: hata ve kontrol akışı

  • Runtime çağrıları cudaError_t döndürür, kernel başlatma döndürmez. Konfigürasyon hatası → başlatmadan hemen sonra cudaGetLastError(); yürütme hatası → cudaDeviceSynchronize() ya da sonraki ilgisiz bir çağrı. Yürütme hataları kalıcıdır (sticky).
  • cudaPeekAtLastError() okur; cudaGetLastError() okur ve sıfırlar.
  • Predication (GPU): komutlar atlanmaz, predicate'i false olan thread'de etkisizdir; kısa dallar için. Prediction (CPU): tahmin + spekülatif yürütme.
  • #pragma unroll N döngünün hemen önünde; sayısız: sabit tur sayısında tam açar; 1: açmaz. Bedel: register ve kod boyutu → spill / occupancy.
  • Sayaç int olsun: signed taşma tanımsız, derleyici daha çok optimize eder; unsigned ile geri sayan i >= 0 döngüsü hiç bitmez.

Zor hesap soruları

Hepsi hesap makinesiz yapılabilir. Her soruda iki ayrı konu birleşiyor; önce hangi formüllerin gerektiğini yazın.

H1 · Amdahl, tersten

Bir programın %95'i paralelleştirilebiliyor. (a) 16 çekirdekte speedup ve verim? (b) Speedup 15 için en az kaç çekirdek gerekir? (c) Speedup 20'ye ulaşılabilir mi? (d) Aynı program Gustafson'a göre 16 çekirdekte ne verir, ve hoca hangisini sorarsa hangisini kullanırsınız?

(a) 1/(0,05 + 0,95/16) = 1/(0,05 + 0,059375) = 1/0,109375 ≈ 9,14; verim 9,14/16 ≈ %57. (b) 1/(0,05 + 0,95/N) ≥ 15 ⇒ 0,05 + 0,95/N ≤ 1/15 ≈ 0,0667 ⇒ 0,95/N ≤ 0,0167 ⇒ N ≥ 57. (c) Hayır: tavan 1/0,05 = 20, ancak N → ∞ iken yaklaşılır, ulaşılmaz. (d) 0,05 + 0,95·16 = 15,25. Problem boyutu sabitse (aynı işi daha hızlı) Amdahl, süre sabit ve problem N ile büyüyorsa Gustafson.

H2 · Karınca ordusu mu, fil mi?

Pahalı bir CPU, ucuz bir CPU'dan r = 4 kat hızlı. Programın α = 0,8'i paralel. (a) Kaç ucuz CPU pahalı tek CPU'yu geçer? (b) r = 5 olsaydı? (c) Bu sonuç neden Top500'deki makinelerin yapısıyla çelişiyor gibi görünür?

Pahalı CPU'ya göre hızlanma 1/((1−α)r + αr/N). (a) 0,2·4 + 3,2/N < 1 ⇒ 3,2/N < 0,2 ⇒ N > 16 ⇒ 17 ucuz CPU. (b) (1−α)r = 0,2·5 = 1: payda her zaman > 1, hiçbir N yetmez (r ≥ 1/(1−α) = 5). (c) Bu hesap problemi sabit tutar (Amdahl). Süper bilgisayarlar daha büyük problemler çözer: paralel kısım N ile büyür (Gustafson), bu yüzden çok sayıda ucuz çekirdek kazanır.

H3 · Pipeline ve kopya aşama

4 aşamalı pipeline: 3, 7, 2, 4 ms. (a) 50 öğe ne kadar sürer? (b) 7 ms'lik aşamayı iki kopya hâlinde çalıştırırsak? (c) Neden yine 2 ms'ye inmez?

(a) İlk öğe 3+7+2+4 = 16 ms'de çıkar, sonra her 7 ms'de bir: 16 + 49·7 = 359 ms. (b) İki kopya ⇒ o aşama etkin olarak 3,5 ms'de bir öğe verir; yeni darboğaz 4 ms'lik aşama: 16 + 49·4 = 212 ms. (c) Pipeline'ın hızını en yavaş aşama belirler; sırada 4 ms (sonra 3 ms) var. Her darboğazı kaldırınca bir sonraki ortaya çıkar.

H4 · Occupancy: hangi sınır kazanır?

SM: en fazla 2048 thread, 64 warp, 32 blok, 65.536 register, 64 KB shared. Kernel: blok 192 thread, thread başına 40 register, blok başına 9 KB shared. (a) SM başına kaç blok, occupancy? (b) Shared 8 KB'ye inerse? (c) Register da 32'ye inerse?

Blok = 6 warp, 192·40 = 7680 register. (a) Thread: ⌊2048/192⌋ = 10; warp: 64/6 = 10; register: ⌊65536/7680⌋ = 8; shared: ⌊64/9⌋ = 7; blok: 32 ⇒ 7 blok = 42 warp / 64 = %65,6 (sınırlayan shared). (b) Shared 64/8 = 8, register 8 ⇒ 8 blok = 48 warp = %75 (artık register ve shared birlikte sınırlıyor). (c) 192·32 = 6144 ⇒ ⌊65536/6144⌋ = 10; shared 8; thread 10 ⇒ yine 8: bir darboğaz kalkınca shared sınırlar. Ders: tek bir sınırı iyileştirmek yetmez, en küçüğü bakın.

H5 · double ve stride 3: kaç segment?

Bir warp, 128 B hizalı bir double dizisinden a[3*threadIdx.x] okuyor. Kaç tane 32 B segment taşınır, verim nedir? float olsaydı?

double: lane i bayt 24i … 24i+7'yi okur; son lane 744–751. Elemanlar arası boşluk 16 B < 32 B olduğu için 0–767 arasındaki her 32 B segmente dokunulur: 24 segment = 768 B taşınır, 32·8 = 256 B kullanılır ⇒ %33. float: lane i bayt 12i…12i+3, son 372–375 ⇒ 0–383 arası 12 segment = 384 B, kullanılan 128 B ⇒ yine %33. Stride k'lık erişimde verim ≈ 1/k (eleman segmentten küçükse).

H6 · 3D indeks, warp ve lane

Grid (4,3,2), blok (8,4,4); hacim W = 32, H = 12, D = 8 (x en hızlı). blockIdx = (3,2,1), threadIdx = (7,3,2) için: global (x, y, z), hacimdeki lineer indeks, blok içi lineer id, warp ve lane, bloğun lineer numarası?

x = 3·8 + 7 = 31, y = 2·4 + 3 = 11, z = 1·4 + 2 = 6. Lineer = x + W·(y + H·z) = 31 + 32·(11 + 72) = 31 + 2656 = 2687. Blok içi: 7 + 8·(3 + 4·2) = 7 + 88 = 95 ⇒ warp 95/32 = 2, lane 95 % 32 = 31. Blok numarası: 3 + 4·(2 + 3·1) = 23. Kontrol: grid 4·8 = 32 = W, 3·4 = 12 = H, 2·4 = 8 = D, yani hacim tam kaplanıyor.

H7 · 2D blokta divergence

Blok (16,16). Her koşul için kaç warp diverge olur? (a) if (threadIdx.x < 8) (b) if (threadIdx.y < 8) (c) if ((threadIdx.y * 16 + threadIdx.x) % 64 < 32) (d) if (threadIdx.y % 2 == 0)

16×16 blokta bir warp = iki satır (y = 2w ve 2w+1), her satırda x = 0..15. (a) Her satırın yarısı true ⇒ 8 warp'ın hepsi. (b) y < 8 ⇒ warp 0–3 tamamen true, 4–7 tamamen false ⇒ 0. (c) Lineer id % 64 < 32 ⇒ çift numaralı warp'lar true, tekler false; her warp tek parça ⇒ 0. (d) Bir warp'ta bir çift bir tek satır ⇒ 8. Tuzak: (b)'de “yarısı false” diye divergence saymak.

H8 · Konvolüsyonda karo + halo trafiği

5×5 filtre, 16×16 çıktı karosu, her blok bir karo. (a) Shared memory olmadan çıktı başına kaç global okuma? (b) Karoyu halo ile shared'a bir kez yüklersek blok başına kaç okuma, çıktı başına kaç? (c) Kaç kat azalma? (d) Shared alanı kaç bayt? (e) Filtre nerede durmalı?

(a) 25. (b) Halo her yönde 2 ⇒ (16+4)² = 400 okuma / 256 çıktı ≈ 1,56. (c) 25/1,5625 = 16 kat. (d) 400·4 = 1600 B. (e) __constant__: aynı döngü adımında warp'taki herkes aynı katsayıyı okur ⇒ tek istek, yayın. Karo büyüdükçe halo/iç oranı küçülür (32×32'de 36²/1024 ≈ 1,27 okuma/çıktı) ama shared ve thread sınırları büyür.

H9 · Pitch ve yanlış pointer aritmetiği

1000 float genişliğinde, 256 B hizalı satırlar. (a) Pitch? (b) Satır 3, sütun 999'un bayt ofseti? (c) float* p için p[3*pitch + 999] yazan biri nereye erişir?

(a) 4000 B → 256'nın sonraki katı 4096 B. (b) 3·4096 + 999·4 = 12288 + 3996 = 16284 B. (c) float* aritmetiği eleman sayar: 3·4096 + 999 = 13287 eleman = 53148 B, yani satır 12'nin ortası (yanlış ve ayrılan alan küçükse sınır dışı). Doğrusu ((float*)((char*)p + 3*pitch))[999].

H10 · Hesap mı bellek mi? Tiling yeter mi?

G80: tepe 367 GFLOPS, 86,4 GB/s. (a) Matmul'ün hesapla sınırlı olması için CGMA en az kaç olmalı? (b) T = 16 tiling yeterli mi, ulaşılan tavan? (c) T = 32 neden G80'de mümkün değil?

(a) 86,4/4 = 21,6 G float/s ⇒ 21,6·CGMA ≥ 367 ⇒ CGMA ≥ 17. (b) T = 16 ⇒ CGMA 16 ⇒ 21,6·16 = 345,6 GFLOPS: hâlâ az farkla bellekle sınırlı ama tepeye çok yakın. (c) 32×32 = 1024 thread, G80'in blok başına 512 sınırını aşar (shared açısından 2·32²·4 = 8 KB sığardı). Bir thread'e birden çok eleman verilerek (ör. 32×16 blok) aşılabilir.

Kod oku, hatayı bul

Bu kodların hepsi derlenir; bazıları yine de yanlıştır. Her birinde önce ne yaptığını, sonra neyin bozuk olduğunu ve düzeltmeyi yazın. Hepsi aynı programda: ▶ ile düzeltilmiş versiyonları çalıştırabilirsiniz.

K1 · Bir bariyer eksik

for (int m = 0; m < width / T; ++m) {
    Ms[ty][tx] = M[row * width + m * T + tx];
    Ns[ty][tx] = N[(m * T + ty) * width + col];
    __syncthreads();
    for (int k = 0; k < T; ++k)
        sum += Ms[ty][k] * Ns[k][tx];
}

Ne yanlış gidebilir? Neden test ederken çoğu zaman doğru sonuç verir?

İç döngüden sonra bariyer yok: hızlı bir warp bir sonraki fazın Ms/Ns elemanını yazar, yavaş warp hâlâ eski fazın değerini okuyordur (write-after-read yarışı) ⇒ sonuç belirsiz. Küçük bloklarda warp'lar neredeyse birlikte ilerlediği için çoğu zaman tutar; bu yüzden “çalıştı” kanıt değildir. Düzeltme: iç döngüden sonra ikinci __syncthreads().

K2 · Erken return

__global__ void earlyReturn(const float* in, float* out, int n) {
    __shared__ float s[256];
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;
    s[threadIdx.x] = in[i];
    __syncthreads();
    out[i] = s[255 - threadIdx.x];
}

Hangi blokta, hangi iki ayrı hata var? Düzeltilmiş kodu yazın.

Son blokta (blok 3: i = 768…1023) 24 thread (i ≥ 1000) return eder: (1) bariyere bütün thread'ler ulaşmaz ⇒ tanımsız davranış; (2) geçerli thread'ler s[255 − threadIdx.x] ile o 24 thread'in hiç yazmadığı yerleri okur ⇒ çöp. Düzeltme: s[threadIdx.x] = (i < n) ? in[i] : 0;, herkes __syncthreads(), sonra if (i < n) out[i] = ….

K3 · Histogram: iki bariyer var, yine de yanlış

__shared__ unsigned int local[BINS];
if (threadIdx.x < BINS) local[threadIdx.x] = 0;
__syncthreads();
int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) local[data[i] % BINS]++;
__syncthreads();
if (threadIdx.x < BINS) hist[threadIdx.x] += local[threadIdx.x];

İki ayrı yarışı bulun. Bariyerler neden yetmez? Düzeltme ne, ve neden önce shared'da sayıp sonra global'e ekliyoruz?

(1) local[bin]++: aynı bloktaki birçok thread aynı kutuyu oku-ekle-yaz yapar ⇒ kayıp güncelleme. (2) hist[...] += ...: farklı bloklar aynı global kutuya yazar ⇒ yine kayıp. Bariyer sadece ilerlemeyi eşgüdümler, aynı anda yazmayı engellemez. Düzeltme: atomicAdd(&local[bin], 1u) ve atomicAdd(&hist[b], local[b]) (programdaki histFixed). Shared atomikler ucuzdur ve global'e blok başına kutu başına bir atomik kalır: 220 yerine 4096 blok × 64.

K4 · Sonuç doğru, hız berbat

int row = blockIdx.x * blockDim.x + threadIdx.x;
int col = blockIdx.y * blockDim.y + threadIdx.y;
if (row < H && col < W) A[row * W + col] *= 2;

Grid doğru seçilirse sonuç doğrudur. Bir warp'ın erişimini anlatın: kaç segment, verim? Düzeltme?

Bir warp'ta threadIdx.x = 0..31 değişir, threadIdx.y sabit ⇒ row ardışık, col sabit. Adresler W = 4096 float = 16 KB aralıklı ⇒ her lane ayrı bir 32 B segment: okuma 32 segment, yazma 32 segment, 4 B'ı kullanılan 32 B'lık parçalar ⇒ %12,5. Düzeltme: x'ten sütun, y'den satır: col = blockIdx.x*blockDim.x + threadIdx.x; row = blockIdx.y*blockDim.y + threadIdx.y; (grid de buna göre).

K5 · Döngünün içinde bariyer

for (int k = 0; k < threadIdx.x % 4; ++k) {
    __syncthreads();
    s[threadIdx.x] += s[(threadIdx.x + 1) % 128];
}

Bariyer if içinde değil. Yine de neden yanlış? Ayrıca ikinci bir yarış var mı?

Tur sayısı thread'e bağlı (0, 1, 2 ya da 3): threadIdx.x % 4 == 0 olanlar bariyere hiç gelmez, diğerleri farklı sayıda gelir ⇒ bariyer bütün thread'ler için aynı sayıda çağrılmıyor ⇒ tanımsız. İkinci yarış: thread t, s[t+1]'i okurken thread t+1 aynı anda onu güncelliyor olabilir (bariyer okuma ile yazma arasında değil). Düzeltme: tur sayısını blok için sabit yapın (ör. 3 tur, gerekmeyen thread işlem yapmasın), oku ve yaz arasında da bariyer koyun (önce geçici değişkene oku, bariyer, sonra yaz).

K6 · Aynı karo, üç okuma

__shared__ float tile[32][32];
float a = tile[t][0];
float b = tile[t][t];
float c = tile[t / 2][t % 2];

Üç okumanın her biri kaç-yollu bank conflict yapar? tile[32][33] olsaydı?

tile[r][c]'nin bankı (32r + c) % 32 = c. (a) c = 0 hep ⇒ 32 farklı kelime aynı bankta ⇒ 32-yollu. (b) bank = t ⇒ hepsi farklı ⇒ conflict yok (köşegen). (c) bank = t % 2 ⇒ sadece 2 bank, her birinde 16 farklı kelime ⇒ 16-yollu. [32][33] ile bank = (33r + c) % 32 = (r + c) % 32: (a) r = t ⇒ hepsi farklı, conflict yok; (b) 2t % 32 ⇒ t ve t+16 aynı bank ⇒ 2-yollu (padding köşegeni bozdu!); (c) (t/2 + t%2) % 32 ⇒ değerler 0,1,1,2,2,3,… ⇒ 1,2 gibi bankların her biri iki farklı kelime alır ⇒ 2-yollu.

K7 · CPU tarafında sonsuz döngü

void reverseCopy(const float* in, float* out, unsigned n) {
    for (unsigned i = n - 1; i >= 0; i--)
        out[n - 1 - i] = in[i];
}

Ne olur? n = 0 için ayrıca ne olur? Lecture 7'nin signed sayaç tavsiyesiyle bağlantısı?

unsigned hiçbir zaman < 0 olmaz: i >= 0 hep doğru; i = 0'dan sonra i-- 232 − 1'e sarar ⇒ dizi dışına yazar, sonsuz döngü / çökme. n = 0'da baştan i = 232 − 1. Düzeltme: for (int i = (int)n - 1; i >= 0; i--). Bağlantı: unsigned taşma tanımlı (başa sarar); hem bu hataya yol açar hem de derleyicinin optimizasyonlarını kısıtlar. Signed sayaç iki açıdan da daha iyi.

Tasarım ve "neden" soruları

T1 · 10⁸ elemanı topla

10⁸ float'ın toplamını GPU'da hesaplayın. Neden tek bir kernel'de bütün blokların sonucunu bir bariyerle birleştiremezsiniz? Önerdiğiniz tasarımın adımlarını ve her adımdaki senkronizasyonu yazın.

__syncthreads() sadece blok içidir ve bloklar herhangi bir sırada, belki aynı anda değil çalışır: hepsinin aynı anda yerleşik olduğunu varsayan bir “grid bariyeri” kilitlenebilir (cooperative groups ayrı bir başlatma ister). Tasarım: (1) her blok kendi parçasını shared memory'de ağaç biçiminde toplar (her adımda yarı thread, adımlar arasında __syncthreads(); bölen threadIdx.x / 32'ye hizalı olunca son adımlar dışında divergence yok); (2) blok sonucu partial[blockIdx.x]'a yazılır; (3) ikinci kernel (ya da tek bloklu aynı kernel) partial'ı toplar. Kernel sınırı, bloklar arası bariyerdir. Alternatif: blok başına bir atomicAdd; kısa ama float toplama sırası değiştiği için sonuç bit bit tekrarlanmayabilir.

T2 · Isı denklemi: küme mi GPU mu?

2D ızgarada her adımda her hücre 4 komşusunun ortalamasını alıyor (1000 adım). PCAM ile hem 100 düğümlü dağıtık bellekli bir küme için hem GPU için tasarlayın. İletişim nerede, iki tasarım nerede ayrışır?

P: hücre başına bir görev (geometrik/veri ayrıştırması). C: her adımda 4 komşu; adımlar arası bağımlılık (adım t+1, t'nin bitmesini bekler). A: kümede 100 parça (10×10 karo ya da şerit; karo halo/iç oranını küçültür), her adım sonunda sadece kenar satır/sütunlar komşuya mesajla gider. M: eşit parçalar, komşu parçalar ağda yakın düğümlere. GPU: karo = blok, halo shared'a yüklenir, adım = kernel başlatması (adımlar arası global bariyer kernel sınırıdır), iki tampon (eski/yeni) dönüşümlü. Ayrışma: kümede iletişim pahalı mesajlardır ⇒ büyük karolar; GPU'da global bellek erişimidir ⇒ coalesced satırlar ve shared ile yeniden kullanım.

T3 · Daha çok occupancy her zaman daha mı hızlı?

Bir arkadaşınız register'ı -maxrregcount ile 64'ten 32'ye indirip occupancy'yi %50'den %100'e çıkardı ama kernel yavaşladı. İki olası nedeni açıklayın.

(1) Register spill: 32'ye sığmayan değerler local memory'ye (DRAM) gider; her erişim yüzlerce çevrim, kazanılan latency hiding'i yer. (2) Kernel zaten bant genişliğiyle sınırlıysa ya da %50'de yeterince warp gecikmeyi gizliyorsa ek warp'lar bir şey kazandırmaz; ayrıca önbellek başına düşen veri azalır. Occupancy bir araçtır, hedef değil: ölçün (--ptxas-options=-v ile spill'e bakın).

T4 · Hata yanlış satırda

Program şunları yapıyor: k1<<<…>>>(); k2<<<…>>>(); cudaMemcpy(…);. cudaMemcpy "illegal memory access" döndürüyor. Hangi kernel suçlu olabilir, nasıl bulursunuz, ve hatadan sonra neden sonraki her çağrı da başarısız oluyor?

İkisi de olabilir: başlatmalar asenkron, hata ilk senkronize eden çağrıda (burada cudaMemcpy) raporlanır. Bulmak için her kernel'den sonra cudaGetLastError() (başlatma hatası) ve cudaDeviceSynchronize() (yürütme hatası) kontrol edin; hangisinden sonra hata çıkarsa o. Yürütme hataları kalıcıdır (sticky): context bozulur, process'teki sonraki bütün CUDA çağrıları aynı hatayı döndürür; düzeltmek için programı yeniden başlatmak gerekir.

Tuzak sorular

Bir warp'ın 32 thread'i __constant__ float c[64]'ten c[threadIdx.x] okuyor. Ne olur?

  1. Tek istek, tam verim: ardışık adresler.
  2. 32-yollu bank conflict.
  3. İstek 32 ayrı isteğe bölünür.
  4. Derleme hatası: constant'a thread indeksiyle erişilemez.

s[threadIdx.x % 16] (float, 32 bank) okunuyor. Conflict derecesi?

  1. 2-yollu: iki thread aynı bankta.
  2. Conflict yok.
  3. 16-yollu.
  4. 32-yollu.

Bir blokta 48 thread var. SM'nin warp sınırı 64, thread sınırı 2048, blok sınırı 32. Warp occupancy ve aktif thread oranı?

  1. %75 ve %75
  2. %100 ve %100
  3. %50 ve %75
  4. %100 warp, %75 aktif thread

Hangisi her zaman yanlıştır?

  1. Blok 0, blok 1'den önce başlar.
  2. Bir warp'ın bütün thread'leri aynı bloktadır.
  3. Aynı bloktaki thread'ler aynı SM'de çalışır.
  4. Kernel başlatma host'a hemen döner.

Bir counting semafor 3 ile başlatıldı ve 3 thread'in paylaşılan counter++ yapmasına izin veriyor. Sonuç?

  1. Doğru: semafor karşılıklı dışlama sağlar.
  2. Deadlock.
  3. Hâlâ data race: 3 thread aynı anda oku-ekle-yaz yapabilir.
  4. Sadece x86'da doğru.

-gencode arch=compute_70,code=sm_70 ile derlenen program 8.6'lı bir GPU'da:

  1. Çalışır; sürücü sm_70 ikilisini JIT ile çevirir.
  2. "no kernel image" hatası verir: ikili major'lar arası uyumsuz, PTX gömülmemiş.
  3. Çalışır ama Tensor Core kullanmaz.
  4. Derleme hatası.

Tiled matmul'de T = 16'dan T = 32'ye geçmek kesin olarak neyi değiştirir?

  1. Kernel 2 kat hızlanır.
  2. Faz sayısı aynı kalır.
  3. Blok başına shared kullanımı aynı kalır.
  4. Thread başına global okuma yarıya iner ve blok başına thread 4 katına çıkar.

Condition variable'da notify_one() çağrıldı ama bekleyen thread yokken. Sonra bir thread wait()'e girer (koşul kontrolü olmadan). Ne olur?

  1. Sinyal kaybolmuştur; thread bir sonraki notify'a kadar uyur.
  2. Thread hemen uyanır: sinyal saklanmıştır.
  3. Deadlock garanti.
  4. Tanımsız davranış.

Divergence için hangisi doğru?

  1. Yanlış sonuç verebilir.
  2. Farklı bloklar farklı dallara giderse oluşur.
  3. Kısa dallarda derleyici predication ile dallanmayı tamamen kaldırabilir.
  4. if (threadIdx.x < 32) 64 thread'lik blokta iki warp'ı da diverge ettirir.

Speedup 16 çekirdekte 18 ölçüldü (süperdoğrusal). En olası açıklama?

  1. Amdahl yasası yanlış.
  2. Her çekirdeğe düşen veri önbelleğe sığmaya başladı (ya da seri versiyon en hızlı değil).
  3. Gustafson yasası.
  4. İmkânsız; ölçüm hatası.

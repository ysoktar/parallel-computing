Derleme ve bellek türleri

Bir .cu dosyası GPU'da çalışan koda nasıl dönüşür, hangi GPU'larda çalışır? Ve her bellek türü (register, local, shared, global, constant, texture) ne zaman, nasıl kullanılır? Lecture 6'nın coalescing kısmı ayrı sayfada.

  • Runtime API ile driver API'yi ayırt etmek; PTX, cubin ve JIT derlemeyi açıklamak.
  • Bir -gencode satırından hangi GPU'ya hangi kodun yükleneceğini söylemek.
  • Register ve shared bellek sınırlarından SM başına blok/thread sayısını hesaplamak.
  • Local ve constant belleğin ne olduğunu ve en iyi erişim desenlerini söylemek (texture bu vizede yok).

Programlama arayüzü: runtime ve driver API

  • CUDA C++ = C++'a küçük bir uzantı kümesi + bir runtime kütüphanesi. Bu uzantıları içeren her kaynak dosya nvcc (NVIDIA CUDA Compiler) ile derlenmeli.
  • Runtime API (cuda ile başlar, ör. cudaMalloc()): host'ta çalışan, cihaz belleği ayırma/serbest bırakma, host-cihaz kopyalama, çoklu cihaz yönetimi gibi fonksiyonlar. Daha alt seviyedeki driver API'nin (cu ile başlar, ör. cuMemAlloc()) üzerine kuruludur.
  • Driver API ek kontrol verir: CUDA context (cihaz için host process'in karşılığı) ve CUDA module (cihaz için dinamik yüklenen kütüphanenin karşılığı). Kernel başlatmak daha zahmetlidir (konfigürasyon ve parametreler açık fonksiyon çağrılarıyla), ama modüller gerektiğinde yüklenip boşaltılabilir; dilden bağımsızdır (sadece cubin nesneleriyle çalışır).
  • Runtime API başlatma, context ve modül yönetimini örtük yapar → daha kısa kod, daha az kontrol. Çoğu uygulama runtime API kullanır; gerekirse ikisi birlikte kullanılabilir.
  • Primary context: runtime, process başına cihaz başına bir tane oluşturur (referans sayımlı), process'teki tüm runtime kullanıcıları paylaşır. cudaDeviceSynchronize() ile senkronize, cudaDeviceReset() ile yok edilir. Tuzak: aynı process'teki eklentilerden biri cudaDeviceReset() çağırırsa diğerlerinin context'i habersizce yok olur.
  • Bir context kendi adres uzayına sahiptir: farklı context'lerdeki aynı pointer değeri farklı bellek konumlarını gösterir.

nvcc ile derleme

  • Kerneller CUDA komut seti mimarisi PTX (Parallel Thread Execution) ile de yazılabilir (Assembly'ye benzer); genelde C++ daha verimli. Her iki durumda da kerneller nvcc ile ikili koda derlenmeli.
  • Offline derleme: nvcc host ve device kodunu ayırır; device kodunu PTX'e ve/veya ikili cubin'e derler; host kodundaki <<<…>>> sözdizimini kernel'i yükleyip başlatan runtime çağrılarıyla değiştirir. Değiştirilmiş host kodu C++ olarak ya da host derleyicisi çağrılarak nesne kodu olarak çıkar.
  • JIT (just-in-time) derleme: uygulamanın çalışma zamanında yüklediği PTX, sürücü tarafından ikili koda derlenir. Yükleme süresini uzatır ama yeni sürücülerdeki derleyici iyileştirmelerinden faydalanır ve derlendiği zaman var olmayan GPU'larda çalışmanın tek yoludur. Sonuç compute cache'te saklanır, sürücü güncellenince geçersiz olur. Alternatif: NVRTC (çalışma zamanında C++ → PTX).

Derleme zinciri (tahtada): .cu (C/C++) → nvcc ön ucu → PTX (sanal ISA, metin) → ptxas → SASS (gerçek makine kodu, belirli bir sm_XY için; cubin içinde). PTX taşınabilir ara dildir, SASS mimariye özeldir. Ara dosyaları görmek: nvcc -keep veya -ptx; SASS'i görmek: cuobjdump -sass; register sayısı: --ptxas-options=-v.

Uyumluluk

  • İkili (cubin) uyumluluk: cubin mimariye özeldir; -code=sm_80 compute capability 8.0 için kod üretir. X.y için üretilen cubin sadece X.z (z ≥ y) cihazlarda çalışır: aynı major içinde ileriye uyumlu; geriye veya major'lar arası değil. (Sadece masaüstü; Tegra'da yok.)
  • PTX uyumluluğu: bazı PTX komutları sadece yüksek compute capability'lerde var (ör. warp shuffle 5.0+). -arch C++ → PTX derlemede varsayılan compute capability'yi belirtir (maksimum performans için her zaman verin). Belli bir compute capability için üretilen PTX, ona eşit veya büyük her ikili koda derlenebilir. Ama eski PTX'ten derlenen ikili yeni donanım özelliklerini kullanamaz (ör. Pascal 6.0 PTX'inden Volta 7.0 ikilisi Tensor Core kullanmaz).
  • Uygulama uyumluluğu: gelecekteki (henüz ikili üretilemeyen) mimarilerde çalışmak için uygulama JIT ile derlenecek PTX içermeli.
nvcc x.cu -gencode arch=compute_50,code=sm_50
          -gencode arch=compute_60,code=sm_60
          -gencode arch=compute_70,code=\"compute_70,sm_70\"
CihazÇalışan kod
5.0, 5.25.0 ikilisi
6.0, 6.16.0 ikilisi
7.0, 7.57.0 ikilisi
8.0, 8.67.0 PTX'i, çalışma zamanında JIT ile derlenir

Mimariye özel kod yolları için __CUDA_ARCH__ makrosu: sadece device kodunda tanımlı; -arch=compute_80 ile 800'e eşit.

Başlatma ve zaman ölçümü

  • CUDA 12.0'dan beri cudaInitDevice() ve cudaSetDevice() runtime'ı ve cihazın primary context'ini başlatır. Bunlar çağrılmazsa runtime cihaz 0'ı kullanır ve ilk API çağrısında kendini başlatır (o çağrı yavaş olur, hata kodu da o çağrıdan gelir). 12.0 öncesi: başlatmayı ayırmak için cudaFree(0).
  • Context oluşturulurken gerekirse device kodu JIT ile derlenip cihaz belleğine yüklenir.
  • GPU yardımcı işlemcidir; işletim sistemini CPU başlatır, "şovu CPU yönetir".
  • Süre ölçerken: (1) GPU önceden başlatılmış olmalı (soğuk çalıştırma olmasın), (2) kod bitmiş olmalı. Kernel başlatmaları asenkrondur: kernel'den sonra, süreyi almadan önce cudaDeviceSynchronize(). (Yoksa "mucizevi derecede kısa" süreler ölçersiniz.) Örnek: texRotate.cu 100 tekrarın her birinde kernel + cudaDeviceSynchronize() süresini ölçüp ortalamasını alır.

Bellek sınırları ve etkileri

  • Register sınırı, yüksek performansla (spill olmadan) çalışabilecek thread sayısını doğrudan etkiler.
  • Shared bellek sınırı, SM'de yerleşebilecek blok sayısını doğrudan (thread sayısını dolaylı) etkiler.
  • Özet: thread başına ne kadar çok bellek gerekirse SM'de (ve tüm işlemcide) o kadar az thread yerleşebilir.

G80: 16 SM, SM başına 8K = 8192 register → toplam 128K = 131.072. Çok gibi görünür ama SM başına 768 thread'i doldurmak için thread başına sadece 8192/768 ≈ 10 register.

Register spill: derlenen kod (maks. register / thread sayısı)'ndan fazla register kullanırsa kernel yine çalışır ama fazlası local memory'ye (= global bellek, thread'e özel) taşar → performans düşer. Register sayısını görmek: --ptxas-options=-v.

Shared: G80'de SM başına 16 KB, en fazla 8 blok → maksimuma ulaşmak için blok başına ≤ 2 KB. 2 KB'tan fazla kullanılırsa SM'deki blok sayısı toplam 16 KB'ı aşmayacak kadar olur.

Matmul: 16×16 tile → Mds 16·16·4 = 1 KB + Nds 1 KB = 2 KB/blok → 8 blok sığar (zaten G80 sınırı). Ama asıl sınır SM başına 768 thread: 768 / 256 = 3 blok → shared'ın sadece 3·2 = 6 KB'ı kullanılır. Bu sınırların hepsi cihaza bağlıdır.

Mimari listesi (2023 itibarıyla ~20 tür): Tesla (1.0, 1.1), Fermi (2.0, 3.0), Kepler (3.0, 3.5, 3.7), Maxwell (5.0, 5.2, 5.3), Pascal (6.0, 6.1, 6.2), Volta (7.0, 7.2), Turing (7.5), Ampere (8.0, 8.6, 8.7), Lovelace (8.9). Bellek davranışları cihaza bağlı: her zaman kullandığınız cihazın özelliklerini bilin.

Global bellek

Verimli erişim için dört ana nokta (slayt 35):

  1. Erişimleri coalesce edin.
  2. Bayt hizalamasına dikkat edin (pitch'li erişimler).
  3. Büyük gruplar hâlinde okuyup yazın.
  4. Shared memory kullanın.

Ayrıntılar, segment hesapları, pitch ve transpose: Coalescing sayfası. Kısaca: cudaMalloc adresleri en az 256 bayta hizalıdır; ama 2D bir dizide bir sonraki satırın başı genişliğe bağlıdır, bu yüzden cudaMallocPitch/cudaMalloc3D satırları doldurup pitch döndürür. Adreslenebilir belleğe (global, local, shared, constant, texture) erişen bir komut, adreslerin warp'taki dağılımına göre birkaç kez yeniden verilmek (re-issue) zorunda kalabilir.

cudaExtent extent = make_cudaExtent(width * sizeof(float), height, depth);
cudaPitchedPtr devPitchedPtr;
cudaMalloc3D(&devPitchedPtr, extent);

__global__ void MyKernel(cudaPitchedPtr devPitchedPtr, int width, int height, int depth) {
    char* devPtr = (char*)devPitchedPtr.ptr;
    size_t pitch = devPitchedPtr.pitch;
    size_t slicePitch = pitch * height;
    for (int z = 0; z < depth; ++z) {
        char* slice = devPtr + z * slicePitch;
        for (int y = 0; y < height; ++y) {
            float* row = (float*)(slice + y * pitch);
            for (int x = 0; x < width; ++x) { float element = row[x]; }
        }
    }
}

Local memory

  • Sadece bazı otomatik değişkenler local memory'ye gider: (1) sabit indekslendiği belirlenemeyen diziler, (2) çok register yiyecek büyük struct/diziler, (3) kernel mevcut register'dan fazlasını kullanıyorsa herhangi bir değişken (register spilling).
  • PTX'te (-ptx veya -keep) .local ile bildirilip ld.local/st.local ile erişilir. Sonraki derleme aşamaları yine de karar değiştirebilir: cuobjdump ile cubin'e bakın; --ptxas-options=-v toplam local kullanımını (lmem) raporlar. Bazı matematik fonksiyonları da local memory kullanabilir.
  • Cihaz belleğinde durur: global kadar yüksek gecikme, düşük bant genişliği, aynı coalescing kuralları. Ama ardışık 32-bit kelimeler ardışık thread ID'lerine düşecek şekilde düzenlenmiştir: warp'taki tüm thread'ler aynı göreli adrese (aynı dizi indeksi, aynı struct üyesi) erişirse tam coalesced. 5.x ve sonrası: L2'de önbelleklenir.

Shared memory

  • On-chip; local/global'den çok daha yüksek bant genişliği, çok daha düşük gecikme.
  • Kullanımı senkronizasyonla birlikte gelir (__syncthreads()). Kullanılan miktar SM başına blok sayısını doğrudan etkiler.
  • Global bellek erişiminin aksine, shared erişimi gecikmeyi gizlemek için başka bir hazır warp'ın çalışmasına yol açmaz.
  • Kullanımı ve tiled matmul: L5.

Bank'lar ve bank conflict'ler finalde

Duyuru: "Shared memory bank optimization bu sınava dahil değil." Bilgi için kısa özet:

  • Yüksek bant genişliği için shared bellek eşit boyutlu, aynı anda erişilebilen 32 bank'a bölünür; ardışık 4 baytlık (yeni mimarilerde 8 bayt) parçalar ardışık bank'lara atanır.
  • n farklı bank'a düşen n adres aynı anda servis edilir. İki adres aynı bank'a düşerse bank conflict: istek çakışmasız parçalara bölünüp seri yapılır (n-yollu conflict → throughput / n).
  • Stride 1 ve stride 3 (tek sayı) çakışmasız; stride 2 iki-yollu conflict. Aynı kelimeyi okuyan thread'ler çakışma yaratmaz (broadcast).
  • Çözüm: padding (ör. tile[32][33]).

L2 önbellek kontrolü

Bir kernel global bellekteki bir bölgeye tekrar tekrar erişiyorsa bu erişimler persisting, bir kez erişiyorsa streaming'dir. CUDA 11.0 ve compute capability 8.0+ ile L2'nin bir kısmı persisting erişimlere ayrılabilir; normal/streaming erişimler o kısmı ancak boşsa kullanır.

Constant memory

  • Cihaz belleğinde (global) durur, salt okunur constant cache'te önbelleklenir.
  • Bir istek, içindeki farklı adres sayısı kadar ayrı isteğe bölünür (throughput o oranda düşer); cache hit'te constant cache hızında, değilse cihaz belleği hızında servis edilir.
  • En iyi senaryo: tüm thread'ler aynı adresi okur (global belleğin tersi: orada ardışık adresler iyi).
__constant__ float constData[256];          // fonksiyonların dışında
float data[256];                             // host tarafındaki tampon
cudaMemcpyToSymbol(constData, data, sizeof(data));   // kernel'den önce kopyala

Texture memory 2. vizede yok

Texture memory 2. vize kapsamında değil. Bu bölüm sadece bilgi ve sonrası için.

  • GPU'nun grafik için kullandığı texture donanımının bir alt kümesi. Texture salt okunur; surface yazılabilen texture gibidir.
  • Cihaz belleğinde durur, texture cache'te önbelleklenir: fetch sadece cache miss'te bir cihaz belleği okumasına mal olur. Cache 2D uzamsal yerellik için optimize: 2D'de birbirine yakın adresleri okuyan warp en iyi performansı alır. Sabit gecikmeli akış için tasarlanmıştır: hit DRAM trafiğini azaltır, gecikmeyi değil.
  • Faydalar: global/constant'ın erişim desenine uymayan ama yerelliği olan okumalarda daha yüksek bant genişliği; adres hesapları kernel dışında özel birimlerde (daha az register); paketlenmiş verinin tek işlemde ayrı değişkenlere dağıtılması; 8/16-bit tamsayıların isteğe bağlı olarak [0, 1] / [-1, 1] aralığında float'a çevrilmesi; ücretsiz doğrusal filtreleme ve sınır dışı işleme.
  • Dezavantajlar: yazılamaz; doğrusal belleği texturing için bir CUDA array'e kopyalamak gerekir ve bu zaman alır: sonraki hesap buna değmeli.

Texture object

Texture'dan okumaya texture fetch denir; her fetch bir texture object alır. Texture object şunları belirtir:

ÖzellikSeçenekler
TextureFetch edilen texture bellek parçası (cudaResourceDesc).
Boyut1D, 2D, 3D (1/2/3 koordinat); elemanlara texel denir.
Texel tipiTemel tamsayı ve kayan nokta tipleri; char/short/int/long/longlong/float/double'dan 1-, 2-, 4-bileşenli vektörler.
Okuma moducudaReadModeElementType (dönüşüm yok) / cudaReadModeNormalizedFloat (8/16-bit tamsayı → işaretsizse [0, 1], işaretliyse [-1, 1]).
KoordinatlarVarsayılan [0, N-1]; normalize edilmişse [0, 1-1/N] (64×32 texture: [0,63]×[0,31] yerine iki yönde de [0, 1)). Boyuttan bağımsız koordinat isteyen uygulamalar için.
Adresleme modu (sınır dışı)cudaAddressModeClamp (varsayılan; kenar pikselini tekrarla), Border (sıfır), Wrap (sar), Mirror (ayna). Wrap ve mirror sadece normalize koordinatlarla. Her koordinat için ayrı (3 elemanlı dizi).
FiltrelemecudaFilterModePoint (en yakın texel) / cudaFilterModeLinear (1D'de 2, 2D'de 4, 3D'de 8 texel'in doğrusal/bilineer/trilineer interpolasyonu; sadece float dönüşte, düşük hassasiyetli).

CUDA array: texture fetch için optimize edilmiş, opak (değerlere doğrudan erişilemez) 1D/2D/3D bellek düzeni; 1, 2 veya 4 bileşenli elemanlar (8/16/32-bit tamsayı, 16/32-bit float). Kernel'ler sadece texture fetch (okuma) veya surface okuma/yazma ile erişir.

// Host: 1) CUDA array ayır  2) veriyi kopyala  3) resDesc  4) texDesc  5) texture object oluştur
cudaChannelFormatDesc ch = cudaCreateChannelDesc(32, 0, 0, 0, cudaChannelFormatKindFloat);
cudaArray_t cuArray;
cudaMallocArray(&cuArray, &ch, width, height);
cudaMemcpy2DToArray(cuArray, 0, 0, img, width * sizeof(float), width * sizeof(float), height,
                    cudaMemcpyHostToDevice);

cudaResourceDesc resDesc = {};  resDesc.resType = cudaResourceTypeArray;  resDesc.res.array.array = cuArray;
cudaTextureDesc texDesc = {};
texDesc.addressMode[0] = cudaAddressModeWrap;   texDesc.addressMode[1] = cudaAddressModeWrap;
texDesc.filterMode = cudaFilterModeLinear;      // bilineer interpolasyon bedava
texDesc.readMode = cudaReadModeElementType;
texDesc.normalizedCoords = 1;                   // koordinatlar [0, 1)
cudaTextureObject_t texObj = 0;
cudaCreateTextureObject(&texObj, &resDesc, &texDesc, NULL);

// Device: normalize koordinatı merkez etrafında θ kadar döndür, texture'dan oku
__global__ void transformKernel(float* output, cudaTextureObject_t texObj, int width, int height, float theta) {
    unsigned int x = blockIdx.x * blockDim.x + threadIdx.x;
    unsigned int y = blockIdx.y * blockDim.y + threadIdx.y;
    if (x < width && y < height) {
        float u = x / (float)width - 0.5f, v = y / (float)height - 0.5f;
        float tu = u * cosf(theta) - v * sinf(theta) + 0.5f;
        float tv = v * cosf(theta) + u * sinf(theta) + 0.5f;
        output[y * width + x] = tex2D(texObj, tu, tv);
    }
}
// dim3 block(16, 16); dim3 grid((width + 15) / 16, (height + 15) / 16);

Device tarafında okuma: doğrusal bellek texture'ları tex1Dfetch(), array texture'ları tex1D(), tex2D(), tex3D(). Yönetim fonksiyonları: cudaMallocArray, cudaFreeArray, cudaMemcpyToArray, cudaMemcpyFromArray. Eski texture reference API'de tip, boyut ve okuma modu derleme zamanında sabit; normalize, filtre ve adres modu çalışma zamanında değiştirilebilir (sadece CUDA array texture'ları).

Sınama

Compute capability 8.6'lı bir GPU, sadece -gencode arch=compute_70,code=sm_70 ile derlenmiş bir uygulamayı çalıştırabilir mi?

  1. Evet, sm_70 ikilisi 8.6'da çalışır.
  2. Hayır: ikili major sürümler arasında uyumlu değil ve gömülü PTX yok.
  3. Evet, sürücü sm_70 ikilisini JIT ile yeniden derler.
  4. Sadece aynı sürücü sürümüyle derlendiyse.

Kernel süresini ölçerken neden cudaDeviceSynchronize() gerekir?

  1. Bellek ayırmayı tamamlamak için.
  2. cudaMemcpy asenkron olduğu için.
  3. Blokları birbirine senkronize etmek için.
  4. Kernel başlatmaları asenkron; bitmesini beklemeden süre alınırsa çok kısa (yanlış) çıkar.

Hangisi local memory'ye konma ihtimali en yüksek değişkendir?

  1. Çalışma zamanında hesaplanan bir indeksle erişilen otomatik dizi.
  2. Bir int döngü sayacı.
  3. Bir __shared__ dizi.
  4. Bir __constant__ dizi.

cudaMallocPitch ile 700 baytlık satırlar ayrıldı (256 B hizalama). r. satırın başına nasıl ulaşılır?

  1. (float*)((char*)p + r * 700)
  2. p + r * pitch
  3. (float*)((char*)p + r * pitch), pitch = 768
  4. (float*)((char*)p + r * 512)

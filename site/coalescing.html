Coalescing, transpose, unrolling

Bir warp'ın 32 thread'i global belleğe aynı anda gider. Adresleri yan yana ise donanım hepsini tek bir büyük okumada karşılar; dağınıksa aynı veri için defalarca okuma yapar. 2. vizenin en önemli performans konusu bu.

  • Bir erişim deseni için kaç tane 32/128 baytlık segmente dokunulduğunu ve verimi hesaplamak.
  • Bir kodun coalesced olup olmadığını threadIdx.x'in adreste nerede durduğuna bakarak söylemek.
  • Naive transpose'un neden yavaş olduğunu ve shared memory karosuyla nasıl düzeltildiğini indeks indeks açıklamak.
  • Loop unrolling'in ne kazandırdığını ve maliyetini söylemek.

Global bellek transaction'ları

Lecture 6, slayt 43–48:

  • En yüksek performans için global bellek erişimleri coalesced (birleştirilmiş) olmalı.
  • Global bellek 32, 64 veya 128 baytlık transaction'larla erişilir. Her erişim bu parçalara oturtulur: "11 bayt okumak" diye bir şey yoktur, 32 bayt okursunuz.
  • Bir bellek bölgesi, ilk adresi N'nin katıysa N bayta hizalıdır. Sadece kendi boyutuna hizalı 32/64/128 B segmentler okunup yazılabilir. 33 bayt okursanız iki tane 32 B erişim olur.
  • Bir warp global belleğe erişen bir komutu çalıştırdığında, thread'lerin erişimlerini bir veya daha fazla transaction'a birleştirir. Kaç tane olacağını belirleyen iki şey: (1) her thread'in eriştiği kelimenin boyu, (2) adreslerin thread'lere dağılımı.
  • Ne kadar çok transaction gerekirse, thread'lerin istemediği o kadar çok kelime de taşınır ve komut verimi o oranda düşer. Genel kural: adresler ne kadar dağınıksa throughput o kadar düşük.

Slayt 47: neden "throughput / 8"?

  • 32 thread rastgele adreslerden 4'er bayt okur → her thread için ayrı bir 32 B transaction (en küçük parça) → 32 × 32 B = 1024 B okunur.
  • 32 thread ardışık adreslerden 4'er bayt okur ve başlangıç 128 B hizalı → 32 × 4 = 128 B = tek bir 128 B transaction.
  • 1024 / 128 = 8 kat fazla veri → etkin bant genişliği / 8.

Temel hizalama şartı

  • Global bellek komutları thread başına 1, 2, 4, 8 veya 16 baytlık kelimeleri okuyup yazabilir.
  • Global bellekteki bir veriye erişim ancak ve ancak (1) veri tipinin boyu 1, 2, 4, 8 veya 16 bayt ve (2) veri doğal hizalı (adresi boyutunun katı) ise tek bir komuta derlenir. Değilse birden fazla komuta bölünür ve bunlar tam coalesce olamaz.
  • char, short, int, long, long long, float, double, float2, float4 gibi yerleşik tipler bu şartı otomatik sağlar. Struct'lar için derleyiciye __align__(8) veya __align__(16) ile zorlatılır:
struct __align__(8)  { float x; float y; };            // 8 bayt, 8'e hizalı → tek 8 B load
struct __align__(16) { float x; float y; float z; };   // 12 bayt veri, 16'ya yuvarlanır → tek 16 B load
  • cudaMalloc ve diğer ayırma fonksiyonlarının döndürdüğü adresler en az 256 bayta hizalıdır.
  • Çoklu dizi tuzağı (slayt 52–53): birkaç cudaMalloc yerine tek büyük blok ayırıp içini dizilere bölerseniz, her dizinin başlangıcı bloğun başından kaydırılmış olur. Bir float dizisinin ardından gelen float2 dizisi 4 B'ye hizalıdır ama 8 B'ye hizalı olması garanti değildir. 8/16 baytlık kelimeleri hizasız okumak yanlış sonuç verir (birkaç kelime kayma).

Kodda coalescing'i görmenin kısa yolu: adres ifadesinde threadIdx.x'in (ya da ondan türeyen col/x'in) çarpansız, en sağda durup durmadığına bakın. A[row*width + col] ✓; A[col*width + row] ✗ (ardışık thread'ler width eleman aralıklı); A[2*col] yarı verim.

2D diziler ve pitch

  • Yaygın desen: (tx, ty) thread'i BaseAddress + width·ty + tx adresine erişir. Tam coalescing için hem thread bloğunun genişliği hem de dizinin genişliği warp boyunun (32) katı olmalı.
  • Genişliği 32'nin katı olmayan bir dizi, en yakın 32 katına yuvarlanmış genişlikle ayrılıp satırları doldurulursa (padding) çok daha verimli erişilir. Bunu donanımdan bağımsız yapan fonksiyonlar: cudaMallocPitch() (2D), cudaMalloc3D() (3D). Doğru stride'ı (pitch) hesaplayıp döndürürler; elemanlara erişirken bu pitch kullanılmalı.
  • Kopyalama: cudaMallocPitch ile ayrılan bellek cudaMemcpy2D, cudaMalloc3D ile ayrılan cudaMemcpy3D ile kopyalanır.
// Host
int width = 64, height = 64;
float* devPtr; size_t pitch;
cudaMallocPitch(&devPtr, &pitch, width * sizeof(float), height);
MyKernel<<<100, 512>>>(devPtr, pitch, width, height);

// Device: pitch BAYT cinsinden → önce char*'a çevirip satır başını bul
__global__ void MyKernel(float* devPtr, size_t pitch, int width, int height) {
    for (int r = 0; r < height; ++r) {
        float* row = (float*)((char*)devPtr + r * pitch);
        for (int c = 0; c < width; ++c) { float element = row[c]; }
    }
}

// Kopyalama
cudaMemcpy2D(devPtr, devPitch,            // hedef ve pitch'i (GPU)
             hostPtr, hostPitch,          // kaynak ve pitch'i (CPU), genelde Ncols*sizeof(float)
             Ncols * sizeof(float), Nrows,// satır başına BAYT, satır sayısı
             cudaMemcpyHostToDevice);

Pitch örnekleri (256 B hizalama): genişlik 5, 50, 250 B → pitch 256; 500 B → 512; 700 B → 768.

Matris transpose derste

Hocanın derste verdiği örnek; NVIDIA'nın "An Efficient Matrix Transpose in CUDA C/C++" yazısındaki kernel serisi. Transpose hiç hesap yapmaz, sadece veri taşır: performansı tamamen bellek erişim desenine bağlıdır. Bu yüzden coalescing'i göstermek için en iyi örnek.

Kurulum: 32×32 karo, 32×8 thread

  • TILE_DIM = 32, BLOCK_ROWS = 8. Her blok matrisin bir 32×32 karosunu işler ama 32×8 = 256 thread'i vardır.
  • Bu yüzden her thread karo içinde 4 eleman işler (32/8): satır y, y+8, y+16, y+24. Döngü ikinci indeks (satır) üzerinde döner, böylece bir warp'ın ardışık thread'leri hâlâ ardışık adreslere gider. Faydası: indeks hesabının maliyeti 4 elemana bölünür.
  • Grid: N×N matris için dim3(N/32, N/32), blok: dim3(TILE_DIM, BLOCK_ROWS) = dim3(32, 8).

1) Referans: copy

const int TILE_DIM = 32;
const int BLOCK_ROWS = 8;

__global__ void copy(float* odata, const float* idata)
{
    int x = blockIdx.x * TILE_DIM + threadIdx.x;
    int y = blockIdx.y * TILE_DIM + threadIdx.y;   // TILE_DIM ile, blockDim.y ile değil!
    int width = gridDim.x * TILE_DIM;
    for (int j = 0; j < TILE_DIM; j += BLOCK_ROWS)
        odata[(y + j) * width + x] = idata[(y + j) * width + x];
}
// dim3 grid(N / TILE_DIM, N / TILE_DIM), block(TILE_DIM, BLOCK_ROWS);

Okuma da yazma da coalesced: bir warp = bir satırdaki 32 ardışık float = 128 B. Transpose ne kadar hızlı olursa olsun bu kernelden hızlı olamaz; ölçüm için "tavan".

Hocanın tavsiyesiyle aynı fikir: önce hesap yapmayan bir kopya kernel'i yazın, çıktının girdiye eşit olduğunu (ve hızını) görün; sonra asıl işlemi ekleyin. Shared memory'li versiyonda da önce copySharedMem (global → shared → global, aynı yere) yazılıp indeksler doğrulanır.

2) Naive transpose

__global__ void transposeNaive(float* odata, const float* idata)
{
    int x = blockIdx.x * TILE_DIM + threadIdx.x;
    int y = blockIdx.y * TILE_DIM + threadIdx.y;
    int width = gridDim.x * TILE_DIM;
    for (int j = 0; j < TILE_DIM; j += BLOCK_ROWS)
        odata[x * width + (y + j)] = idata[(y + j) * width + x];
}
  • Okuma idata[(y+j)*width + x]: x en sağda, çarpansız → warp 128 B'lık tek satır okur ✓.
  • Yazma odata[x*width + (y+j)]: x width ile çarpılmış → ardışık thread'ler width eleman aralıklı. 1024×1024 matriste aralık 1024 float = 4096 B → warp'ın 32 yazması 32 ayrı segment. Coalesced değil.
  • Laboratuvardaki a[i*1024] örneği tam olarak bu yazma.

3) Shared memory ile coalesced transpose

Fikir: karoyu global bellekten satır satır (coalesced) okuyup shared memory'ye koy; yer değiştirmeyi shared memory içinde yap (orada dağınık erişim ucuz); sonra karonun sütununu çıktıda satır olarak (coalesced) yaz. Blok da transpoze edilmiş yere yazmalı.

__global__ void transposeCoalesced(float* odata, const float* idata)
{
    __shared__ float tile[TILE_DIM][TILE_DIM];

    int x = blockIdx.x * TILE_DIM + threadIdx.x;
    int y = blockIdx.y * TILE_DIM + threadIdx.y;
    int width = gridDim.x * TILE_DIM;

    for (int j = 0; j < TILE_DIM; j += BLOCK_ROWS)
        tile[threadIdx.y + j][threadIdx.x] = idata[(y + j) * width + x];   // coalesced okuma

    __syncthreads();   // thread'ler okuduklarından FARKLI elemanları yazacak: karo tamamen dolmalı

    x = blockIdx.y * TILE_DIM + threadIdx.x;   // transpoze blok konumu: bx ↔ by
    y = blockIdx.x * TILE_DIM + threadIdx.y;

    for (int j = 0; j < TILE_DIM; j += BLOCK_ROWS)
        odata[(y + j) * width + x] = tile[threadIdx.x][threadIdx.y + j];   // coalesced yazma
}

İndeks takibi (N = 1024, grid 32×32, blok 32×8): blockIdx = (1, 2), threadIdx = (5, 3).

  • Yükleme: x = 1·32 + 5 = 37, y = 2·32 + 3 = 67. j = 0, 8, 16, 24 için idata'nın satır 67, 75, 83, 91 / sütun 37'sini okuyup tile[3][5], tile[11][5], tile[19][5], tile[27][5]'e koyar. Bu blok girdinin satır 64–95, sütun 32–63 karosunu yükler.
  • Yazma: x = 2·32 + 5 = 69, y = 1·32 + 3 = 35. odata'nın satır 35, 43, 51, 59 / sütun 69'una tile[5][3], tile[5][11], tile[5][19], tile[5][27]'yi yazar. Kontrol: tile[5][3] = girdi (satır 64+5, sütun 32+3) = idata[69][35] → odata[35][69] ✓.
  • Warp'taki ardışık thread'ler (threadIdx.x = 0..31) hem okumada hem yazmada ardışık global adreslere gider; dağınık kısım (tile[threadIdx.x][…], sütun okuma) shared memory'de.

Buradaki __syncthreads() zorunlu: bir thread'in yazdığı tile[threadIdx.x][threadIdx.y+j] başka bir thread (hatta başka bir warp) tarafından yüklendi. Sadece kopya yapan copySharedMem'de her thread kendi yüklediğini yazdığı için bariyer teknik olarak gereksizdir (yazıda sadece karşılaştırma için konmuş); ölçümler bariyerin darboğaz olmadığını gösterir.

4) Bank conflict'siz versiyon finalde

32×32 karoda bir sütunun tüm elemanları aynı shared memory bank'ına düşer; sütun okumak (tile[threadIdx.x][…]) 32-yollu bank conflict'tir. Çözüm tek satır: __shared__ float tile[TILE_DIM][TILE_DIM + 1]; (her satır bir bank kayar). Bank optimizasyonu bu sınavda yok; sadece neden var olduğunu bilmek yeter.

Loop unrolling derste

Döngü gövdesini birkaç kez kopyalayıp döngü sayısını azaltmak. Her döngü turunda "asıl iş"in yanında sayaç artırma, karşılaştırma ve dallanma komutları da çalışır; GPU'da bunlar da komut slotu yer. Unrolling bu ek yükü azaltır ve bağımsız komutları yan yana getirerek komut düzeyi paralelliği (ILP) artırır.

float sum = 0;
for (int k = 0; k < 16; ++k)
    sum += Mds[ty][k] * Nds[k][tx];
// 16 tur × (çarp-topla + k++ + k<16 + dallanma)

float sum = 0;
for (int k = 0; k < 16; k += 4) {
    sum += Mds[ty][k]     * Nds[k][tx];
    sum += Mds[ty][k + 1] * Nds[k + 1][tx];
    sum += Mds[ty][k + 2] * Nds[k + 2][tx];
    sum += Mds[ty][k + 3] * Nds[k + 3][tx];
}
// 4 tur: döngü kontrolü 4 kat azaldı

#pragma unroll                 // döngü sayısı derleme zamanında belliyse tamamen açar
for (int k = 0; k < TILE_WIDTH; ++k)      // TILE_WIDTH bir #define / const → sabit
    Pvalue += Mds[ty][k] * Nds[k][tx];

#pragma unroll 4               // 4 kat aç
for (int i = 0; i < n; ++i) { ... }

#pragma unroll 1               // açma
  • Kazanç: daha az döngü kontrol komutu; tam açılınca indeksler sabit olur (Mds[ty][3] gibi) ve adres hesapları derleme zamanında yapılır; bağımsız load'lar art arda verilip gecikme gizlenir.
  • Maliyet: kod büyür; aynı anda canlı değişken sayısı artar → register kullanımı artar → thread başına register sınırı aşılırsa register spill (local memory) ya da SM başına daha az thread (occupancy düşer).
  • Döngü sayısı sabitse (transpose'daki j döngüsü: TILE_DIM/BLOCK_ROWS = 4 tur; tiled matmul'deki k döngüsü: TILE_WIDTH tur) derleyici genelde zaten açar. Döngü sayısı çalışma zamanında belliyse (width/TILE_WIDTH) tam açılamaz.
  • Bağlantı: L6'daki "local memory" slaytı. Sabit olmayan indekslerle erişilen diziler register yerine local memory'ye konur; unrolling indeksleri sabitlediği için diziyi register'da tutmayı mümkün kılabilir.

Sınama

Bir warp 128 B hizalı bir float dizisinden a[3*threadIdx.x] okuyor. Kaç tane 32 B segmente dokunulur?

  1. 4
  2. 12
  3. 32
  4. 3
Taşınan 12·32 = 384 B, kullanılan 128 B → verim 1/3.

Transpose kernellerinde blok neden 32×32 değil de 32×8 thread?

  1. 32×32 blok başlatılamaz.
  2. Bank conflict'leri önlemek için.
  3. Her thread karoda 4 eleman işlesin, indeks hesabının maliyeti paylaşılsın diye.
  4. Shared bellekten tasarruf için.

transposeCoalesced'da yazma aşamasında neden x = blockIdx.y*TILE_DIM + threadIdx.x kullanılıyor?

  1. Girdideki (bx, by) karosu çıktıda transpoze konuma, (by, bx)'e yazılmalı.
  2. Bank conflict'leri azaltmak için.
  3. Okumayı coalesced yapmak için.
  4. Bir yazım hatası; blockIdx.x olmalı.

#pragma unroll için hangisi doğru?

  1. Döngü turlarını farklı thread'lere dağıtır.
  2. Register kullanımını azaltır.
  3. Sonucu değiştirebilir, dikkat edilmeli.
  4. Döngü sayısı derleme zamanında sabitse döngüyü tamamen açabilir.

Kernel, indeks, shared memory

İç içe for döngüleri GPU'da nereye gider? Her thread kendi verisini nasıl bulur? Ve aynı veriyi tekrar tekrar global bellekten okumak neden kernel'i %6 verime mahkûm eder?

  • Bir CPU döngüsünü kernel'e çevirmek: host tarafı (ayır, kopyala, başlat, geri kopyala, serbest bırak) ve device tarafı.
  • blockIdx, blockDim, threadIdx'ten satır/sütun hesaplamak.
  • __syncthreads()'in kuralları; warp'lar ve latency hiding.
  • CGMA'yı hesaplayıp tiling'in global trafiği neden T kat azalttığını göstermek; tiled matmul kernel'ini yazmak.

Veri paralelliği: döngüden kernel'e

Veri paralelliği: bağımsız veri elemanları üzerinde aynı işlemin aynı anda yapılması (vektör toplama, konvolüsyon, matris-vektör ve matris-matris çarpımı). Pratik kural: düzenli indekslenen iç içe for döngüleri gördüğünüzde büyük ihtimalle paralelleştirilebilir.

for (int i = 0; i < N; i++)
    C[i] = A[i] + B[i];

__global__ void VecAdd(float* A, float* B, float* C) {
    int i = threadIdx.x;
    C[i] = A[i] + B[i];
}
// VecAdd<<<1, N>>>(A, B, C);   // 1 blok, N thread

for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        C[i*N + j] = A[i*N + j] + B[i*N + j];

__global__ void MatAdd(float* A, float* B, float* C) {
    const int i = threadIdx.y * blockDim.x + threadIdx.x;
    C[i] = A[i] + B[i];
}
// dim3 threadsPerBlock(N, N);
// MatAdd<<<1, threadsPerBlock>>>(A, B, C);

Matris çarpımı: CPU versiyonu

void MatrixMultiplication(float* M, float* N, float* P, int width) {
    for (int i = 0; i < width; ++i)
        for (int j = 0; j < width; ++j) {
            float sum = 0;
            for (int k = 0; k < width; ++k)
                sum += M[i*width + k] * N[k*width + j];
            P[i*width + j] = sum;
        }
}

Çıktıdan başlayın: bir çıktı elemanı = bir iç çarpım = bir for döngüsü, ve komşu çıktı elemanları birbirinden bağımsız. Yani her thread bir P[i][j] hesaplayabilir; dıştaki iki döngü thread'lere dönüşür, içteki k döngüsü thread'in içinde kalır.

Host tarafı: ayır, kopyala, başlat

GPU bir yardımcı işlemcidir (coprocessor): paralel işi ona aktarırız (offload), sonucu geri kopyalayıp devam ederiz. Kernel asıl GPU kodu; gerisi kurulum ve host (CPU) tarafından çalıştırılır.

void cuMatrixMultiplication(float* M, float* N, float* P, int width)
{
    int size = width * width * sizeof(float);
    float *Md, *Nd, *Pd;
    // 1. cihazda bellek ayır
    cudaMalloc((void**)&Md, size);
    cudaMalloc((void**)&Nd, size);
    cudaMalloc((void**)&Pd, size);
    // 2. girdileri cihaza kopyala
    cudaMemcpy(Md, M, size, cudaMemcpyHostToDevice);
    cudaMemcpy(Nd, N, size, cudaMemcpyHostToDevice);
    // 3. kernel'i başlat
    dim3 dimBlock(TILE_WIDTH, TILE_WIDTH);
    dim3 dimGrid(width / TILE_WIDTH, width / TILE_WIDTH);
    MatMulKernel<<>>(Md, Nd, Pd, width);
    // 4. sonucu host'a geri kopyala
    cudaMemcpy(P, Pd, size, cudaMemcpyDeviceToHost);
    // 5. cihaz belleğini serbest bırak
    cudaFree(Md); cudaFree(Nd); cudaFree(Pd);
}
  • cudaMalloc(void** devPtr, size_t size): ilk parametre pointer değişkeninin adresi (fonksiyon ayrılan adresi oraya yazar), (void**)'a çevrilir çünkü fonksiyon tipten bağımsızdır. İkinci parametre bayt cinsinden boyut (C'deki malloc gibi).
  • cudaFree(void* devPtr): cudaMalloc ile ayrılanı serbest bırakır.
  • cudaMemcpy(hedef, kaynak, bayt, tür): tür cudaMemcpyHostToHost / HostToDevice / DeviceToDevice / DeviceToHost. Senkrondur (bloklar, bitene kadar dönmez); asenkron versiyonları da var.
  • Kernel başlatma ise asenkrondur: süre ölçerken cudaDeviceSynchronize() ile bitmesini bekleyin (L6).

Slayttaki float* Md, Nd, Pd; satırı C'de sadece Md'yi pointer yapar (Nd, Pd düz float olur). Doğrusu float *Md, *Nd, *Pd;. Sınavda kod yazarken dikkat.

Kernel ve fonksiyon niteleyicileri

Kernel, tüm thread'lerin çalıştıracağı kodu tanımlar. SIMT (Single Instruction Multiple Threads): thread'ler aynı komutu görür ama komutun parametreleri her thread'in kendi register'larından gelir, bu yüzden farklı thread'ler farklı iş yapabilir. threadIdx, thread'in kendini ayırt edip verinin kendisine düşen kısmına yönelmesini sağlar (donanım register'larından okunan önceden tanımlı değişkenler).

Niteleyici yazılmazsa fonksiyon __host__ sayılır. __global__ kernel demektir, void döner.

__global__ void MatMulKernel(float* Md, float* Nd, float* Pd, int width)
{
    int tx = threadIdx.x;
    int ty = threadIdx.y;
    float sum = 0;
    for (int i = 0; i < width; i++)
        sum += Md[ty * width + i] * Nd[i * width + tx];
    Pd[ty * width + tx] = sum;
}
// dim3 blockDim(width, width); dim3 gridDim(1, 1);

Döngüler nerede? Dıştaki i ve j döngüleri gitti: yerlerini ty (satır) ve tx (sütun) aldı. İç çarpım döngüsü kaldı.

Sorunu: sadece bir blok kullanıyor, yani matris en fazla blok başına thread sınırı kadar elemanlı olabilir (eski GPU'larda 512 → 16×16; yenilerde 1024 → 32×32). Daha fazla blok kullansak bile aynı threadIdx'e sahip farklı bloklardaki thread'ler aynı Pd elemanını hesaplardı, çünkü blockIdx kullanılmıyor.

Thread blokları ve indeksleme

  • Bir kernel başlatılınca paralel thread'lerden oluşan bir grid olarak çalışır (binlerce-milyonlarca hafif thread).
  • İki seviyeli hiyerarşi: grid → bir veya daha fazla thread bloğu; grid'deki tüm blokların thread sayısı aynıdır. Her bloğun blockIdx koordinatı var (compute 1.x'te 2D, 2.0+ 3D).
  • Her blok en fazla 512 (compute 1.x) / 1024 (2.0+) thread'lik 3D bir dizi; thread'in blok içindeki koordinatı threadIdx.
  • 1D örnek (slayt 31–33): N blok, her biri M thread → toplam N·M thread. Blok 0'ın 3. thread'i: 0·M + 3; Blok 5'in 3. thread'i: 5·M + 3. Genel: blockIdx.x * blockDim.x + threadIdx.x.
  • Girdi ve çıktı eşlemesi farklı olabilir: veriyi bir eşlemeyle okuyup başka bir eşlemeyle işleyip üçüncü bir eşlemeyle yazabilirsiniz (farklı girdi/çıktı oranları, shared memory hazırlığı, sınır koşulları).
__global__ void MatMulKernel(float* Md, float* Nd, float* Pd, int width)
{
    int row = blockIdx.y * TILE_WIDTH + threadIdx.y;
    int col = blockIdx.x * TILE_WIDTH + threadIdx.x;
    float sum = 0;
    for (int i = 0; i < width; i++)
        sum += Md[row * width + i] * Nd[i * width + col];
    Pd[row * width + col] = sum;
}

Burada TILE_WIDTH = blockDim.x = blockDim.y. Kendi konfigürasyonunuzla deneyin: laboratuvar.

Slayt 40'ın soruları. (1) Blokların çalışma sırasını zorlayabilir miyiz? Hayır. (2) Küçük ID'li bloğun büyük ID'liden önce başlayacağını varsayabilir miyiz? Hayır. (3) Bunun ölçeklenebilirlikle ilgisi? Bloklar bağımsız olduğu için çalışma zamanı onları istediği SM'ye, istediği sırada (round-robin) dağıtabilir; aynı program 2 SM'li GPU'da da 80 SM'li GPU'da da çalışır.

Dikkate alınması gereken sınırlar: blok başına en fazla thread, SM başına en fazla blok, SM başına en fazla thread. Genelde SM'lerde mümkün olduğunca çok thread'in yerleşik olması (occupancy) hedeflenir.

Senkronizasyon: __syncthreads()

  • Aynı bloktaki thread'ler faaliyetlerini bariyer senkronizasyonuyla koordine eder. Çağıran her thread, bloktaki tüm thread'ler o noktaya gelene kadar orada tutulur. Böylece bir sonraki faza geçmeden herkes önceki fazı bitirmiş olur. Tipik örnek: shared memory'yi doldurmak.
  • Gerçek hayat: işe aynı arabayla giden dört kişi. Masalarında paralel çalışırlar; dönüşte herkes arabaya gelene kadar beklenir (bariyer).
  • Bloktaki tüm thread'ler tarafından çalıştırılmalı. if/else içinde kullanmak tanımsız davranış; tek istisna koşulun bloktaki tüm thread'ler için aynı sonucu vermesi.
  • Gerçekte thread'leri değil, warp'ları senkronize eder.
  • Bekleme süreleri uzamasın diye çalışma zamanı bir bloğun tüm thread'lerini aynı SM'ye birlikte atar.
  • Bloklar arası senkronizasyon CUDA 9 öncesi neredeyse imkânsızdı (__threadfence() ile hileler: thread'i önceki shared/global yazmaları diğerlerine görünür olana kadar durdurur). CUDA 9 (Pascal) ile cooperative groups.

Blok atama, warp'lar, latency hiding

  • Kernel başlayınca çalışma zamanı grid'i oluşturur; thread'ler SM'lere blok blok atanır. GT200: 30 SM, SM başına en fazla 8 blok → aynı anda 240 blok; biten bloğun yerine listeden yenisi gelir.
  • SM başına izlenebilen thread sayısı da sınırlı: GT200'de SM başına 1024 thread (ör. 4 × 256 veya 8 × 128) → 30 · 1024 = 30.720 yerleşik thread.
  • Warp: ardışık threadIdx'li 32 thread; SM'de zamanlama birimi. Thread 0–31 ilk warp, 32–63 ikinci… Eşleme deterministik. 256 thread'lik blok = 8 warp; SM'de 3 blok = 24 warp.
  • "CUDA kodu yazmak için warp'ı bilmeniz gerekmez; yüksek performanslı CUDA kodu yazmak için gerekir."
  • Latency hiding: bir warp uzun gecikmeli bir işlemin (global bellek erişimi, pipeline'lı FP aritmetiği, dallanma) sonucunu beklerken seçilmez; hazır olan başka bir warp çalıştırılır. Seçim boş zaman eklemez: sıfır maliyetli thread zamanlaması. Yeterince warp varsa donanım her an çalıştıracak bir warp bulur.
  • Bu yüzden GPU'lar büyük önbelleklere ve dallanma tahminine CPU'lar kadar alan ayırmaz; o alanı FP birimlerine verir.

GT200 için matmul blok boyutu (1024 thread/SM, 8 blok/SM, 512 thread/blok):

  • 8×8 = 64 thread → SM'yi doldurmak için 16 blok gerekir ama sınır 8 → 8·64 = 512 thread: kaynaklar yarı boş, gecikmeyi gizleyecek warp az.
  • 16×16 = 256 thread → 1024/256 = 4 blok (8 sınırının altında) → tam kapasite ✓.
  • 32×32 = 1024 thread → blok başına 512 sınırını aşar ✗.

Sonuç: 16×16. (Henüz shared memory yok; olunca hesap karmaşıklaşır.)

Bellek erişim verimi: CGMA

  • Basit kernel donanımın potansiyelinin küçük bir kısmına ulaşır: thread'ler örtüşen girdi verisini tekrar tekrar global bellekten okur.
  • Global bellek = DRAM: yüzlerce saat çevrimi gecikme, sınırlı bant genişliği. Latency hiding iyidir ama herkes sürekli global belleğe gidiyorsa yetmez.
  • CGMA (compute to global memory access): bir bölgede global bellek erişimi başına yapılan FP işlem sayısı. Matmul iç döngüsünde her turda 2 global okuma, 1 çarpma + 1 toplama → CGMA = 1.
G80: 86,4 GB/s global bant genişliği 86,4 / 4 B = 21,6 milyar float/s yüklenebilir CGMA = 1 → en fazla 21,6 GFLOPS Tepe 367 GFLOPS → 21,6 / 367 ≈ %6 Daha yüksek performans için CGMA artırılmalı.

Tiling ile shared memory

Temel ödünleşim: global bellek büyük ama yavaş, shared bellek küçük ama hızlı. Strateji: veriyi her biri shared belleğe sığan karolara (tile) böl; karolar üzerindeki hesaplar birbirinden bağımsız yapılabilmeli. (Her veri yapısı her kernel için karolara bölünemez.)

Örtüşen erişimler

Slayttaki küçük örnek: dört 2×2 blokla P hesaplanıyor. Blok (0,0)'ın dört thread'i Pd0,0, Pd1,0, Pd0,1, Pd1,1'i hesaplar. Her thread Md'den 4, Nd'den 4 eleman okur ve thread(0,0) ile thread(1,0) Md'nin 0. satırının tamamını ikisi de okur. Blok (0,0) çalışırken her Md ve Nd elemanı tam iki kez okunur: thread'ler işbirliği yapıp her elemanı bir kez yüklerse global trafik yarıya iner.

Genel: N×N bloklarla olası azalma N kat. 16×16 → global trafik 1/16.

16×16 blok, shared memory YOK: 16·16 thread × (width + width) okuma = 16·16·2·width 16×16 blok, shared memory VAR: her eleman bir kez okunur = 16·width·2 Oran: (16·16·2·width) / (16·width·2) = 16

Slayt 86 ve 88: "16×8 ne olur?", "1024×1024 matris, 32×8 blok?" BX×BY'lik bir blok P'nin BY satır × BX sütunluk karosunu hesaplar. Shared memory olmadan blok BX·BY·2·width okuma yapar; karolarla M'den BY·width, N'den BX·width okur. Azalma = 2·BX·BY / (BX + BY). 16×8: 256/24 ≈ 10,7×. 32×8: 512/40 = 12,8× (matris boyutundan bağımsız). Kare T×T için bu T'ye eşittir.

Tiled kernel

Thread'ler Md ve Nd elemanlarını işbirliğiyle shared belleğe yükler, sonra iç çarpımda bunları kullanır. Shared bellek küçük olduğu için Md ve Nd, shared'a sığan karolara bölünür ve iç çarpım fazlara ayrılır: faz m'de her thread M karosundan ve N karosundan birer eleman yükler.

__global__ void MatrixMulKernel(float* Md, float* Nd, float* Pd, int width)
{
    __shared__ float Mds[TILE_WIDTH][TILE_WIDTH];
    __shared__ float Nds[TILE_WIDTH][TILE_WIDTH];
    int bx = blockIdx.x, by = blockIdx.y;
    int tx = threadIdx.x, ty = threadIdx.y;
    int Row = by * TILE_WIDTH + ty;     // bu thread'in P satırı
    int Col = bx * TILE_WIDTH + tx;     // bu thread'in P sütunu
    float Pvalue = 0;
    for (int m = 0; m < width / TILE_WIDTH; ++m) {           // faz döngüsü
        Mds[ty][tx] = Md[Row * width + (m * TILE_WIDTH + tx)];   // M[Row][m*T + tx]
        Nds[ty][tx] = Nd[(m * TILE_WIDTH + ty) * width + Col];   // N[m*T + ty][Col]
        __syncthreads();                                      // (1) karolar dolsun
        for (int k = 0; k < TILE_WIDTH; ++k)
            Pvalue += Mds[ty][k] * Nds[k][tx];
        __syncthreads();                                      // (2) herkes kullanmayı bitirsin
    }
    Pd[Row * width + Col] = Pvalue;
}
  • M yükleme: satır Row sabit (thread'in satırı), sütun m*T + tx: faz m'deki karonun tx. sütunu. Warp'ta tx ardışık → coalesced.
  • N yükleme: satır m*T + ty, sütun Col: faz m'deki karonun ty. satırı. Yine tx (Col'un içinde) en sağda → coalesced.
  • Hesap: Mds[ty][k] = P satırının k. elemanı, Nds[k][tx] = P sütununun k. elemanı. Toplam width/T faz × T terim = width terim, CPU versiyonuyla aynı.
  • Neden iki bariyer? (1) Yazmalardan sonra: diğer thread'lerin yüklediği Mds[ty][k], Nds[k][tx] okunacak; karo dolmadan okunmamalı. (2) Hesaptan sonra: bir sonraki faz Mds/Nds'nin üzerine yazacak; hızlı bir thread diğerleri hâlâ okurken yazmamalı.
  • Thread başına global okuma: naive 2·width, tiled 2·width/T → T kat az. Bu kod width'in TILE_WIDTH'in katı olduğunu varsayar.

Kare olmayan blokla (ör. dim3(8,32)) aynı fikir: 2. vize rehberindeki çözüm.

Sınama

cudaMalloc((void**)&Md, size) çağrısında neden &Md veriliyor?

  1. Md host belleğinde ayrılacağı için.
  2. Boyutu bayt cinsinden vermek için.
  3. Fonksiyon ayırdığı adresi Md değişkenine yazabilsin diye.
  4. Veriyi Md'ye kopyalamak için.

256 thread'lik bloklarla bir SM'de 3 blok varsa SM'de kaç warp vardır?

  1. 8
  2. 24
  3. 768
  4. 32

Naive matmul'ün CGMA oranı neden 1'dir?

  1. Her shared bellek erişimine bir FP işlem düşer.
  2. Her thread bir eleman okur.
  3. Her thread bir register kullanır.
  4. Her turda 2 global okuma ve 2 FP işlem (çarpma, toplama) yapılır.

Tiled kernel'deki ikinci __syncthreads() kaldırılırsa ne olabilir?

  1. Bir thread bir sonraki fazın karosunu yüklerken başka bir thread hâlâ önceki fazın değerlerini okuyor olabilir.
  2. Derleme hatası olur.
  3. Pd'ye yazma coalesced olmaz.
  4. Hiçbir şey olmaz; ikinci bariyer gereksizdir.

__constant__ değişkenler için hangisi doğru?

  1. On-chip ayrı bir bellekte tutulur, önbelleğe gerek yoktur.
  2. Kernel içinde bildirilir.
  3. Tüm grid'ler aynı versiyonu görür; global bellekte saklanır ama önbelleklenir.
  4. Kernel'ler içine yazabilir.
